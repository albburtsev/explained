Предыдущий урок закончился тем, что исходные данные поступают в платформу. Задания загрузки данных записывают их в объектное хранилище в виде файлов — обычно Parquet, колоночного формата, который так удобен для аналитических сканирований. Здесь и начинается следующая проблема: папка, полная файлов Parquet, — ещё не таблица. У неё нет согласованной схемы, нет способа добавить столбец, не трогая историю, нет определения «текущего содержимого» и нет правила, которое помешало бы двум пишущим процессам испортить работу друг друга.

`Apache Iceberg` — открытый табличный формат для огромных аналитических наборов данных: спецификация метаданных, которые превращают набор файлов в объектном хранилище в таблицу со схемой, версиями и безопасной одновременной записью. Документация Iceberg описывает это как добавление таблиц в вычислительные движки — Spark, Trino, PrestoDB, Flink, Hive, Impala — с помощью формата, который «работает точно так же, как SQL-таблица».

Воспринимайте его как стандарт, а не как продукт. Ничто не запускает Iceberg так, как запускают PostgreSQL. Движки встраивают библиотеку Iceberg, а таблицы — это файлы, которые может открыть любой другой движок с поддержкой Iceberg.

## Что такое Iceberg

Решение, из которого вытекает всё устройство формата, умещается в одну фразу спецификации: этот табличный формат отслеживает отдельные файлы данных таблицы, а не директории. Принадлежность к таблице задаётся явным списком, а не правилом «всё, что оказалось в этой папке».

Этот список — дерево файлов метаданных с указателем на вершине:

```text
catalog
  `- table name -> current metadata file
                     |  schema, partition spec, properties, snapshot history
                     `- snapshot -> manifest list
                                      |- manifest -> data files + statistics
                                      `- manifest -> data files + statistics
```

У каждого уровня своя роль:

- `Файл метаданных` (metadata file) — JSON-документ, в котором хранятся схема таблицы, конфигурация партиций, свойства и снимки. Каждое изменение таблицы записывает *новый* файл метаданных; уже записанные файлы метаданных никогда не редактируются.
- `Снимок` (snapshot) — состояние таблицы в определённый момент, то есть полный набор файлов данных, которые она тогда содержала.
- `Список манифестов` (manifest list) принадлежит одному снимку и перечисляет манифесты, из которых тот состоит, вместе с диапазонами партиций и числом файлов для каждого манифеста. Благодаря этому движок может пропустить манифесты, которые заведомо не подходят под запрос.
- `Манифест` (manifest) перечисляет файлы данных с их значениями партиций и статистикой по столбцам, например диапазонами значений и числом null. Манифесты переиспользуются между снимками, поэтому небольшой коммит не переписывает всю опись.
- `Каталог` (catalog) хранит последнее звено: указатель от имени таблицы, например `sales.orders`, на её текущий файл метаданных.

Именно статистика на уровнях списка манифестов и манифестов делает всё это быстрым. Движок сужает сканирование, читая метаданные, а не перечисляя содержимое хранилища. Спецификация прямо называет цель: планировать сканирование за O(1) удалённых вызовов, а не за O(n), когда число вызовов растёт вместе с числом партиций или файлов.

## Как работает коммит

Пишущий процесс выполняет свою работу в стороне, а затем делает её видимой за один шаг:

1. Записать новые файлы данных. Файлы неизменяемы и записываются сразу на своё место: их никогда не перемещают и не изменяют.
2. Записать новые манифесты, новый список манифестов и новый файл метаданных, описывающий получившийся снимок.
3. Попросить каталог переключить указатель таблицы с базового файла метаданных на новый.

Пока шаг 3 не завершился успешно, читатели ничего не видят. На этом атомарном переключении целиком держится гарантия изоляции в Iceberg: читатели используют снимок, который был текущим в момент загрузки таблицы, и последующие коммиты их не затрагивают, пока они не обновят таблицу.

Одновременную запись регулирует `оптимистичная конкурентность` (optimistic concurrency). Пишущий процесс исходит из того, что за время его работы ничего не изменилось; если к моменту коммита указатель уже сдвинулся, переключение не проходит, и процесс повторяет попытку поверх новой текущей версии. Некоторые операции умеют заново применить свои изменения, не переделывая всю работу.

Две знакомые возможности появляются сами собой, если хранить старые снимки. `Time travel` позволяет запросу прочитать указанный более ранний снимок, так что отчёт становится воспроизводимым. `Откат` (rollback) возвращает указатель таблицы на заведомо исправный снимок после неудачной загрузки — это изменение метаданных, а не восстановление из резервной копии.

## Зачем он нужен

Iceberg создавался в ответ на недостатки вполне конкретного предшественника. В раскладке в стиле Hive таблица *была* директорией, партиция — поддиректорией вроде `event_date=2026-09-01`, а файлы внутри — данными. У этого соглашения четыре изъяна, с которыми рано или поздно сталкивается любая команда, использующая его в больших масштабах.

**Нет атомарного коммита.** Задание, которое пишет файлы в директорию, становится частично видимым ещё во время работы, а замена партиции означает удаление одних файлов и запись других с промежутком между этими шагами. Читатели видят недоделанные состояния. В Iceberg коммит — это одно переключение указателя.

**Планирование через перечисление.** Чтобы найти файлы для чтения, нужно перечислять содержимое директорий, и стоимость этого растёт с числом партиций и файлов. Объектные хранилища перечисляют медленно, и Iceberg был намеренно спроектирован так, чтобы решить проблемы корректности в объектных хранилищах с итоговой согласованностью, избегая перечислений и переименований. Вместо этого Iceberg читает дерево метаданных.

**Партиционирование на совести пользователя.** Hive нужно явно передавать значения партиций, потому что он не знает, что `event_date` выводится из `event_time`. Документация Iceberg без обиняков перечисляет последствия: если пишущий процесс использует неверный формат или не тот исходный столбец, результаты молча оказываются неверными вместо ошибки; читатель, забывший фильтр по партиции, сканирует всю таблицу; а работающие запросы привязаны к физической раскладке, так что её нельзя изменить, не сломав их.

Ответ Iceberg — `скрытое партиционирование` (hidden partitioning). Для таблицы задаётся преобразование — `day(event_time)` или бакет по идентификатору, — и Iceberg сам вычисляет значения партиций и запоминает эту связь. Потребители никогда не видят столбец партиции:

```sql
-- Hive-style: the writer supplies event_date, and the reader must filter on it
SELECT level, count(*) FROM logs
WHERE event_time BETWEEN TIMESTAMP '2026-09-01 10:00:00' AND TIMESTAMP '2026-09-01 12:00:00'
  AND event_date = '2026-09-01';

-- Iceberg table partitioned by day(event_time): the filter on the real column is enough
SELECT level, count(*) FROM logs
WHERE event_time BETWEEN TIMESTAMP '2026-09-01 10:00:00' AND TIMESTAMP '2026-09-01 12:00:00';
```

**Небезопасная эволюция.** Раз запросы больше не называют значения партиций, раскладку можно менять. `Эволюция партиционирования` (partition evolution) — операция над метаданными: старые данные сохраняют прежнюю спецификацию, новые записываются по новой, обе живут в одной таблице, и запрос планируется отдельно для каждой раскладки. Переход с помесячных партиций на подневные больше не требует новой таблицы.

Изменения схемы тоже затрагивают только метаданные. Iceberg отслеживает каждый столбец по уникальному идентификатору поля (field ID), поэтому добавление, удаление, переименование, перестановка столбцов и расширение типа не трогают файлы данных. По той же причине удалённый столбец не воскреснет, если его имя позже используют снова, — а в форматах, которые сопоставляют столбцы по имени или позиции, это вполне реальная опасность.

## Версии формата

Спецификация версионируется отдельно от Java-библиотеки, и номер версии важен, когда вы смешиваете движки.

- **V1** управляет аналитическими таблицами поверх неизменяемых файлов Parquet, Avro и ORC.
- **V2** добавляет построчные обновления и удаления через файлы удалений (delete files), так что одну строку можно удалить или заменить, не переписывая её файл данных.
- **V3** расширяет типы и метаданные: временные метки с наносекундной точностью, `variant`, геометрия и география, значения столбцов по умолчанию, преобразования с несколькими аргументами, происхождение строк (row lineage), бинарные векторы удалений (deletion vectors) и ключи шифрования таблиц.

Версии 1, 2 и 3 завершены и приняты; версия 4 активно разрабатывается и формально ещё не принята. Текущий релиз реализации Apache — 1.11.0, вышедший в мае 2026 года. Движки поддерживают новые возможности спецификации неравномерно, поэтому, прежде чем включить какую-то из них, проверьте движки, которыми действительно пользуетесь.

## Где проходят его границы

- **Это не движок запросов.** Сам по себе Iceberg ничего не планирует и ничего не вычисляет. Читать его должно что-то другое — то, чему посвящён следующий урок, или Spark, или Flink.
- **Это не база данных и не инструмент для OLTP.** Здесь нет точечного поиска за миллисекунды: чтобы получить одну строку, нужно обратиться к метаданным и просканировать файл данных. Как правило, нет ни обязательных первичных ключей, ни уникальности, ни внешних ключей, ни построчных транзакций. База данных вашего приложения сюда не переедет.
- **Запись — это коммиты, а не обновления.** Свежесть измеряется коммитами: строка становится видимой вместе со своим снимком. Частые мелкие записи означают частые снимки, а обновить несколько строк — значит записать файлы удалений или перезаписать файлы данных, но не править их на месте.
- **Мелкие файлы копятся, а обслуживание — ваша забота.** Потоковая загрузка данных порождает множество мелких файлов, которые раздувают метаданные и замедляют запросы из-за накладных расходов на открытие каждого файла. Снимки и старые файлы метаданных тоже накапливаются и удерживают устаревшие файлы данных. Уплотнение (compaction), истечение срока снимков, очистка метаданных и удаление файлов-сирот — это задания по расписанию, у которых должен быть владелец. Отчасти поэтому в курсе и есть последний урок.
- **Он зависит от каталога.** Атомарность целиком держится на компоненте, способном безопасно переключить указатель: сервисе REST-каталога, Hive metastore, AWS Glue, базе данных через JDBC или чём-то подобном. Такой каталог — общая зависимость и единственный источник истины для имён; два движка, настроенные на разные каталоги, смотрят на разные таблицы.
- **Он не заменяет файловый формат.** Строки по-прежнему хранят Parquet, ORC и Avro. Iceberg описывает, какие из этих файлов принадлежат таблице и что они означают.

## Типичные сценарии использования

Iceberg хорошо подходит, когда эти условия встречаются вместе:

- **Большие таблицы, куда в основном дописывают данные и которые питает непрерывная загрузка данных**, — если читателям нужно согласованное представление, пока загрузка продолжает делать коммиты.
- **Одна таблица, несколько движков.** Пакетная обработка, ad hoc SQL и фреймворки машинного обучения читают одни и те же таблицы без отдельного шага экспорта для каждого.
- **История, к которой нужно обращаться запросами.** Воспроизводимые отчёты, аудит и возможность отката после неудачной загрузки.
- **Точечные удаления и обновления в data lake, который в остальном неизменяем**, например удаление строк одного клиента по его запросу.
- **Таблицы, которые переживут свой первоначальный замысел.** Схемы и раскладки партиций, которые будут меняться годами без отдельного проекта миграции на каждое изменение.
- **Уход с хранилища в раскладке Hive**, где стоимость перечислений и дисциплина партиций стали ежедневной проблемой.

Это неверный выбор, когда данных так мало, что на любой вопрос ответит одна управляемая база данных, когда нужна транзакционная обработка или отклик быстрее секунды, или когда никто не возьмёт на себя задания обслуживания, которые поддерживают таблицы в порядке.

## Проверьте себя

1. Почему читатель никогда не видит недописанную запись в Iceberg?
2. Запрос к таблице в раскладке Hive фильтрует по `event_time`, но не по столбцу партиции `event_date`. Что произойдёт и чем отличается поведение Iceberg?
3. Ваше задание добавляет столбец в таблицу с десятилетней историей. Сколько данных будет переписано?
4. Два задания Spark одновременно делают коммит в одну и ту же таблицу. Что определяет исход?
5. Потоковое задание делает коммит в таблицу Iceberg каждые десять секунд, и с каждой неделей запросы работают всё медленнее, хотя объём данных невелик. Какова вероятная причина?

Ожидаемые ответы: 1. Сначала записываются файлы данных, а частью таблицы они становятся только тогда, когда каталог атомарно переключает указатель таблицы на новый файл метаданных. 2. Hive просканирует все файлы, потому что не знает о связи двух столбцов; Iceberg выводит значение партиции через преобразование и применяет фильтр автоматически. 3. Нисколько: изменение схемы — операция над метаданными, а идентификаторы полей сохраняют существующие файлы читаемыми. 4. Оптимистичная конкурентность: побеждает первое переключение, а второй пишущий процесс повторяет попытку поверх новых текущих метаданных. 5. Множество мелких файлов, а также накопившиеся снимки и метаданные, которым нужны уплотнение и истечение срока.
