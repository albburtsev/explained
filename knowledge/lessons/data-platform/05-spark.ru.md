В предыдущем уроке Trino отвечал на SQL-вопросы по таблицам lakehouse. Но кто-то должен эти таблицы построить. Сырые файлы нужно очистить, соединить и переписать в таблицы, удобные для отчётов, — часто за годы истории. Такая работа может длиться часами и обязана пережить отказ машины. Большинство платформ поручают её Apache Spark.

`Apache Spark`, по его собственному определению, — «унифицированный аналитический движок для обработки данных большого масштаба». Он выполняет ваш код на кластере машин: читает данные из хранилища, преобразует их и записывает результат обратно. Как и Trino, своих данных он не хранит. Но, в отличие от Trino, это не только SQL-движок, а универсальный движок для программ, обрабатывающих данные.

## Что такое Spark

Программа на Spark называется приложением. У каждого приложения есть один `driver` — процесс, который выполняет вашу основную программу, планирует работу и координирует её. Сами вычисления выполняют `executors` — процессы на машинах кластера, которые запускают задачи и хранят данные этого приложения. Машины приложению выделяет `cluster manager`, менеджер кластера. Spark поддерживает собственный менеджер Standalone, Hadoop YARN и Kubernetes.

Работу вы описываете через API `DataFrame` — похожий на таблицу набор данных с именованными столбцами, доступный в Python, Scala, Java и R. Spark SQL работает на том же движке, поэтому в одном задании можно смешивать SQL и код на DataFrame. Вот небольшое задание на PySpark. Предполагается, что в сессии уже есть каталог Iceberg с именем `lakehouse`:

```python
from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.appName("daily-revenue").getOrCreate()

orders = spark.table("lakehouse.sales.orders")
daily = (
    orders
    .where(F.col("status") == "paid")
    .groupBy(F.to_date("created_at").alias("day"))
    .agg(F.sum("total").alias("revenue"))
)

daily.writeTo("lakehouse.marts.daily_revenue").createOrReplace()
```

Первые строки не читают никаких данных. Spark различает `трансформации` (transformations), такие как `where` и `groupBy`, и `действия` (actions), такие как запись или сбор результата. Трансформации ленивы: Spark их только запоминает. Последняя строка — действие, и лишь тогда Spark планирует всю цепочку целиком и запускает её. Видя цепочку заранее, оптимизатор может прочитать только нужные столбцы и передать фильтр на уровень файлов.

Действие запускает `задание` (job). Spark делит задание на `этапы` (stages) в каждой точке `shuffle` — шага, на котором строки перемещаются между машинами, например чтобы все строки одного `day` встретились в одном месте для `groupBy`. Каждый этап — это набор задач, по одной на каждый срез данных, и executors выполняют их параллельно.

Два проектных решения делают Spark пригодным для долгой работы:

- **Shuffle идёт через диск.** Во время shuffle промежуточные файлы записываются на диск, и лишь потом их читает следующий этап. Это стоит времени, зато, если упадёт более поздний этап, предыдущий не придётся начинать заново.
- **Потерянная работа вычисляется повторно.** Spark помнит трансформации, из которых получен каждый фрагмент данных; эту цепочку называют lineage. Когда executor выходит из строя, Spark заново вычисляет только потерянные фрагменты и повторяет упавшие задачи. Задание продолжается.

Поверх того же движка у Spark есть и библиотеки более высокого уровня: Structured Streaming для потоковой обработки, MLlib для машинного обучения и pandas API. Текущая линейка релизов — Spark 4. Spark 4.2.0 вышел в июле 2026 года.

## Зачем он нужен

Spark появился в лаборатории AMPLab Калифорнийского университета в Беркли как более быстрый преемник Hadoop MapReduce. MapReduce записывал результаты на диск после каждого шага и умел выражать только map, за которым следует reduce. Многошаговые пайплайны и итеративные алгоритмы, например алгоритмы машинного обучения, работали медленно, а писать их было неудобно. Spark по возможности держит данные в памяти между шагами и позволяет одной программе описать целый граф шагов.

В платформе данных у Spark обычно три роли:

- **Трансформация в масштабе.** Чтение сырых данных и запись очищенных, соединённых и агрегированных таблиц Iceberg. Задание может длиться часами и переживает сбои по ходу дела.
- **Логика за пределами SQL.** Разбор неаккуратных форматов, вызов библиотек Python, построение признаков для машинного обучения. Код на DataFrame способен на то, что в SQL сделать трудно или невозможно.
- **Обслуживание таблиц.** Iceberg поставляет процедуры Spark для задач обслуживания, о которых шла речь в уроке про Iceberg, — например, для уплотнения файлов и удаления устаревших снимков:

```sql
CALL lakehouse.system.rewrite_data_files(table => 'sales.orders');
```

## Где его пределы

**Он медленно стартует.** Прежде чем что-либо сделать, приложение должно получить executors у менеджера кластера. Каждый этап добавляет накладные расходы на планирование. Для двухчасового задания секунды или минуты запуска ничего не значат, но из-за них Spark плохо подходит на роль движка за интерактивным дашбордом.

**Это не база данных.** Spark не владеет хранилищем и не сохраняет таблицы между приложениями — разве что через каталог и записанные им файлы. OLTP здесь нет: ни чтения по ключу за миллисекунды, ни обслуживания запросов приложения.

**Производительность определяет shuffle, а настройка — это настоящая работа.** Перемещение данных между машинами — самая дорогая часть большинства заданий. Число партиций для shuffle по умолчанию равно `200`, каким бы ни был объём данных. Перекошенные ключи отправляют большую часть строк в одну задачу, и тогда всё задание ждёт именно её. Adaptive Query Execution, включённый по умолчанию начиная со Spark 3.2, исправляет часть этих проблем во время выполнения, но не все. Настройки памяти, размеры партиций и стратегии соединения по-прежнему остаются вашей заботой.

**Driver — узкое место по замыслу.** Действия вроде `collect()` вытягивают весь результат в память driver. На большом наборе данных driver от этого падает. Результаты должны уходить в хранилище, а не в driver.

**За Python приходится платить.** Встроенные функции DataFrame выполняются внутри движка. Пользовательская функция на Python заставляет Spark отправлять строки в процесс Python и обратно, а это гораздо медленнее. Предпочитайте встроенные функции, а функции на Python используйте только для логики, у которой нет встроенного аналога.

**Потоковая обработка по умолчанию построена на микропакетах.** Structured Streaming обрабатывает поток как серию небольших пакетных заданий со сквозной задержкой примерно от 100 миллисекунд. Этого достаточно, чтобы записывать потоки в таблицы, но это не обработка каждого события по отдельности.

**Для небольших данных он избыточен.** Если данные помещаются на одну машину, обычная база данных или локальный инструмент позволят написать решение быстрее и обойдутся дешевле в работе. Сложность Spark оправдана лишь тогда, когда данным или обработке действительно нужен кластер.

## Типичные сценарии

- **Построение таблиц lakehouse.** Ночные и ежечасные задания, превращающие сырые файлы в смоделированные таблицы Iceberg.
- **Backfill и повторная обработка.** Перезапись многолетней истории после изменения логики, когда задание длинное и не должно падать из-за одной потерянной машины.
- **Обслуживание таблиц.** Уплотнение файлов, удаление устаревших снимков и очистка осиротевших файлов через процедуры Spark из Iceberg.
- **Пайплайны машинного обучения.** Построение признаков на больших наборах данных, обучение моделей и расчёт прогнозов с помощью MLlib или библиотек Python.
- **Потоковая загрузка данных (ingestion).** Задания Structured Streaming, которые каждые несколько секунд или минут записывают поступающие данные в таблицы.

## Spark и Trino

Оба — распределённые движки. Оба читают одни и те же таблицы Iceberg и не хранят собственных данных. Оба понимают SQL. Но создавались они для разной работы, и отсюда вытекают все различия.

| | Trino | Spark |
| --- | --- | --- |
| Для чего создан | Интерактивные SQL-вопросы | Долгие задания по обработке данных |
| Интерфейс | SQL | DataFrame в Python, Scala, Java, R, а также SQL |
| Кластер | Постоянный и общий; запросы приходят и уходят | Executors принадлежат одному приложению на всё время его работы |
| Промежуточные данные | Передаются между узлами worker потоком в памяти | Проходят shuffle через файлы на диске |
| Отказ узла | По умолчанию запрос падает; повторы включаются по желанию | Упавшие задачи перезапускаются, потерянные данные вычисляются заново |
| Типичное время работы | От секунд до минут | От минут до часов |
| Помимо SQL | Практически ничего | Потоковая обработка, машинное обучение, пользовательский код |
| Источники данных | Федерация множества систем в одном запросе | В основном файлы и таблицы lakehouse |

Практическое правило простое. Берите Trino, когда ответа ждёт человек или дашборд. Берите Spark, когда задание производит данные, которые позже прочитают другие запросы. В уроке про Trino говорилось, что шестичасовому заданию, которое должно пережить отказ узлов, место на движке пакетной обработки. Spark и есть такой движок.

Многие платформы запускают оба движка над одними и теми же таблицами. Spark их записывает и обслуживает. Trino отвечает на вопросы по ним. Пересечение реально: Trino умеет выполнять `INSERT` и `MERGE`, а Spark SQL — ad hoc запросы. Выбирайте по характеру нагрузки, а не по тому, какой движок технически способен выполнить инструкцию.

## Проверьте себя

1. Скрипт на PySpark определяет десять трансформаций и ничего не выводит. Сколько данных прочитает Spark?
2. Посреди трёхчасового задания Spark выходит из строя executor. Что произойдёт?
3. Задание с `groupBy` по `customer_id` проводит большую часть времени в одной задаче. Какова вероятная причина?
4. Аналитик хочет, чтобы дашборд над таблицей lakehouse обновлялся за две секунды. Spark или Trino?
5. Ночное задание соединяет пять больших таблиц, выполняет собственный разбор на Python и записывает новую таблицу Iceberg. Spark или Trino?

Ответы: (1) Нисколько. Трансформации ленивы, и без действия Spark не запускает ни одного задания. (2) Spark перезапускает упавшие задачи на других executors и заново вычисляет потерянные данные по их lineage. Задание продолжается. (3) Перекос ключей: на немногих клиентов приходится большая часть строк, поэтому одна задача получает львиную долю данных после shuffle. (4) Trino. Накладные расходы Spark на запуск и планирование не годятся для интерактивного дашборда. (5) Spark. Задание долгое, требует пользовательского кода и должно переживать сбои.
