Платформа данных никогда не сводится к одному заданию. Сырые файлы попадают в объектное хранилище, задание Spark записывает их в таблицу Iceberg, второе задание строит поверх этой таблицы агрегат, а отчёт читает результат через Trino. Каждый шаг зависит от предыдущего, каждый может упасть, и каждый завтра нужно будет запустить снова.

Cron может запустить все четыре шага в заданное время. Но он не умеет выразить, что агрегат должен дождаться успешного завершения загрузки данных, повторить только упавший шаг или перезапустить прошлый вторник, когда кто-то найдёт ошибку. Apache Airflow существует именно для того, чтобы закрыть этот пробел.

## Пайплайн как код на Python

Airflow называет себя «платформой для оркестрации пакетных рабочих процессов». Вы описываете рабочий процесс в файле на Python, а Airflow планирует его, запускает и показывает.

`DAG` — это один рабочий процесс: набор шагов и правила, по которым он запускается. Название происходит от *directed acyclic graph* — направленного ациклического графа: каждый шаг указывает вперёд, на зависящие от него шаги, и ни один путь не ведёт обратно к более раннему шагу. `Задача` (task) — один шаг в этом графе, а `оператор` — переиспользуемый шаблон для определённого вида задач, например для выполнения SQL-инструкции или запуска контейнера.

Современный Airflow позволяет писать задачи как Python-функции с декораторами. Такой стиль называется TaskFlow API:

```python
from airflow.sdk import dag, task


@dag(schedule="@daily", catchup=False)
def daily_orders():
    @task
    def extract() -> str:
        return "s3://raw/orders/2026-09-24"

    @task
    def load(path: str) -> None:
        print(f"loading {path}")

    load(extract())


daily_orders()
```

Вызов `load(extract())` ничего не запускает. Он объявляет, что `load` зависит от `extract`, и по этому вызову Airflow строит граф. Более старая явная форма, `extract_task >> load_task`, выражает ту же зависимость и по-прежнему часто встречается в существующих пайплайнах.

Превратить этот файл в работающие процессы помогают четыре компонента:

- **DAG processor** разбирает ваши файлы и сохраняет полученные из них рабочие процессы.
- **Планировщик** (scheduler) решает, какие экземпляры задач готовы к запуску, исходя из расписания и того, какие вышестоящие задачи уже успешно завершились.
- **Executor** — параметр конфигурации планировщика — передаёт эти задачи локальному процессу, пулу worker или подам Kubernetes.
- **База метаданных**, обычно PostgreSQL, хранит состояние задач, DAG и переменных. Это журнал того, что запускалось, когда и с каким результатом.

API-сервер обслуживает REST API и веб-интерфейс, где можно просматривать запуски, читать логи и вручную запускать DAG.

## Чего не умеет cron

Ценность Airflow — в том, что он отслеживает между запусками и между задачами.

Планировщик знает граф, поэтому запускает задачу только после успешного завершения всех её зависимостей. Состояние хранится в базе данных, поэтому сбой становится известным фактом, а не проходит незамеченным: у задачи есть политика повторов, и Airflow перезапускает только её, прежде чем признать весь запуск неудачным. К запускам можно обращаться по отдельности, поэтому, когда меняется логика или источник запаздывает, можно запустить *backfill* — копии DAG для диапазона прошлых дат.

`Сенсор` (sensor) — особый оператор, который ждёт какого-то события, например появления файла или записи партиции. Он избавляет от привычки угадывать безопасное время старта для следующего задания. В режиме `reschedule` сенсор освобождает слот worker между проверками, так что долгое ожидание не удерживает ресурсы.

Всё это держится на одной дисциплине, которую Airflow не может обеспечить за вас: задачи должны быть `идемпотентными`, то есть повторный запуск с теми же параметрами должен давать тот же результат, а не дубликат. Официальные рекомендации прямо указывают на типичную ошибку: заменяйте `INSERT` на upsert и читайте фиксированную партицию, а не «самые свежие данные», чтобы повторная попытка не могла испортить результат.

Airflow 3, вышедший в апреле 2025 года, добавил версионирование, благодаря которому запуск завершается на той версии DAG, с которой начался; перенёс backfill в планировщик; ввёл API выполнения задач, отделяющий код задач от базы данных; научился запускать работу по внешним событиям, а не только по часам.

## Где заканчиваются возможности Airflow

Airflow — оркестратор пакетной обработки, и документация чётко обозначает эту границу: он «спроектирован для конечных рабочих процессов, ориентированных на пакетную обработку» и «не предназначен для непрерывно работающих, событийно-управляемых или потоковых нагрузок». Непрерывным потоком занимается потоковая система, а Airflow подхватывает данные уже после неё, пакетами.

Кроме того, это не движок обработки данных. Airflow запускает работу в других системах — запрос Trino, задание Spark, контейнер — и фиксирует её результат. Данные не должны проходить через планировщик. Механизм `XCom`, который передаёт значения между задачами, «рассчитан только на небольшие объёмы данных; не используйте его для передачи больших значений, таких как датафреймы».

Ещё два ограничения определяют, что стоит помещать в DAG. Запуск задачи несёт ощутимые накладные расходы, от задержки планирования до старта процесса или пода, поэтому сотни односекундных задач тратят больше времени на запуск, чем на работу; объединяйте их в пакеты. Кроме того, Airflow не универсальная очередь заданий: он плохо подходит для работы на каждый запрос, с низкой задержкой или высокой частотой, с которой лучше справляются очередь и worker.

Соседняя категория — оркестрация рабочих процессов приложений, которой посвящён курс по Temporal на этом сайте: Temporal надёжно сохраняет состояние одного длительного бизнес-процесса, а Airflow планирует зависимые пакетные запуски над наборами данных.

## Типичные сценарии

Airflow подходит для работы, у которой есть чёткое начало и конец и которая повторяется:

- ELT по расписанию: загрузка сырых данных, а затем построение таблиц и агрегатов в порядке их зависимостей.
- Обслуживание таблиц, например уплотнение файлов или удаление устаревших снимков в таблицах lakehouse.
- Backfill и повторная обработка после исправления ошибки или запоздавшего источника.
- Пайплайны машинного обучения: построение признаков, обучение моделей и пакетный расчёт прогнозов.
- Последовательности шагов в разных системах, где один запоздавший или упавший шаг должен остановить всё, что идёт после него.
