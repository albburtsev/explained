Как разработчик приложений вы уже работаете с системой данных: это база данных за сервисом, со схемой, индексами и транзакциями. Она отвечает на вопросы вроде *что лежит в заказе 4812?* за миллисекунду, тысячи раз в секунду, пока другие запросы пишут в те же самые строки.

Теперь бизнес задаёт вопрос иного рода: *как за последние три года менялось среднее время доставки по регионам у клиентов, впервые сделавших заказ во время акции?* В самом вопросе нет ничего необычного, и всё же ваша рабочая база данных — неподходящее место, чтобы на него отвечать. Такой запрос прочитает бо́льшую часть таблицы, на минуты займёт ресурсы и будет соперничать с тем самым трафиком, ради которого система существует. К тому же нужные ему данные разбросаны по разным местам: заказы — в базе одного сервиса, отгрузки — в базе другого, события кликов — в логе.

Платформа данных нужна, чтобы отвечать на вопросы второго рода, не вредя системам первого. Этот урок даёт карту: из каких функций складывается платформа и какой инструмент за что отвечает. Следующие уроки по очереди разбирают каждый инструмент.

## Два вида нагрузки

Различие, из которого вырастает вся платформа, — это `OLTP` (online transaction processing, оперативная обработка транзакций) и `OLAP` (online analytical processing, оперативная аналитическая обработка). Это не два продукта, а две нагрузки с противоположными требованиями.

| | OLTP | OLAP |
| --- | --- | --- |
| Типичный запрос | Прочитать или записать несколько строк по ключу | Просканировать миллионы строк и агрегировать несколько столбцов |
| Целевая задержка | Миллисекунды | От секунд до минут |
| Конкурентность | Много мелких параллельных транзакций | Немного крупных запросов |
| Охват данных | Текущее состояние одного сервиса | Много источников, включая историю |
| Оптимизировано для | Корректной изолированной записи | Дешёвого чтения больших объёмов |
| Раскладка хранения | Обычно построчная | Обычно колоночная |

Всё остальное определяет последняя строка. Транзакционная база хранит поля одной строки вместе, потому что транзакция затрагивает строки целиком. Аналитическая система хранит вместе значения каждого столбца, потому что отчёт читает три столбца из восьмидесяти и хочет пропустить остальные, не читая их. Одни и те же данные, разложенные под другой вопрос.

Отсюда первый принцип платформы: скопировать данные из операционных систем туда, где всё устроено под вторую нагрузку, и поддерживать эту копию в актуальном состоянии. Всё остальное вытекает из этой фразы.

## Четыре функции

Почти любая аналитическая платформа, из чего бы она ни была собрана, распадается на четыре функции.

**Загрузка данных (ingestion) и доставка событий.** Извлечь данные из систем, которые их производят, — баз данных приложений, сервисов, устройств, сторонних API — и доставить их в платформу: либо пакетами, либо непрерывно, по мере того как происходят события. Главные трудности этого слоя — развязка (производитель не должен ждать каждого потребителя), буферизация (потребители отстают и должны догонять) и повторное воспроизведение (replay): потребителю, который сутки был неисправен, снова нужны вчерашние данные.

**Хранение и табличный формат.** Место, где данные лежат. Современные платформы держат байты в `объектном хранилище` — сервисе, который хранит файлы по имени, дёшево и надёжно, и не требует поддерживать работающий сервер. Однако дешёвые файлы сами по себе ещё не таблицы. У директории с файлами нет схемы, нет способа безопасно изменить одну запись и нет способа уберечь два пишущих процесса от порчи работы друг друга. `Табличный формат` — это слой метаданных, который превращает набор файлов в таблицу со столбцами, типами, версиями и правилами одновременной записи.

**Вычислительные движки.** Компоненты, которые читают слой хранения, распределяют работу между многими машинами и возвращают строки или записывают новые таблицы. Одни движки созданы, чтобы интерактивно отвечать на SQL-вопросы. Другие — для долгих заданий, которые преобразуют большие объёмы данных. В этой архитектуре движки отделены от хранилища: данные не находятся «внутри» движка, и одни и те же таблицы может читать не один движок.

**Оркестрация.** Платформа — это не один пайплайн, а сотни зависимых задач: загрузить, очистить, соединить, агрегировать, опубликовать. Они должны выполняться в правильном порядке, по расписанию, с повторными попытками при сбое шага и с возможностью перезапустить прошлый вторник, когда ошибку исправят. `Оркестратор` владеет этим графом зависимостей и его выполнением.

Эти четыре функции — разделение труда, а не строгая последовательность. Данные могут возвращаться по кругу: результат одного движка становится новой таблицей, которую читает другое задание.

## Место каждого инструмента

Вот как в эту картину укладывается остальная часть курса.

| Функция | Инструмент в этом курсе | Роль в одной строке |
| --- | --- | --- |
| Загрузка данных | В курсе не рассматривается | Выгрузки, потоки изменений или событийные пайплайны, которые доставляют исходные данные в платформу |
| Хранение и табличный формат | Apache Iceberg | Метаданные таблиц, благодаря которым файлы в объектном хранилище ведут себя как настоящие таблицы со схемами и версиями |
| Архитектурный паттерн | Lakehouse | Подход, при котором таблицы в духе data warehouse живут прямо в хранилище data lake, а не загружаются в warehouse |
| Вычисления: интерактивные запросы | Trino | Распределённый SQL-движок, который выполняет запросы к большим наборам данных в источниках, которыми он не владеет |
| Вычисления: обработка данных | Apache Spark | Распределённый движок для долгих заданий, которые преобразуют данные и строят таблицы |
| Оркестрация | Apache Airflow | Платформа для разработки, планирования и мониторинга рабочих процессов с пакетной обработкой (batch), описанных в виде кода |

Некоторые из этих мест стоит пояснить уже сейчас: именно в них новички ошибаются чаще всего.

Для загрузки данных в курсе нет инструмента. Курс считает, что исходные данные просто поступают в объектное хранилище, и начинается там, где они оказываются.

Iceberg — это спецификация, а не работающий сервис. Ничто не «запускает Iceberg» так, как запускают базу данных. Он определяет, как метаданные описывают таблицу, чтобы независимые движки могли безопасно и одновременно читать и записывать одну и ту же таблицу.

Trino — движок запросов без собственного хранилища. Его документация прямо говорит, что это не реляционная база данных общего назначения и что он не проектировался для OLTP: он создан для аналитики — сканирования, агрегации, отчётов. Он читает таблицы Iceberg в объектном хранилище, а ещё умеет напрямую читать ваши операционные базы данных.

Spark выполняет ту же вычислительную функцию, что и Trino, и их легко спутать. Оба читают одни и те же таблицы, и оба принимают SQL. Trino создан для вопросов, ответа на которые ждёт человек или дашборд. Spark — для долгих заданий, которые готовят данные для последующих запросов. Урок о Spark подробно сравнивает их.

Airflow планирует работу и следит за ней, но сам не перемещает и не преобразует данные. Задача лишь поручает работу какой-то другой системе. Модель Airflow ориентирована на пакетную обработку — запуски с началом и концом, — поэтому непрерывными потоками событий занимаются другие системы.

## Путь одного вопроса через платформу

Возьмём вопрос о времени доставки из начала урока и проследим его путь.

1. Задания загрузки данных копируют данные о заказах и отгрузках из баз сервисов и кладут их файлами в объектное хранилище. Сами сервисы обслуживают только собственный трафик.
2. Задание Spark читает эти файлы и записывает их в таблицы. Iceberg даёт этим таблицам схему, так что позже можно добавить столбец, не переписывая историю, а читатели никогда не видят незавершённую запись.
3. Следующие задания Spark очищают и соединяют сырые таблицы, превращая их в таблицы, удобные для отчётности.
4. Аналитик выполняет SQL. Trino планирует запрос, читает только нужные столбцы нужных файлов на многих машинах и возвращает результат.
5. Airflow отвечает за шаги 2 и 3: что запускать, в каком порядке, как часто, что делать при сбое шага и как перезапустить прошедший день.

Рабочая база данных появляется лишь на самом левом краю, как источник. В этом и состоит смысл всей конструкции.

## Карта — не закон

Четыре блока — это способ рассуждать, а не закон природы.

- **Границы пересекаются.** Trino умеет записывать таблицы, Spark — отвечать на ad hoc SQL-запросы, а некоторые оркестраторы сами выполняют преобразования. Вендоры намеренно объединяют блоки.
- **Не у каждой платформы есть все четыре.** Для небольшой компании полноценной платформой может стать одна аналитическая база данных. Выгрузки по расписанию — вполне законный способ загрузки данных. Заводить четыре системы ради одного отчёта — плохая сделка.
- **Эти инструменты распространены, но не обязательны.** Для каждой строки таблицы есть достойные альтернативы, и роли важнее названий.

Судите об архитектуре по тому, есть ли у каждой функции владелец и подходит ли он для неё. Именно на этот вопрос курс учит отвечать.

## Проверьте себя

1. Почему колоночная раскладка плохо подходит для нагрузки, которую обслуживает база данных вашего приложения?
2. Какой из четырёх функций не хватает, если данные исправно попадают в объектное хранилище, но никто не может сказать, завершилась ли вчерашняя загрузка?
3. И Trino, и Spark принимают SQL. Какой из них вы ожидаете увидеть за дашбордом, а какой — за ночным заданием, которое перестраивает большую таблицу?
4. У Trino нет хранилища. Что должно существовать, чтобы от него была польза?
5. Еженедельный отчёт строится одной выгрузкой по расписанию и одним запросом к единственной аналитической базе данных. Какие блоки пропускает такая платформа и проблема ли это?

Ожидаемые ответы: 1. Транзакция читает и записывает строки целиком, поэтому, если разнести строку по отдельным хранилищам столбцов, самая частая операция станет дорогой. 2. Оркестрации — слоя планирования, повторных попыток и наблюдаемости. 3. Trino — за дашбордом, потому что он создан для интерактивных вопросов; Spark — для ночного задания, потому что он создан для долгой обработки, которая должна переживать сбои. 4. Данные в слое хранения, который он умеет читать, и метаданные таблиц, которые их описывают. 5. Она обходится без отдельного табличного формата и отдельных вычислительных движков; это нормально, пока объём, требования к свежести и число источников остаются небольшими.
