Веб-приложение нередко загружает интерфейс с одного сервера, а данные — с другого. Например, JavaScript на `https://app.example` может обращаться к API на `https://api.example`. Для браузера это разные границы безопасности, хотя у обоих имён хостов общий родительский домен.

Обычно **same-origin policy** (политика одного источника) не позволяет JavaScript читать ответ, принадлежащий другому origin. **Cross-Origin Resource Sharing (CORS)** — это HTTP-протокол, с помощью которого сервер может ослабить это ограничение для выбранных origin. Соблюдение CORS обеспечивает браузер; это не система аутентификации и не универсальный сетевой файрвол.

## Что такое origin

**Origin** — это сочетание схемы, хоста и порта URL. Путь в него не входит.

Допустим, страница загружена с `https://app.example`:

| URL | Тот же origin? | Почему |
| --- | --- | --- |
| `https://app.example/settings` | Да | Схема, хост и порт по умолчанию совпадают. |
| `http://app.example` | Нет | Другая схема. |
| `https://api.example` | Нет | Другой хост. |
| `https://app.example:8443` | Нет | Другой порт. |

Эта граница строже, чем «тот же сайт» или «та же компания». Когда JavaScript в браузере пересекает её с помощью `fetch()`, ответ должен пройти проверку CORS, прежде чем скрипт сможет его прочитать.

## Открыть доступ к ответу осознанно

Предположим, приложение запрашивает публичный профиль:

```js
const response = await fetch('https://api.example/profiles/42');
const profile = await response.json();
```

Браузер добавляет к запросу origin страницы:

```http
GET /profiles/42 HTTP/1.1
Host: api.example
Origin: https://app.example
```

Если API намерен поделиться ответом с этим приложением, он возвращает:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: https://app.example
Vary: Origin

{"id":42,"name":"Ada"}
```

`Access-Control-Allow-Origin` называет origin, коду которого разрешено читать ответ. Если заголовка нет или он не совпадает, API всё равно может вернуть ответ `200`, но браузер не отдаст его вызвавшему JavaScript. Вот почему ошибка CORS может появиться в консоли даже тогда, когда в журнале сервера запрос значится успешным.

Добавляйте `Vary: Origin`, когда разрешённый origin выбирается динамически из списка разрешённых. Этот заголовок сообщает HTTP-кэшам, что ответы могут различаться в зависимости от origin запроса. Не копируйте произвольное значение `Origin` в `Access-Control-Allow-Origin` — сначала сверьте его с явным списком разрешённых origin.

Для ресурса, который действительно публичен и не использует учётные данные, сервер может разрешить любой origin:

```http
Access-Control-Allow-Origin: *
```

Wildcard означает, что прочитать этот ответ может любой origin. Он уместен для публичных данных, но не для закрытых эндпоинтов.

## Как проходит preflight

Некоторые cross-origin запросы невозможно создать обычной HTML-формой. Прежде чем отправить такой запрос, браузер, как правило, выполняет **preflight-запрос** методом `OPTIONS`. Например, `PUT` с JSON вызывает preflight:

```http
OPTIONS /profiles/42 HTTP/1.1
Host: api.example
Origin: https://app.example
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type
```

API может одобрить предложенные origin, метод и заголовки:

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Methods: PUT
Access-Control-Allow-Headers: Content-Type
Access-Control-Max-Age: 600
Vary: Origin
```

Лишь после успешного preflight браузер отправляет сам `PUT`. `Access-Control-Max-Age` позволяет браузеру кэшировать это разрешение на ограниченное время.

Запросам с методами и заголовками из списка CORS-safelisted preflight не нужен. Поэтому cross-origin `GET` или `POST`, похожий на отправку формы, может дойти до сервера раньше, чем браузер проверит, можно ли отдать скрипту ответ. Никогда не считайте наличие preflight авторизацией и не полагайтесь на один лишь CORS, чтобы предотвратить изменение состояния.

## Осторожно с учётными данными

По умолчанию cross-origin `fetch()` не передаёт учётные данные. Если приложению нужны cookie или HTTP-аутентификация, его код явно включает их:

```js
const response = await fetch('https://api.example/account', {
  credentials: 'include',
});
```

Ответ тоже должен явно это разрешить:

```http
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Credentials: true
Vary: Origin
```

Для запроса с учётными данными `Access-Control-Allow-Origin: *` недопустим: сервер должен вернуть конкретный разрешённый origin. Обычные механизмы управления cookie, включая `SameSite` и политики браузера в отношении сторонних cookie, по-прежнему действуют.

Разрешая учётные данные, вы даёте скриптам одобренного origin возможность читать данные от имени аутентифицированного пользователя. Держите список разрешённых origin как можно короче и по-прежнему аутентифицируйте пользователя и авторизуйте каждую операцию на сервере.

## Не размывать границу безопасности

CORS определяет, может ли код в браузере прочитать cross-origin ответ, а для запросов с preflight — продолжит ли браузер отправку предложенного запроса. Но он не решает всех проблем, связанных с другими сайтами:

- **Аутентификация и авторизация:** клиент вне браузера CORS не ограничен. Сервер по-прежнему должен выяснять, кто обращается и что ему разрешено.
- **Подделка межсайтовых запросов (CSRF):** некоторые cross-origin запросы отправляются без preflight. То, что ответ скрыт, не отменяет изменения состояния. Защищайте действия, аутентифицируемые через cookie, такими мерами, как подходящие настройки `SameSite` у cookie, CSRF-токены и проверка origin на сервере.
- **Межсайтовый скриптинг (XSS):** вредоносный код, уже выполняющийся в разрешённом origin, получает все его полномочия. Предотвращайте внедрение кода и используйте дополнительные браузерные политики как эшелонированную защиту.
- **Кликджекинг:** CORS не определяет, может ли чужая страница встроить ваш документ во фрейм. В следующем уроке для этой границы используется директива CSP `frame-ancestors`.
- **Открытые редиректы:** CORS не проверяет адрес перенаправления. Приложение само должно ограничивать допустимые адреса — как правило, известными origin или локальными путями.

Полезно спрашивать не «Включён ли CORS?», а «Какой ответ может прочитать какой origin и с какими учётными данными?». Такая формулировка привязывает политику к конкретному решению о доверии.

## Как спроектировать узкую политику

Выбирайте поведение CORS для каждого ресурса отдельно, а не применяйте одно разрешительное правило ко всему серверу:

| Ресурс | Кто должен обращаться | Подходящая политика |
| --- | --- | --- |
| Публичный каталог товаров | Любой сайт, без учётных данных | `Access-Control-Allow-Origin: *` |
| API учётной записи | `https://app.example`, с cookie | Точный разрешённый origin, `Access-Control-Allow-Credentials: true` и `Vary: Origin` |
| Внутренний административный API | Никаких cross-origin обращений из браузера | Не отправлять заголовки CORS; аутентификация и авторизация по-прежнему обязательны |

Затем разрешите только те методы и заголовки запроса, которые действительно нужны браузерному клиенту. Широкие разрешения CORS — вовсе не настройка для удобства: они расширяют круг origin, способных читать ответы вашего API.

## Как разобраться в неудачном запросе

Проследите работу протокола на панели Network в браузере:

1. Убедитесь, что у страницы и целевого URL действительно различаются схема, хост или порт.
2. Посмотрите на заголовок `Origin` в запросе.
3. Если появился запрос `OPTIONS`, проверьте его статус и соответствие значений `Access-Control-Allow-Methods` и `Access-Control-Allow-Headers`.
4. Убедитесь, что в самом ответе есть ровно одно подходящее значение `Access-Control-Allow-Origin`.
5. Для запроса с учётными данными проверьте точный origin и `Access-Control-Allow-Credentials: true`; не заменяйте origin на `*`.

Перевести запрос на фронтенде в `mode: 'no-cors'` — не значит исправить CORS. Обычно в результате JavaScript получает непрозрачный (opaque) ответ, тело и бо́льшую часть метаданных которого прочитать невозможно.

## Практика

Спроектируйте заголовки ответа для двух эндпоинтов:

1. `GET https://api.example/timezones` отдаёт публичные данные, которые может читать любой сайт, и никогда не использует учётные данные.
2. `PUT https://api.example/account` принимает JSON только от `https://app.example` и использует сессионную cookie.

Для каждого эндпоинта определите разрешённый origin, решите, допустимы ли учётные данные, и ожидается ли preflight. Задание выполнено, если первая политика использует публичный wildcard без учётных данных, а вторая — точный origin приложения, разрешает `PUT` и `Content-Type` на этапе preflight, возвращает `Access-Control-Allow-Credentials: true` и сохраняет обычную аутентификацию, авторизацию и защиту от CSRF на сервере.
