**Content Security Policy (CSP)** is a set of instructions that a server sends to a browser, usually in the `Content-Security-Policy` response header. The policy limits capabilities of the protected page: which scripts can run, where images can load from, which endpoints JavaScript can contact, where forms can submit, and who may embed the page.

CSP and CORS enforce different boundaries. CORS controls whether a script may read a cross-origin response. CSP controls capabilities of the current document and can prevent a request or action even when CORS would otherwise allow it. Neither policy grants application permissions or replaces server-side authorization.

## Read a policy as a set of directives

A policy is a semicolon-separated list of **directives**. Each directive governs one kind of capability and contains one or more allowed **source expressions**:

```http
Content-Security-Policy: default-src 'none'; script-src 'nonce-6R6d7M7JwLw2oTQqj8Xxvg'; style-src 'self'; img-src 'self' https://images.example; connect-src 'self' https://api.example; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'
```

Read the important pieces from left to right:

- `default-src 'none'` denies resource types that fall back to this directive unless another directive permits them.
- `script-src 'nonce-…'` permits only script elements carrying the matching one-time value.
- `style-src 'self'` permits styles from the page's own origin.
- `img-src 'self' https://images.example` permits same-origin images and images from one explicit HTTPS origin.
- `connect-src` limits destinations used by APIs such as `fetch()`, `XMLHttpRequest`, and WebSocket.
- `object-src 'none'` disables plugin-style embeds such as `<object>`.
- `base-uri 'none'` prevents an injected `<base>` element from changing how relative URLs are resolved.
- `form-action 'self'` limits form submissions to the page's own origin.
- `frame-ancestors 'none'` prevents every origin, including the page's own origin, from embedding the response in a frame.

`'self'` represents the protected resource's own origin. `'none'` means no source. Keywords such as these require single quotes; host sources do not.

Not every directive falls back to `default-src`. In particular, `base-uri`, `form-action`, and `frame-ancestors` must be written explicitly when you need those restrictions. Also distinguish the similarly named framing directives: `frame-src` controls which frames this page may load, while `frame-ancestors` controls which pages may frame this page.

## Allow intended scripts without allowing every inline script

An injected script is useful to an attacker only if the browser executes it. A strict CSP can require each intended script to carry an unpredictable **nonce** generated by the server for one response:

```http
Content-Security-Policy: script-src 'nonce-6R6d7M7JwLw2oTQqj8Xxvg'; object-src 'none'; base-uri 'none'
```

The server places the same value on scripts that belong to that response:

```html
<script nonce="6R6d7M7JwLw2oTQqj8Xxvg" src="/assets/app.js"></script>
```

The value above is only an example. In a real application, generate at least 128 random bits with a cryptographically secure generator for every response, put the encoded value in both the header and the intended script elements, and never insert untrusted text into a nonce-bearing script. A reused or predictable nonce stops being a useful trust signal. A static site can use CSP hashes instead, but each hash must change when its script content changes.

Avoid weakening `script-src` with `'unsafe-inline'` or broad sources merely to silence violations. `'unsafe-inline'` permits the inline script patterns that a strict policy is meant to block, while any script loaded from an allowed origin executes with the page's authority. Keep trusted code and origins narrow.

CSP is defense in depth, not an XSS repair. Continue to encode output, sanitize allowed HTML, avoid dangerous DOM APIs, and validate input. The policy reduces what an injection flaw can execute if one of those primary defenses fails.

## Stop clickjacking with `frame-ancestors`

In a **clickjacking** attack, an attacker places a real page inside a disguised or transparent frame and tricks a user into clicking its controls. The protected response can tell the browser which ancestor pages, if any, may frame it:

```http
Content-Security-Policy: frame-ancestors 'none'
```

Use `'none'` when the page never needs embedding. Use `'self'` when same-origin pages may embed it, or list the exact trusted origins when another site has a legitimate framing use case. The browser checks the full ancestor chain, not only the immediate parent.

Deliver this directive in an HTTP response header. A CSP supplied through `<meta http-equiv="Content-Security-Policy">` cannot enforce `frame-ancestors`, and it also cannot provide report-only monitoring. The response header is therefore the reliable default for a complete policy.

## Know what CSP does not fix

An **open redirect** occurs when an application accepts an untrusted destination and redirects a user to it, for example:

```text
https://app.example/redirect?next=https://attacker.example
```

CSP does not validate the server's `Location` response header and does not repair this route. `form-action` can restrict where HTML forms submit, but it is not a general navigation or redirect policy. Fix an open redirect in application logic: accept only local paths when that is sufficient, or compare destinations against a small allowlist of exact trusted origins and reject everything else.

Apply the same boundary test to other vulnerabilities. CSP can restrict browser behavior, but it cannot correct broken access control, unsafe database queries, missing request validation, or insecure business rules.

## Deploy without breaking the application

A new policy can block legitimate scripts, fonts, API calls, or integrations. Start by sending the candidate policy with the monitoring header:

```http
Content-Security-Policy-Report-Only: default-src 'none'; script-src 'nonce-6R6d7M7JwLw2oTQqj8Xxvg'; style-src 'self'; img-src 'self' https://images.example; connect-src 'self' https://api.example; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'
```

Report-only mode records violations but does not block the behavior. Exercise important pages and inspect the browser console or a configured reporting endpoint. For each violation, decide whether the resource is required. Add the narrowest source that supports a real use case; do not automatically add a wildcard or an unsafe keyword.

Once normal flows produce the expected results, send the policy as `Content-Security-Policy` so the browser enforces it. Continue monitoring after deployment because new features and third-party resources can change what the application needs. Treat violation reports as diagnostic, potentially attacker-controlled data rather than proof that an attack succeeded.

## Check your understanding

Assume this illustrative policy and its nonce were generated for one response:

```http
Content-Security-Policy: default-src 'none'; script-src 'nonce-course123'; img-src 'self' https://images.example; connect-src 'self' https://api.example; form-action 'self'; frame-ancestors 'none'
```

For each action, predict whether the browser allows or blocks it before reading the answers:

1. `<script nonce="course123" src="/app.js"></script>` executes.
2. `<script src="/legacy.js"></script>` executes without a nonce.
3. The page loads `https://images.example/logo.svg` in an `<img>`.
4. JavaScript calls `fetch("https://tracker.example/event")`.
5. A page on `https://partner.example` embeds this page in an `<iframe>`.
6. The server redirects `/redirect?next=https://attacker.example` to the supplied destination.

The browser allows 1 and 3. It blocks 2 because the script has no matching nonce, 4 because the destination is absent from `connect-src`, and 5 because `frame-ancestors` allows no ancestor. Item 6 is outside this policy: the server can still issue the unsafe redirect until application logic rejects the destination.
