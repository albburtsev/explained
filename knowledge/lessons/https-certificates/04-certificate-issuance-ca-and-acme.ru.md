Доверенная цепочка позволяет браузеру установить, кто подписал сертификат. Прежде чем поставить подпись, центр сертификации должен убедиться, что заявитель вправе запросить указанные в нём имена. Выпуск сертификата связывает это право с открытым ключом.

## Подготовьте ключ и запрос

Администратор или управляемый сервис хостинга создаёт ключевую пару для сертификата. Закрытый ключ должен оставаться под контролем сервера или сервиса, который принимает TLS-соединения. Центру сертификации нужен открытый ключ; закрытый ему не требуется.

`Запрос на подпись сертификата (CSR)` — это подписанный запрос на выпуск сертификата. Для HTTPS он содержит открытый ключ и запрошенные имена SAN. Запрос подписывают соответствующим закрытым ключом. Подпись доказывает владение этим ключом, но не подтверждает контроль над доменом.

CA проверяет запрос и выполняет необходимые проверки подлинности. Затем формирует сертификат, назначает срок действия и серийный номер и подписывает его собственным закрытым ключом. Подпись CSR и подпись сертификата создаются разными ключами. См. [структуру запроса PKCS #10](https://www.rfc-editor.org/rfc/rfc2986.html#section-3) и [объяснение выпуска у Let's Encrypt](https://letsencrypt.org/how-it-works/).

## Разберитесь, что проверяет CA

Эти обозначения описывают проверки перед выпуском:

- `Domain Validation (DV)` подтверждает контроль над запрошенными доменными именами. Личность компании при этом не проверяют.
- `Organization Validation (OV)` дополнительно подтверждает подлинность организации, указанной в сертификате.
- `Extended Validation (EV)` предусматривает более подробные проверки подлинности организации и права заявителя подать запрос.

[DigiCert описывает эти уровни проверки](https://www.digicert.com/difference-between-dv-ov-and-ev-ssl-certificates). Они определяют, какие сведения о владельце проверит CA. Сами по себе они не делают шифрование трафика TLS более стойким. Стойкость зависит от алгоритмов и ключей, которые использует соединение; их роль описана в [TLS 1.3](https://www.rfc-editor.org/info/rfc9846/).

## Автоматизируйте выпуск с помощью ACME

`ACME` (Automatic Certificate Management Environment) — протокол для автоматизации запросов на сертификаты и проверки доменов. Его использует Let's Encrypt. Клиент ACME может работать на вашем сервере или внутри управляемого сервиса.

У клиента есть `ключ аккаунта`, который подтверждает подлинность запросов к CA. Он должен отличаться от ключа сертификата, используемого TLS-сервером. [ACME требует такого разделения](https://www.rfc-editor.org/rfc/rfc8555.html#section-11.1).

Обычный выпуск нового сертификата проходит в четыре шага:

1. Клиент создаёт `order` — заявку со списком нужных доменных имён.
2. CA предлагает `challenges` — задания, которые позволяют доказать контроль над этими именами. Клиент готовит ответы и просит CA проверить их.
3. Когда необходимые разрешения получены, клиент отправляет CSR для завершения заявки. Запрошенные в нём имена должны совпадать с именами в заявке.
4. CA выпускает сертификат. Клиент загружает его вместе с цепочкой промежуточных сертификатов.

Ключ аккаунта подтверждает подлинность обмена по ACME. Ключ сертификата подписывает CSR, а позже удостоверяет TLS-сервер. Контроль над доменом проверяют отдельно. [RFC 8555 описывает работу с заявками](https://www.rfc-editor.org/rfc/rfc8555.html#section-7.4).

## Проследите проверку HTTP-01

Рассмотрим условный запрос для `api.example.com`. Это пример процесса, а не домен, который можно использовать для собственного выпуска.

При `HTTP-01` клиент публикует значение по определённому HTTP-пути:

1. CA выдаёт новый токен.
2. Клиент готовит ответ из токена и отпечатка открытого ключа аккаунта.
3. Он публикует ответ по адресу `http://api.example.com/.well-known/acme-challenge/<TOKEN>`.
4. CA обращается по этому URL и проверяет ответ, прежде чем разрешить выпуск.

Первоначальный запрос идёт на порт `80`; выбрать другой порт нельзя. Через прокси или балансировщик этот путь должен вести к обработчику проверки. Если ответить могут несколько серверов, каждый должен возвращать правильное значение. HTTP-01 не позволяет проверить wildcard-имя. [Let's Encrypt описывает HTTP-01](https://letsencrypt.org/docs/challenge-types/#http-01-challenge).

## Используйте DNS-01, когда HTTP не подходит

При `DNS-01` клиент публикует TXT-запись DNS с именем `_acme-challenge.api.example.com`. Её значение — хеш, полученный из токена и открытого ключа аккаунта, а не просто сам токен. CA ищет ожидаемое значение в публичном DNS.

DNS-01 позволяет проверить `*.example.com`; запись для такой проверки размещают на `_acme-challenge.example.com`. Веб-серверу не нужен публичный доступ, но ответ DNS должен быть виден извне. Прежде чем запускать проверку, дождитесь распространения изменений DNS. Для автоматизации используйте учётные данные API DNS с минимально доступными правами. [Let's Encrypt описывает DNS-01 и обращение с учётными данными](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge).

Публичные CA не выпускают сертификаты для `localhost` или частных имён вроде `app.test`. Для локальной разработки можно использовать частный CA, которому доверяют ваши клиенты. Это следует из [правил имён в публичных сертификатах](https://cabforum.org/working-groups/server/baseline-requirements/documents/CA-Browser-Forum-TLS-BR-2.3.1.pdf) и [рекомендаций Let's Encrypt для localhost](https://letsencrypt.org/docs/certificates-for-localhost/).

## Проверьте право центра на выпуск

`Certification Authority Authorization (CAA)` — запись DNS, которая позволяет ограничить список CA, имеющих право выпускать сертификаты для домена. Успешная проверка домена не отменяет ограничение CAA. CAA управляет выпуском, но не меняет хранилище доверия браузера. [Let's Encrypt объясняет CAA](https://letsencrypt.org/docs/caa/).

## Проверьте себя

Ваш API доступен только во внутренней сети, но вы контролируете публичный DNS его зарегистрированного домена. Вам нужен wildcard-сертификат. Какой способ проверки подойдёт и нужно ли отправлять CA закрытый ключ?

**Ответ:** подойдёт DNS-01: опубликуйте требуемую TXT-запись в публичном DNS. HTTP-01 не поддерживает wildcard и требует доступного извне HTTP-обработчика. Отправьте подписанный CSR с открытым ключом. Соответствующий закрытый ключ оставьте под своим контролем.
