Переключиться на другую ветку посреди незаконченной работы обычно значит спрятать полуготовые изменения в stash, закоммитить промежуточное состояние или держать на диске второй клон репозитория. Встроенный ответ Git на эту проблему — `worktree`: дополнительный рабочий каталог, привязанный к тому же репозиторию, со своей собственной веткой. Каталог, созданный `git init` или `git clone`, называется `основным worktree` (main worktree); каждый дополнительный, созданный командой `git worktree add`, — `связанным worktree` (linked worktree).

Все worktree одного репозитория разделяют общий каталог `.git`: базу объектов, конфигурацию и ссылки — ветки, теги, remote и stash. Коммит, сделанный в одном worktree, сразу виден из всех остальных, а создание worktree никогда не копирует историю, поэтому обходится гораздо дешевле второго клона. (Редкие исключения — ссылки, принадлежащие отдельному worktree, например `refs/bisect`.) У каждого worktree остаются свои собственные `HEAD` (какая ветка или какой коммит сейчас извлечены), индекс (staging area) и рабочие файлы. В корне связанного worktree лежит не каталог `.git`, а небольшой *файл* `.git`. Он указывает на служебные файлы этого worktree, которые хранятся в основном репозитории в `.git/worktrees/<name>`.

Извлечённое состояние ветки связано с одним индексом и одним рабочим каталогом, поэтому Git отказывается извлекать одну и ту же ветку сразу в двух worktree. Чтобы посмотреть на ветку, которая уже извлечена в другом месте, либо отсоедините `HEAD` флагом `-d`, либо обойдите эту защиту флагом `--force`.

## Добавление worktree

Классический сценарий — срочное исправление в другой ветке, пока текущая работа остаётся ровно там, где была:

```sh
git worktree add -b hotfix-login ../hotfix-login main
```

Команда создаёт новую ветку `hotfix-login`, начинающуюся от `main`, и извлекает её в `../hotfix-login`. Закоммитьте и отправьте исправление оттуда — исходный каталог при этом не затрагивается. Чтобы работать с уже существующей веткой, укажите её имя после пути:

```sh
git worktree add ../review-ui feature-ui
```

Если локальной ветки `feature-ui` нет, но она есть ровно в одном remote, Git создаст локальную ветку, отслеживающую удалённую, — точно так же, как это сделал бы `git switch`. Если не указать ветку вовсе, Git назовёт новую ветку по последнему компоненту пути: `git worktree add ../experiments` создаст ветку `experiments` от `HEAD`. Для одноразовой копии, не привязанной ни к какой ветке, используйте отсоединённый режим:

```sh
git worktree add -d ../scratch v2.4.1
```

## Просмотр worktree

```sh
git worktree list
```

```text
/home/alice/project       3f9a1c2 [main]
/home/alice/hotfix-login  8b4e07d [hotfix-login]
/home/alice/scratch       3f9a1c2 (detached HEAD)
```

Первым в списке идёт основной worktree, за ним — каждый связанный со своим коммитом и веткой. Заблокированные worktree и те, что можно удалить через prune, помечаются особо, а `--verbose` объясняет причину. `--porcelain` выдаёт стабильный формат, удобный для скриптов.

## Перемещение, удаление и prune

```sh
git worktree move ../scratch ../spikes/scratch   # relocate a worktree
git worktree remove ../hotfix-login              # delete it and its administrative files
```

`remove` согласится удалить только чистый worktree — без изменённых отслеживаемых файлов и без неотслеживаемых. Поэтому сначала закоммитьте изменения, уберите их в stash или отбросьте, либо передайте `--force`. Основной worktree нельзя ни переместить, ни удалить, а worktree с подмодулями нельзя переместить. Если вы перенесли worktree вручную, а не через `git worktree move`, выполните `git worktree repair` с любой из сторон, чтобы восстановить связь.

Если удалить каталог worktree самостоятельно через `rm -rf`, его служебная запись в `.git/worktrees` останется. Такие записи убираются так:

```sh
git worktree prune -n -v   # show which stale entries would be removed
git worktree prune         # remove them
```

`prune` трогает только те записи, чьего рабочего каталога уже нет. Когда его автоматически запускает `git gc`, записи моложе трёх месяцев по умолчанию сохраняются. Этот льготный срок настраивается через `gc.worktreePruneExpire`, а при ручном запуске можно передать `--expire <time>`.

## Блокировка worktree

Worktree на переносном диске или сетевом ресурсе кажется пропавшим всякий раз, когда устройство отключено, и потому становится кандидатом на prune. Защитите его блокировкой:

```sh
git worktree lock --reason "lives on a USB drive" ../backup
git worktree unlock ../backup
```

Заблокированный worktree никогда не удаляется через prune, и его нельзя переместить или удалить, пока блокировка не снята. `git worktree list` помечает такой worktree, а `--verbose` показывает причину блокировки.

## Когда worktree нужны, а когда нет

Worktree оправдывают себя, когда:

- Срочное исправление или ревью прерывает работу в беспорядочном незаконченном дереве, и при stash легко потерять из виду перемещённые, переименованные и неотслеживаемые файлы.
- Вы изучаете ветку коллеги или запускаете её тесты, не трогая собственную рабочую копию.
- Долгая сборка или прогон тестов должны продолжаться в одной ветке, пока вы работаете в другой.
- Вы хотите сравнить две ветки бок о бок или держать стабильную копию релиза для поддержки.

Лучше выбрать что-то попроще, когда:

- Дело займёт пару минут: у `git switch` или `git stash` меньше механики, чем у создания worktree и последующего его удаления.
- Каждой копии нужен тяжёлый генерируемый контент вроде `node_modules` или артефактов сборки. Он не разделяется между worktree, так что каждый из них платит полную цену установки и сборки — временем и местом на диске. Неотслеживаемые файлы вроде `.env` тоже придётся копировать вручную.
- Ваши инструменты рассчитывают, что `.git` — это каталог, а у связанного worktree вместо него файл `.git`.
- В репозитории есть подмодули: руководство по-прежнему называет работу с несколькими копиями экспериментальной, а поддержку подмодулей в ней — неполной, поэтому не заводите несколько worktree одного суперпроекта.

Worktree незаметно накапливаются, поэтому закрывайте их командой `git worktree remove`, когда задача решена, и время от времени проводите ревизию с помощью `git worktree list`.
