Обычный `git log` идёт по коммитам, достижимым из той ветки, которую вы попросили показать. После жёсткого reset, rebase, исправленного через amend коммита или удаления ветки ценные коммиты могут пропасть из этой истории, хотя их объекты по-прежнему существуют. `reflog` (reference log, журнал ссылок) записывает недавние значения подвижных ссылок Git в одном локальном репозитории. Он даёт ещё один способ найти такие коммиты, пока Git в конце концов их не удалил.

У каждой локальной ветки может быть собственный reflog. Есть он и у `HEAD`: туда попадают как коммиты, так и действия, которые переводят вас с ветки на ветку. Reflog — это локальный учёт: он не коммитится, не отправляется на сервер и не копируется, когда кто-то клонирует репозиторий. Поэтому ваш reflog описывает то, что происходило в вашем клоне, а не в клоне коллеги и не на хостинге.

## Чтение reflog

Запустите команду без подкоманды, чтобы увидеть reflog для `HEAD`:

```sh
git reflog
```

`show` — явная форма той же операции:

```sh
git reflog show HEAD
git reflog show main --date=local
```

Сокращённый пример после случайного reset может выглядеть так:

```text
51a62bd HEAD@{0}: reset: moving to HEAD~2
8db42f1 HEAD@{1}: commit: Validate payment details
d3a710c HEAD@{2}: commit: Add checkout form
51a62bd HEAD@{3}: commit: Create product page
```

Хеш в каждой строке — это значение, которое ссылка получила после записанного действия. Здесь `HEAD@{0}` — текущее положение после reset, а `HEAD@{1}` — коммит, бывший прежней вершиной ветки. Сообщение поясняет, какая операция сдвинула ссылку.

Селекторы reflog работают везде, где Git принимает ревизию:

```sh
git show HEAD@{1}               # the previous value of HEAD
git show main@{2}               # the second prior value of main
git show 'main@{yesterday}'     # where local main pointed yesterday
git switch @{-1}                # the previously checked-out branch or commit
```

Число отсчитывает обновления ссылки, а не коммиты, а селектор с датой спрашивает, куда указывала эта локальная ссылка в заданный момент. Новые действия добавляют записи и сдвигают порядковые номера, поэтому, найдя нужную запись, скопируйте хеш коммита.

## Безопасное восстановление

Если коммит, похоже, потерян, не запускайте команды обслуживания вроде `git gc` и `git reflog expire`. Затем, прежде чем менять текущую ветку, сделайте коммит-кандидат снова достижимым с помощью временной ветки:

```sh
git reflog --date=local
git show --stat 8db42f1
git branch rescue-before-reset 8db42f1
git log --oneline --decorate rescue-before-reset
```

Создание спасательной ветки не меняет рабочее дерево. Убедившись, что восстановленная история верна, можно сделать cherry-pick коммита, слить спасательную ветку или намеренно передвинуть на неё другую ветку. Удаляйте спасательную ветку только тогда, когда нужная работа обрела постоянное место.

Чтобы поставить текущую ветку точно на восстановленный коммит, сначала убедитесь, что её нынешнее состояние сохранено, а в рабочем дереве нет ничего нужного, и затем выполните:

```sh
git reset --hard 8db42f1
```

`--hard` перезаписывает изменения отслеживаемых файлов в рабочем дереве. Reflog помогает вернуть закоммиченные объекты, которые ещё остаются в репозитории, но не сохраняет произвольные незакоммиченные правки, уничтоженные операциями reset, checkout или clean.

## Типичные сценарии восстановления

### Отменить нежелательный reset

Reset сдвигает текущую ветку и записывает и старое, и новое её положение. Найдите запись непосредственно перед reset, изучите её и закрепите спасательной веткой:

```sh
git reflog
git show 8db42f1
git branch rescue-before-reset 8db42f1
```

Замените хеш из примера на прежнюю вершину из вашего собственного reflog. Не рассчитывайте, что это всегда будет `HEAD@{1}`: после reset ссылки могли обновиться ещё раз.

### Восстановиться после rebase или amend

Rebase и `git commit --amend` заменяют коммиты новыми, но reflog ветки обычно сохраняет её прежнюю вершину:

```sh
git reflog show feature --date=local
git branch feature-before-rewrite 8db42f1
git log --oneline --graph --decorate --all
```

Замените хеш из примера на вершину ветки до переписывания. Когда обе вершины закреплены именованными ветками, их можно сравнить и лишь потом решить: сделать reset, перенести отдельные коммиты через cherry-pick или оставить переписанную историю.

### Воссоздать удалённую ветку

При удалении ветки удаляется и её собственный reflog. Но если вы когда-то на неё переключались, её последний коммит может ещё найтись в reflog для `HEAD`:

```sh
git reflog show HEAD
git branch restored-feature 8db42f1
```

Замените хеш из примера на последний коммит удалённой ветки. `git reflog --all` расширяет поиск на все доступные reflog. Восстановление не гарантировано, если ни один из оставшихся reflog не записал этот коммит или его объект уже удалён при очистке.

### Восстановить один файл, а не ветку

Когда reflog указал на нужный коммит, можно вернуть только потерянный файл:

```sh
git restore --source=8db42f1 -- path/to/file
git diff -- path/to/file
```

Замените хеш из примера на найденный коммит. Восстановленное содержимое остаётся незакоммиченным изменением в рабочем дереве, так что его можно проверить обычным образом.

## Подкоманды

Для просмотра полезны три подкоманды:

- `git reflog show [<ref>]` показывает один reflog; эта подкоманда подразумевается, если `show` опущено. Она принимает опции `git log`, например `--date`, `--since` и `--grep-reflog`.
- `git reflog list` перечисляет ссылки, у которых сейчас есть reflog.
- `git reflog exists <ref>` завершается успешно, если у полностью квалифицированной ссылки есть reflog, что удобно в скриптах: `git reflog exists refs/heads/main`.

Остальные подкоманды изменяют данные reflog и нужны в основном для обслуживания репозитория:

- `git reflog expire` удаляет записи по правилам, учитывающим возраст и достижимость. Прежде чем что-то чистить вручную, посмотрите результат через `git reflog expire --dry-run --all`.
- `git reflog delete <ref>@{<specifier>}` удаляет выбранные записи. Эта подкоманда тоже поддерживает `--dry-run`.
- `git reflog drop <ref>` удаляет reflog целиком. В отличие от `delete` и `expire`, у неё нет режима пробного запуска.
- `git reflog write <ref> <old-oid> <new-oid> <message>` добавляет низкоуровневую запись, принимая полностью квалифицированную ссылку и полные идентификаторы объектов. Она доступна начиная с Git 2.51.1 и в повседневной работе нужна редко.

Не начинайте восстановление с изменяющих подкоманд: они могут уничтожить те самые следы и ту защиту объектов, которые вам нужны.

## Ограничения

Reflog недолговечен. По умолчанию правила обслуживания Git удаляют записи через 90 дней, а записи о недостижимых коммитах могут быть удалены раньше — через 30 дней; оба срока меняются в конфигурации репозитория. Как только запись истекла и ни ветка, ни тег, ни другая ссылка не удерживает её объекты достижимыми, последующая сборка мусора может их удалить. Восстанавливайте важную работу без промедления.

В репозитории со связанными worktree начинайте с того worktree, где произошла ошибка: у каждого worktree свой `HEAD` и своя история переключений. Reflog веток всё равно помогает, если сдвинулась общая ссылка на ветку.

Относитесь к reflog как к локальной страховочной сетке, а не как к резервной копии. Он прекрасно подходит, чтобы вернуть недавнюю закоммиченную работу в вашем собственном клоне, но надёжно сохраняют работу удалённая ветка, тег, отправленный на сервер коммит или внешняя резервная копия.
