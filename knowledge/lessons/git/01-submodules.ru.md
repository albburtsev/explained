Иногда проекту нужен код из другого репозитория: общая библиотека, плагин или материалы, которые ведёт другая команда. Если просто скопировать файлы, пропадёт их история, а сливать изменения из upstream станет мучительно. Если же полагаться на внешнюю установку, сборку будет трудно воспроизвести. Git решает эту задачу с помощью `подмодуля` (submodule) — независимого репозитория, встроенного в ваш репозиторий как подкаталог. Ваш репозиторий в этом случае называют `суперпроектом` (superproject).

Суперпроект никогда не отслеживает файлы подмодуля. Вместо этого он хранит две вещи. Первая — файл `.gitmodules` в корне репозитория, где путь каждого подмодуля сопоставлен с URL его удалённого репозитория. Вторая — `gitlink`, особая запись дерева (режим `160000`), которая закрепляет точный коммит, на котором должен стоять подмодуль. Обе фиксируются в коммитах так же, как любые другие файлы, поэтому каждый клон суперпроекта может воссоздать одно и то же составное дерево.

## Добавление подмодуля

Внутри суперпроекта выполните `git submodule add`, передав URL репозитория и, при желании, путь назначения:

```sh
git submodule add https://github.com/example/ui-kit.git libs/ui-kit
```

Git клонирует репозиторий в `libs/ui-kit` и добавляет в индекс файл `.gitmodules` и gitlink, чтобы они попали в следующий коммит. Новая секция `.gitmodules` выглядит так:

```ini
[submodule "libs/ui-kit"]
	path = libs/ui-kit
	url = https://github.com/example/ui-kit.git
```

Чтобы опубликовать подмодуль, закоммитьте обе записи:

```sh
git commit -m "Add ui-kit submodule"
```

Выбирайте URL, доступный каждому, кто будет клонировать суперпроект: именно из `.gitmodules` их Git в первую очередь возьмёт адрес для загрузки. В своём клоне URL можно переопределить командой `git config submodule.libs/ui-kit.url <url>`.

## Клонирование проекта с подмодулями

Обычный клон суперпроекта создаёт каталоги подмодулей, но оставляет их пустыми. Инициализировать и заполнить их можно за один шаг:

```sh
git submodule update --init --recursive
```

`--init` переносит URL каждого подмодуля из `.gitmodules` в ваш локальный `.git/config`, `update` клонирует недостающее и переключается на закреплённый коммит, а `--recursive` захватывает и подмодули, вложенные в другие подмодули. Всё это можно сделать прямо при клонировании:

```sh
git clone --recurse-submodules https://github.com/example/main-project.git
```

## Обновление подмодулей

### Следовать за закреплённым коммитом суперпроекта

Когда вы подтягиваете изменения суперпроекта, новые закреплённые коммиты загружаются, но рабочие копии подмодулей остаются нетронутыми. Поэтому `git status` показывает подмодули изменёнными, с пометкой «new commits». Приведите их к записанному состоянию:

```sh
git pull
git submodule update --init --recursive
```

Не убирайте `--init` даже при рутинных обновлениях: pull мог принести новый подмодуль. Можно поступить иначе — выполнять `git pull --recurse-submodules` или задать `git config submodule.recurse true`, чтобы такие команды, как pull и checkout, по умолчанию обходили подмодули. Исключение — `clone`: ему по-прежнему нужен собственный флаг.

### Передвинуть закреплённый коммит на свежую работу из upstream

Закреплённый коммит меняется только тогда, когда вы меняете его сознательно. Чтобы загрузить изменения из upstream самого подмодуля и перевести его рабочую копию на вершину отслеживаемой ветки, выполните:

```sh
git submodule update --remote libs/ui-kit
```

По умолчанию отслеживается ветка удалённого репозитория, заданная как основная. Чтобы все клоны отслеживали другую ветку, запишите её в `.gitmodules`:

```sh
git submodule set-branch --branch stable libs/ui-kit
```

После обновления добавьте в индекс и закоммитьте в суперпроекте сдвинутый gitlink: именно этот коммит переводит коллег на новую версию подмодуля. Если не указывать путь, обновятся сразу все подмодули.

### Работа внутри подмодуля

Простая команда `git submodule update` переключает подмодуль на закреплённый коммит в состоянии detached `HEAD`, то есть без ветки, которая отслеживала бы вашу работу. Прежде чем что-то править внутри подмодуля, переключитесь на ветку и попросите обновления делать merge или rebase работы из upstream в неё:

```sh
cd libs/ui-kit
git switch main
cd ../..
git submodule update --remote --merge
```

Отправляйте коммиты подмодуля раньше, чем коммит суперпроекта, который на них ссылается, иначе коллеги не смогут переключиться на закреплённый коммит. Git умеет следить за этим порядком сам:

```sh
git push --recurse-submodules=check      # fail if submodule commits are not pushed
git push --recurse-submodules=on-demand  # push submodules first, then the superproject
```

## Полезные команды

```sh
git submodule status                   # pinned versus checked-out commit per submodule
git submodule summary                  # commits gained or lost relative to HEAD
git submodule foreach 'git status'     # run a command in every checked-out submodule
git submodule sync --recursive         # adopt changed URLs from .gitmodules
git submodule deinit -f libs/ui-kit    # unregister and empty one submodule locally
```

В выводе `git submodule status` знак `-` в начале строки означает, что подмодуль не инициализирован, а `+` — что его рабочая копия больше не совпадает с закреплённым коммитом. Две настройки упрощают повседневный осмотр: `git config diff.submodule log` показывает коммиты подмодулей прямо в `git diff`, а `git config status.submodulesummary 1` добавляет сводку по подмодулям в вывод `git status`.

Чтобы убрать подмодуль из проекта, выполните `git rm libs/ui-kit` и закоммитьте результат. Команда удалит gitlink, секцию в `.gitmodules` и рабочее дерево подмодуля, а отменить это можно через `git revert`.

## Когда подмодули нужны, а когда нет

Подмодули оправдывают свою сложность, когда:

- Вам нужно дерево другого репозитория внутри вашего, на точном и воспроизводимом коммите: вендоренный сторонний код, общая внутренняя библиотека или материалы со своим циклом релизов.
- Вы развиваете зависимость и основной проект параллельно, и каждый из них нужно коммитить и отправлять в своём ритме.
- Вы делите один логический проект на несколько репозиториев, чтобы управлять его размером, объёмом загрузки или правами доступа.

Лучше выбрать что-то попроще, когда:

- Зависимость можно описать через менеджер пакетов, например npm или Maven: подмодули делают ту же работу, только с большим числом ручных шагов.
- Команду будут раздражать накладные расходы: пустые каталоги после обычного клона, неожиданный detached `HEAD` и устаревшие рабочие копии после смены ветки, если не передать `--recurse-submodules`.
- Зависимость меняется быстро, и вам не хочется проверять и коммитить каждое её обновление: закреплённый коммит означает, что обновления никогда не происходят сами.
