`OpenSpec` распространяется как npm-пакет `@fission-ai/openspec`. Пакет предоставляет интерфейс командной строки (`CLI`) в виде исполняемого файла `openspec`. Этот файл устанавливают npm или Homebrew, а дальше вы вызываете команды `openspec` напрямую и не обращаетесь к npm для работы с каждым изменением.

CLI — общий движок, на котором держатся все интеграции с агентами для программирования. Он умеет инициализировать проект, определять его `схему рабочего процесса`, сообщать о состоянии артефактов, проверять спецификации и архивировать завершённую работу. `Навык агента` добавляет к этому инструкции и здравое суждение, без которых этим движком нельзя управлять безопасно.

## Основные терминальные команды

Эти команды покрывают почти всю настройку и проверку, которая чаще всего нужна новичку:

```sh
openspec init                         # initialize the current project
openspec update                       # refresh generated agent instructions
openspec list                         # list active changes
openspec list --specs                 # list main specifications
openspec status --change <name>       # show artifact readiness and progress
openspec show <name>                  # display a change or specification
openspec validate --all --strict      # validate changes and specifications
openspec view                         # open the interactive dashboard
```

Навыки агента могут вызывать и низкоуровневые команды, например `openspec new change`, `openspec instructions` и `openspec archive`. Их можно изучить и самостоятельно, но обычно ими распоряжается навык, а вы проверяете файлы, которые он создаёт.

## Дерево проекта

Инициализированный проект хранит долговременные данные OpenSpec в каталоге `openspec/`:

```text
openspec/
├── config.yaml
├── specs/
│   └── <capability>/
│       └── spec.md
└── changes/
    ├── <change-name>/
    │   ├── .openspec.yaml
    │   ├── proposal.md
    │   ├── design.md
    │   ├── tasks.md
    │   └── specs/
    │       └── <capability>/
    │           └── spec.md
    └── archive/
        └── <date>-<change-name>/
            └── ...completed change artifacts
```

`config.yaml` выбирает схему рабочего процесса и может добавлять контекст проекта или правила для отдельных артефактов.

`Основные спецификации` лежат в `specs/` и служат источником истины о текущем, согласованном поведении системы. Они сгруппированы по возможностям (capability) и содержат требования с конкретными сценариями.

`Активные изменения` лежат в `changes/` и содержат работу, которая предложена или уже идёт. Каждое изменение живёт в собственном каталоге, поэтому его замысел, обновления поведения, технические решения и ход выполнения задач можно проверить вместе.

`Архив` в `changes/archive/` хранит завершённые изменения. Он объясняет не только то, что система делает сейчас, но и почему и как она пришла к этому.

## Основные спецификации и дельта-спецификации

Основная спецификация описывает текущее поведение. `Дельта-спецификация` внутри изменения описывает только ту разницу, которую это изменение предлагает: требования, которые нужно добавить, изменить, удалить или переименовать.

```text
openspec/specs/search/spec.md
                 ▲
                 │ merged during sync or archive
                 │
openspec/changes/improve-search/specs/search/spec.md
```

Благодаря тому что дельта хранится отдельно, можно проверять или реализовывать несколько изменений сразу и не делать вид, будто предложенное в них поведение уже стало частью системы. Когда завершённое изменение архивируется, его дельта вливается в основную спецификацию, а весь каталог изменения сохраняется как история.

## Граф зависимостей артефактов

Схема по умолчанию, построенная на спецификациях, связывает артефакты планирования так:

```text
                proposal
                /      \
             specs    design
                \      /
                  tasks
                    │
              implementation
```

Вместе `предложение`, `спецификации`, необязательный `дизайн` и `список задач` образуют `артефакты планирования`. Предложение задаёт замысел и рамки изменения. Спецификации определяют наблюдаемое поведение. Дизайн фиксирует технические решения, если изменению они нужны. Список задач превращает проверенный план в работу по реализации, ход которой можно отслеживать. `Зависимости артефактов` показывают, какие сведения делают возможным следующий артефакт. Они не мешают возвращаться к более ранним артефактам и править их, когда понимание задачи меняется.

## Файлы интеграции с агентами

`openspec init` также создаёт файлы там, где каждый выбранный агент для программирования ожидает найти навыки или команды. Например:

```text
.agents/skills/openspec-*/SKILL.md     # Codex and shared agent skills
.claude/skills/openspec-*/SKILL.md     # Claude Code skills
.claude/commands/opsx/*.md             # Claude Code commands
.opencode/skills/openspec-*/SKILL.md   # OpenCode skills
.opencode/commands/opsx-*.md            # OpenCode commands
```

Эти `файлы интеграции с агентами` — лишь адаптеры, а не сама спецификация проекта. После обновления CLI запустите `openspec update`, чтобы обновить и их. Держите каталог `openspec/` в системе контроля версий: тогда текущие требования, активные планы, задачи и история решений будут путешествовать вместе с кодовой базой.
