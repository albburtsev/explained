**Распределённая блокировка** — это ключ в Redis, который олицетворяет право выполнить определённую работу. Процесс, которому удалось создать ключ, владеет блокировкой. Любой другой процесс видит, что ключ уже существует, и отступает. Сама работа Redis ничего не говорит, поэтому блокировка действует лишь до тех пор, пока все участники договорились сначала спрашивать разрешения.

В этом уроке мы соберём такую блокировку команда за командой, а затем потратим не меньше времени на то, чего она обещать не может. Вторая часть важнее первой.

## Одна задача — одному экземпляру

Вы разворачиваете одно и то же приложение на трёх экземплярах за балансировщиком нагрузки. У каждого экземпляра свой планировщик, и в 02:00 все три просыпаются и начинают собирать ночной отчёт. Отчёт пишется трижды, письмо уходит трижды, счета подсчитываются трижды.

Нужно место за пределами трёх экземпляров, где они смогут договориться, кто пойдёт первым. Redis у них и так общий, отвечает он гораздо быстрее миллисекунды и выполняет команды по одной. Поэтому хранить флаг естественно именно в нём.

Называйте ключ по задаче, а не по экземпляру:

```text
lock:job:nightly-report
```

Одна задача — один ключ. Вторая задача по расписанию получает собственный ключ, и они никогда не блокируют друг друга.

## Захват блокировки одной командой

Сначала каждый процесс генерирует значение, которое не выдаст ни один другой процесс. На macOS для этого достаточно `uuidgen`:

```sh
$ uuidgen
9F2A6C3E-1B44-4D0A-9E77-2C5B8D41A6F3
```

Затем он пытается занять ключ:

```sh
127.0.0.1:6379> SET lock:job:nightly-report 9F2A6C3E-1B44-4D0A-9E77-2C5B8D41A6F3 NX PX 30000
OK
```

Прочитаем команду слева направо:

- `lock:job:nightly-report` — ключ, который обозначает задачу.
- `9F2A6C3E-…` — **токен** вызывающего: доказательство того, кто владеет блокировкой прямо сейчас.
- `NX` записывает ключ, только если его ещё нет.
- `PX 30000` задаёт ключу время жизни в 30000 миллисекунд.

`OK` означает, что ключ создан и этот процесс владеет блокировкой. Второй экземпляр, выполнивший ту же команду мгновением позже, не получает ничего:

```sh
127.0.0.1:6379> SET lock:job:nightly-report 4B7E1D08-55C2-4A9F-8E31-6D0FA2C74B19 NX PX 30000
(nil)
```

`(nil)` означает, что ключ уже существовал, и `NX` отказался писать. Этот экземпляр пропускает отчёт и снова засыпает.

Именно `NX` делает захват безопасным. Проверка через `EXISTS` с последующей записью через `SET` — это два сетевых обмена, и в промежутке между ними два экземпляра могут оба увидеть, что ключа нет. `NX` сворачивает проверку и запись в одну команду, а Redis доводит каждую команду до конца, прежде чем приступить к следующей. Это та же атомарность одной команды, которая обеспечила корректность счётчика в предыдущем уроке о rate limiting.

`PX` — то, что сохраняет систему живой. Если процесс, владеющий блокировкой, упадёт, будет убит или потеряет сеть, прибрать за ним будет некому. Без времени жизни ключ остался бы навсегда, и ночной отчёт больше никогда бы не запустился. С `PX` Redis освобождает блокировку сам.

Токен должен быть уникальным для каждого захвата. Постоянное значение вроде `locked` позволило бы любому процессу удалить любую блокировку, потому что каждый процесс узнавал бы это значение как своё. Токен превращает ключ в подписанную заявку: только владелец может доказать, что блокировка всё ещё принадлежит ему.

## Освобождение, которое не удалит чужую блокировку

Очевидный способ освобождения — прочитать ключ, сравнить и удалить:

```sh
127.0.0.1:6379> GET lock:job:nightly-report
"9F2A6C3E-1B44-4D0A-9E77-2C5B8D41A6F3"
127.0.0.1:6379> DEL lock:job:nightly-report
(integer) 1
```

Это неверно, и причина — в промежутке между двумя командами. Проследим, что происходит с тремя экземплярами:

1. Экземпляр A владеет блокировкой, и его отчёт собирается дольше 30 секунд.
2. A выполняет `GET`, видит свой токен и решает удалить ключ.
3. Прежде чем A отправит `DEL`, срок жизни ключа истекает сам собой.
4. Экземпляр B выполняет `SET … NX PX 30000`, получает `OK` и начинает собственный отчёт.
5. Приходит `DEL` от A и удаляет блокировку B.
6. Теперь экземпляр C захватывает блокировку, пока B ещё работает.

A удалил блокировку, которая ему больше не принадлежала. Сравнение и удаление должны происходить за один неделимый шаг, а ни одна строковая команда Redis не делает и то и другое. Это умеет Lua-скрипт:

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

Отправьте его через `EVAL`, передав ключ и токен аргументами, а не вставляя их в текст скрипта:

```sh
127.0.0.1:6379> EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:job:nightly-report 9F2A6C3E-1B44-4D0A-9E77-2C5B8D41A6F3
(integer) 1
```

`1` после скрипта — это число следующих за ним ключей. Redis заполняет таблицу `KEYS` этими именами ключей, а таблицу `ARGV` — всем, что идёт после них. Всегда объявляйте ключи таким образом, а не вписывайте их в тело скрипта.

Redis гарантирует, что скрипт выполняется атомарно: на всё время его работы сервер блокирует любую другую активность, так что ни один клиент не проскользнёт между `get` и `del`. По этой же причине скрипт должен быть коротким.

Ответ говорит, что произошло. `(integer) 1` означает, что ваш токен совпал и блокировка освобождена. `(integer) 0` означает, что ключа уже не было или он принадлежал кому-то другому: ваша блокировка истекла раньше, и только что законченная работа шла без защиты.

В Redis 8.4 появилась команда `DELEX`, которая выражает то же сравнение с удалением одной командой: `DELEX lock:job:nightly-report IFEQ 9F2A6C3E-…`. Она возвращает `1` или `0`, как и скрипт. В любой более ранней версии используйте скрипт.

## TTL, который можно обосновать

Время жизни — это срок, который вы себе отводите. Ошибиться больно в обе стороны:

- Слишком короткий TTL — и блокировка истекает, пока работа ещё идёт. Второй процесс запускает ту же задачу, а ваше освобождение ничего не удаляет.
- Слишком длинный — и упавший владелец блокирует задачу на весь этот срок. TTL в 10 минут означает до 10 минут полного бездействия после сбоя.

Измерьте, сколько задача выполняется на самом деле, и задайте TTL выше реалистичного худшего случая, а не среднего. Оставшееся время можно проверить через `PTTL`:

```sh
127.0.0.1:6379> PTTL lock:job:nightly-report
(integer) 27418
```

Если честный ответ звучит как «задача занимает где-то от 5 секунд до 20 минут», перестаньте подбирать число и продлевайте блокировку.

## Продление блокировки, пока идёт работа

**Watchdog** — это таймер внутри процесса-владельца, который периодически продлевает блокировку, пока работа продолжается. Возьмите короткий TTL, скажем 30 секунд, и отодвигайте его каждые 10 секунд. У продления та же проблема владения, что и у освобождения, поэтому и скрипт устроен так же:

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("pexpire", KEYS[1], ARGV[2])
else
  return 0
end
```

```sh
127.0.0.1:6379> EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('pexpire', KEYS[1], ARGV[2]) else return 0 end" 1 lock:job:nightly-report 9F2A6C3E-1B44-4D0A-9E77-2C5B8D41A6F3 30000
(integer) 1
```

Ответ `0` означает, что блокировка вам больше не принадлежит. Считайте это сигналом остановить работу, а не поводом повторить продление.

Продление сужает окно, в котором блокировка истекает под всё ещё выполняющейся задачей, но не закрывает его. Само продление может опоздать, потому что его отправляет тот же процесс, который может зависнуть. Не считайте, что блокировка удерживается лишь потому, что взявший её процесс ещё жив.

## Тайм-аут — не взаимное исключение

Вот та часть, которую пропускает большинство введений. Блокировка с тайм-аутом не гарантирует, что работу выполняет только один процесс.

Владелец может остановиться, сам того не зная. Долгая пауза на сборку мусора, вытесненный поток на загруженной машине, зависшая запись на диск или сетевое разделение способны заморозить процесс на секунды. Изнутри время не шло. С точки зрения Redis, TTL истёк и ключ исчез. Второй процесс совершенно законно захватывает блокировку, и теперь задачу выполняют два процесса, каждый из которых уверен, что он один.

К тому же Redis отсчитывает истечение срока жизни ключей по системным часам сервера, а не по монотонным часам, так что администратор или неверно настроенная синхронизация времени, сдвинувшие часы, могут досрочно снять блокировку.

Поэтому блокировка в Redis — хороший инструмент для **эффективности**, то есть чтобы избежать дублирующейся работы, которая просто расточительна, и плохой инструмент для **корректности**, то есть чтобы предотвратить исход, который ни в коем случае не должен случиться дважды, — например, повторное списание денег с клиента.

Когда работа действительно не должна выполниться дважды, пусть сам защищаемый ресурс отвергает устаревших писателей. **Fencing token** — это число, которое растёт с каждой выдачей блокировки и передаётся вместе с запросом:

```sh
127.0.0.1:6379> INCR lock:job:nightly-report:fence
(integer) 42
```

Владелец отправляет `42` вместе с каждой записью, а система хранения отвергает любую запись с токеном меньше наибольшего из уже принятых. Процесс, замерший дольше своего TTL, возвращается с `42`, когда новый владелец уже пишет с `43`, и его записи отклоняются. Обратите внимание на условие: это работает, только если нижестоящая система проверяет токен. Если она этого не умеет, используйте систему, созданную для консенсуса, например ZooKeeper или etcd, а не добавляйте новые команды Redis.

## Предложение Redlock — трезвым взглядом

Всё сказанное выше предполагает один master Redis. Если этот master переключится на реплику, блокировка может попросту исчезнуть, потому что репликация в Redis асинхронна: master может подтвердить ваш `SET` и упасть прежде, чем запись дойдёт до реплики. У повышенной реплики ключа блокировки нет, и следующий спросивший процесс получает `OK`.

**Redlock** — алгоритм, который Redis описывает в своей документации для решения этой проблемы. Клиент работает с N независимыми master-узлами Redis — в документации в качестве примера приведено пять — без репликации между ними. Он пытается параллельно записать один и тот же ключ с одним и тем же токеном на все узлы и считает блокировку захваченной, только если это удалось на большинстве из них, а вся попытка заняла гораздо меньше TTL. Оставшийся срок действия равен TTL за вычетом времени, ушедшего на захват. При неудаче клиент освобождает все экземпляры, к которым обращался, включая те, где, по его мнению, захватить не удалось.

Честно оценим его репутацию. Redis публикует Redlock и на той же странице ссылается на анализ Мартина Клеппмана, утверждающего, что для корректности алгоритм небезопасен, и на ответ antirez. Суть спора в том, что безопасность Redlock держится на допущениях о времени: ограниченном дрейфе часов и отсутствии пауз процесса дольше срока действия блокировки. В асинхронной системе эти допущения не выполняются. Сама документация Redis советует реализовать fencing token, если вам важна согласованность.

Практический вывод таков: Redlock повышает ваши шансы при отказе одного узла, но не превращает аренду (lease) во взаимное исключение. Используйте блокировку в Redis, чтобы избежать дублирующейся работы. Используйте fencing или систему консенсуса, когда повторное выполнение стало бы недопустимой ошибкой.

## Что меняется в Redis Cluster

Ключ блокировки соответствует одному хеш-слоту, а этот слот обслуживает один master. Значит, блокировка — объект одного узла, сколько бы узлов ни было в кластере, и она наследует все сбои этого узла: при переключении повышается реплика, которая могла не получить ключ, и блокировки больше нет. Спецификация кластера прямо говорит, что репликация асинхронна и что подтверждённые записи могут быть потеряны при переключении.

Redlock существует как раз для того, чтобы преодолеть это допущение об одном master, и делает это на независимых master-узлах, а не на кластере: Redis Cluster координирует свои узлы, а алгоритму нужно ровно противоположное.

Ваших скриптов это не касается: они работают с одним ключом, так что ограничение на многоключевые скрипты с ключами из разных слотов к ним никогда не применяется. Просто продолжайте передавать ключ через `KEYS`, чтобы клиент мог направить команду на нужный узел.

## Проверьте себя

Ответьте на вопросы, прежде чем читать дальше:

1. Два экземпляра отправляют `SET lock:job:nightly-report <token> NX PX 30000` в одну и ту же миллисекунду. Сколько из них получит `OK`?
2. Почему скрипт освобождения нельзя заменить на `GET` с последующим `DEL`?
3. Ваш скрипт освобождения вернул `(integer) 0`. Что это говорит о только что законченной работе?
4. Ночной отчёт обычно собирается за 40 секунд, но раз в месяц — за 12 минут. Достаточно ли блокировки с `PX 60000`?
5. Нужно гарантировать, что по счёту никогда не спишут деньги дважды. Хватит ли блокировки в Redis?

Ответы: 1. Ровно один: Redis выполняет команды по одной, и для второго `NX` не срабатывает. 2. Потому что между двумя командами ключ может истечь и быть захвачен другим процессом, и тогда ваш `DEL` удалит блокировку, которая вам уже не принадлежит; скрипт объединяет сравнение и удаление в один атомарный шаг. 3. Что ваша блокировка уже истекла, так что работа шла без защиты и, возможно, её выполнял ещё и другой процесс. 4. Нет: при медленном запуске блокировка истечёт через минуту, и второй экземпляр начнёт собирать отчёт; вместо этого периодически продлевайте блокировку. 5. Нет: используйте fencing token, который проверяет биллинговая система, или систему, созданную для консенсуса.
