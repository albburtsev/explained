**`redis-cli`** — терминальный клиент, который поставляется вместе с Redis. Он отправляет команды серверу Redis и печатает ответ. Языка запросов у Redis нет, поэтому `redis-cli` и есть весь интерфейс: каждый пример этого курса — команда, которую вы вводите в его приглашении.

Предыдущий урок объяснял, для чего нужен Redis. Этот даст вам работающий сервер и сеанс, в котором можно экспериментировать. Все следующие уроки опираются на эту настройку, так что доведите её до конца, прежде чем идти дальше.

## Установка Redis на macOS

Redis распространяется как формула Homebrew, поэтому на компьютере должен быть Homebrew. Установите сервер и его инструменты:

```sh
brew install redis
```

Формула устанавливает и `redis-server`, и `redis-cli`. Проверьте, что клиент доступен из командной строки: `redis-cli --version` печатает строку вроде `redis-cli 8.6.0`.

## Запуск сервера

Redis может работать как фоновая служба или на переднем плане. Для повседневной работы используйте фоновую службу:

```sh
brew services start redis
```

Homebrew регистрирует Redis в `launchd`, поэтому сервер запускается сейчас и затем при каждом входе в систему. `brew services info redis` сообщает, работает ли он, а `brew services stop redis` останавливает его, когда работа на сегодня закончена.

Запуск на переднем плане полезен, когда хочется видеть, что делает сервер. Запустите исполняемый файл напрямую:

```sh
redis-server
```

Redis выводит в терминал журнал запуска и занимает терминал. Чтобы остановить его, нажмите `Ctrl-C`. Сервер, запущенный таким образом, использует настройки Redis по умолчанию, а не конфигурационный файл, который устанавливает Homebrew, и занимает порт `6379`. Если фоновая служба уже работает, сервер на переднем плане не сможет занять этот порт и завершится с ошибкой. Запускайте что-то одно, но не оба сразу.

## Проверка подключения

Когда сервер запущен, откройте сеанс:

```sh
redis-cli
```

По умолчанию `redis-cli` подключается к `127.0.0.1` на порт `6379`. Этот адрес виден в приглашении:

```sh
127.0.0.1:6379>
```

Спросите сервер, жив ли он. `PING` — стандартная проверка работоспособности, и исправный сервер отвечает `PONG`:

```sh
127.0.0.1:6379> PING
PONG
```

Если вместо этого приглашение выглядит как `not connected>`, сервер не запущен. Запустите его и попробуйте снова.

Команду можно передать и аргументами, вовсе минуя интерактивный режим: именно так `redis-cli PING` используют в скриптах и проверках работоспособности.

## Сохранение, чтение и удаление ключа

Redis хранит **ключи**, и в каждом лежит одно значение. `SET` записывает строковое значение и отвечает простым статусом `OK`:

```sh
127.0.0.1:6379> SET user:1:name "Alice"
OK
```

`GET` читает его обратно. Строковые ответы `redis-cli` показывает в кавычках, чтобы были видны пробелы в начале и в конце:

```sh
127.0.0.1:6379> GET user:1:name
"Alice"
```

Отсутствующий ключ — не ошибка. `GET` отвечает `(nil)`, то есть пустым ответом. `EXISTS` сообщает, сколько из названных ключей существует, а `DEL` — сколько ключей он удалил:

```sh
127.0.0.1:6379> GET user:2:name
(nil)
127.0.0.1:6379> EXISTS user:1:name
(integer) 1
127.0.0.1:6379> DEL user:1:name
(integer) 1
127.0.0.1:6379> EXISTS user:1:name
(integer) 0
```

Удаление несуществующего ключа не завершается ошибкой, а возвращает `(integer) 0`. Имена команд не зависят от регистра, так что `set` и `SET` — одна и та же команда. А вот имена ключей и значения к регистру чувствительны: `user:1:name` и `User:1:Name` — два разных ключа.

## Перечисление ключей без блокировки сервера

Создайте несколько ключей, чтобы было на что посмотреть. `MSET` задаёт несколько ключей одной командой:

```sh
127.0.0.1:6379> MSET user:1 "Alice" user:2 "Bob" cart:1 "empty"
OK
```

`KEYS *` возвращает имена всех подходящих ключей, и новички хватаются за него первым делом:

```sh
127.0.0.1:6379> KEYS *
1) "user:1"
2) "cart:1"
3) "user:2"
```

Не используйте его на сервере, который чего-то стоит. Redis выполняет команды по одной в единственном потоке, а `KEYS` работает за O(N) от числа ключей в базе. На базе с миллионами ключей он занимает сервер на всё время обхода, и все остальные клиенты ждут. Официальная документация называет его отладочной командой и просит не использовать его в коде приложений.

Безопасная альтернатива — `SCAN`. Это итератор на основе **курсора**: каждый вызов выполняет небольшую часть работы и возвращает курсор вместе с частью ключей. Итерация начинается с курсора `0`:

```sh
127.0.0.1:6379> SCAN 0
1) "0"
2) 1) "user:1"
   2) "cart:1"
   3) "user:2"
```

Ответ состоит из двух частей. Первая — курсор для следующего вызова, вторая — пакет имён ключей. Передайте полученный курсор в следующий `SCAN` и остановитесь, когда сервер снова вернёт `0`. В этой крошечной базе итерация завершается уже на первом вызове.

`MATCH` фильтрует возвращаемые имена, а `COUNT` подсказывает, сколько работы выполнять за один вызов:

```sh
127.0.0.1:6379> SCAN 0 MATCH user:* COUNT 100
```

Два свойства часто удивляют. `MATCH` фильтрует уже собранный пакет, поэтому вызов вполне может вернуть пустой пакет с ненулевым курсором: о конце итерации говорит только курсор. Кроме того, полная итерация может вернуть один и тот же ключ несколько раз, так что обращайтесь с результатом как с множеством, а не как со счётчиком.

Из командной оболочки `redis-cli` проведёт весь цикл сам и напечатает по одному ключу в строке:

```sh
redis-cli --scan --pattern 'user:*'
```

## Осмотр экземпляра

`TYPE` сообщает, какую структуру данных хранит ключ, а `DBSIZE` за постоянное время считает ключи в текущей базе, не перечисляя их. В следующих уроках появятся списки, хеши и sorted sets, а все ключи, созданные до сих пор, — строки:

```sh
127.0.0.1:6379> TYPE user:1
string
127.0.0.1:6379> TYPE nothing:here
none
127.0.0.1:6379> DBSIZE
(integer) 3
```

`INFO` возвращает текстовый отчёт о сервере, разбитый на секции, такие как `server`, `clients`, `memory`, `stats` и `keyspace`. Запрашивайте одну секцию, чтобы вывод оставался читаемым:

```sh
127.0.0.1:6379> INFO keyspace
```

Секция Keyspace выводит по строке на каждую непустую базу в виде `db0:keys=3,expires=0,...`, где `keys` — число ключей, а `expires` — сколько из них имеют срок жизни. `INFO server` сообщает версию и время работы, `INFO memory` — `used_memory_human`, а `INFO stats` — `keyspace_hits` и `keyspace_misses`, которые станут важны, когда вы начнёте использовать Redis как кэш. Точный набор полей зависит от версии Redis.

## Очистка тренировочного экземпляра и выход

`FLUSHDB` удаляет все ключи в текущей базе и отвечает `OK`:

```sh
127.0.0.1:6379> FLUSHDB
OK
127.0.0.1:6379> DBSIZE
(integer) 0
```

Это чистый лист для практики, но действует команда разрушительно и немедленно. Выполняйте её только на локальном экземпляре, который принадлежит вам. `FLUSHALL` делает то же самое во всех базах сервера.

Завершите сеанс командой `QUIT` в приглашении или сочетанием `Ctrl-D`. Выход из клиента не останавливает сервер: служба Homebrew продолжает работать, пока вы её не остановите.

## Подключение к другому серверу или базе

Локальному серверу на стандартном порту никакие параметры не нужны. Во всех остальных случаях укажите хост и порт:

```sh
redis-cli -h cache.example.com -p 6380
```

Один сервер Redis содержит несколько пронумерованных логических **баз данных**, по умолчанию шестнадцать, и новые соединения всегда используют базу `0`. Это отдельные пространства имён ключей на одном сервере, а не отдельные серверы: у них общие процесс, память и конфигурация. Выберите базу при подключении:

```sh
redis-cli -n 1
```

Внутри сеанса то же самое делает `SELECT 1`, а приглашение меняется на `127.0.0.1:6379[1]>`, чтобы было видно, в какой базе вы находитесь. Нумерованные базы нужны, чтобы отделить эксперименты от настоящих данных, а не чтобы размещать несвязанные приложения.

Не передавайте пароль через `-a` в командной строке: вся команда попадёт в историю оболочки. Вместо этого поместите его в переменную окружения `REDISCLI_AUTH`, которую `redis-cli` читает автоматически.

## Замечание о Redis Cluster

Redis Cluster распределяет пространство ключей по нескольким узлам, и это меняет в этом уроке две вещи.

Добавьте `-c`, чтобы клиент следовал перенаправлениям, которые кластер присылает, когда ключ находится на другом узле:

```sh
redis-cli -c -h node1.example.com -p 6379
```

Без `-c` команда для ключа на другом узле вернёт ошибку `MOVED` вместо результата. Кроме того, кластер поддерживает только базу `0`, так что `SELECT` и `-n` недоступны.

Важнее другое: `SCAN`, `DBSIZE`, `KEYS` и `FLUSHDB` работают в пределах одного узла — они видят только ключи того узла, к которому вы подключены. Чтобы охватить весь кластер, их придётся самостоятельно выполнить на каждом узле. В остальной части курса считайте, что экземпляр один, если урок не говорит иного.

## Проверьте себя

Начните с пустой тренировочной базы и предскажите каждый ответ, прежде чем выполнить команду:

```sh
127.0.0.1:6379> FLUSHDB
127.0.0.1:6379> MSET session:a "1" session:b "2" job:1 "queued"
127.0.0.1:6379> DBSIZE
127.0.0.1:6379> EXISTS session:a session:c
127.0.0.1:6379> TYPE job:1
127.0.0.1:6379> GET job:2
127.0.0.1:6379> DEL job:1 job:2
127.0.0.1:6379> SCAN 0 MATCH session:*
```

`DBSIZE` возвращает `(integer) 3`. `EXISTS` возвращает `(integer) 1`, потому что считает только существующие ключи. `TYPE` возвращает `string`, `GET` — `(nil)`, а `DEL` — `(integer) 1`. Последний `SCAN` возвращает курсор `"0"` и ключи `session:a` и `session:b` в каком-то порядке.

Затем ответьте на вопросы без терминала:

1. Почему `KEYS *` — плохая идея на рабочем сервере с десятью миллионами ключей, а `DBSIZE` — нет?
2. Вызов `SCAN` вернул курсор `"3072"` и пустой список ключей. Итерация закончена?
3. Вы выполнили `DBSIZE` на одном узле кластера и получили `(integer) 5000`. Сколько ключей хранит кластер?

Ответы: `KEYS` блокирует однопоточный сервер на всё время полного обхода за O(N), а `DBSIZE` за постоянное время читает счётчик. Итерация не закончена: её завершает только возвращённый курсор `0`. А общее число ключей в кластере неизвестно: `5000` — доля одного этого узла.
