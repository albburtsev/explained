Ключ может исчезнуть из Redis по двум не связанным между собой причинам. **Истечение срока жизни** удаляет ключ, потому что закончился его собственный таймер. **Вытеснение** удаляет ключ, потому что серверу не хватило памяти и её пришлось освободить. Истечением срока жизни вы управляете для каждого ключа, вытеснением — для всего сервера.

Различать эти механизмы важно. Ключ с TTL в 10 минут может пропасть уже через 10 секунд, если вытеснение доберётся до него раньше. По той же причине может пропасть и ключ вовсе без TTL. Такова честная модель Redis: это кэш с возможностью задавать срок жизни, а не хранилище, которое обещает сохранить всё, что вы записали.

## Срок жизни ключа

`EXPIRE` задаёт тайм-аут в целых секундах для уже существующего ключа:

```sh
127.0.0.1:6379> SET session:1001 "alice"
OK
127.0.0.1:6379> EXPIRE session:1001 60
(integer) 1
127.0.0.1:6379> TTL session:1001
(integer) 60
```

`PEXPIRE` делает то же самое в миллисекундах. Обе команды возвращают `1`, если тайм-аут установлен, и `0`, если нет — например, потому что ключа не существует. Ключ с тайм-аутом называют **volatile**.

`TTL` сообщает, сколько секунд осталось, но два его отрицательных ответа — вовсе не длительности:

- `-1` означает, что ключ существует, но срока жизни у него нет.
- `-2` означает, что ключа не существует.

`PTTL` возвращает то же самое в миллисекундах. `PERSIST` снимает тайм-аут и снова делает ключ постоянным:

```sh
127.0.0.1:6379> PERSIST session:1001
(integer) 1
127.0.0.1:6379> TTL session:1001
(integer) -1
```

Повторный вызов `EXPIRE` для volatile-ключа просто заменяет старый тайм-аут. Начиная с Redis 7.0 замену можно сделать условной с помощью одного из флагов `NX`, `XX`, `GT` или `LT`: установить тайм-аут, только если его нет, только если он есть, только если новый срок позже прежнего или только если он раньше. `GT` и `LT` считают, что у ключа без срока жизни TTL бесконечен.

Есть и подвох: `EXPIRE` с нулевым или отрицательным тайм-аутом не назначает срок, а немедленно удаляет ключ.

## Значение и срок в одной команде

`SET` принимает срок жизни прямо в команде, так что ключ ни на миг не появляется без таймера:

```sh
127.0.0.1:6379> SET cache:product:42 "lamp" EX 300
OK
127.0.0.1:6379> TTL cache:product:42
(integer) 300
```

Параметры срока жизни взаимоисключающие:

- `EX seconds` — срок истекает через указанное число секунд.
- `PX milliseconds` — срок истекает через указанное число миллисекунд.
- `EXAT unix-time-seconds` — срок истекает в указанный абсолютный момент Unix-времени в секундах.
- `PXAT unix-time-milliseconds` — то же в миллисекундах.
- `KEEPTTL` — сохранить тайм-аут, который уже был у ключа.

Предпочитайте `SET ... EX` связке из `SET` и `EXPIRE`. Две команды оставляют окно, в котором ключ существует без тайм-аута, и если клиент упадёт именно в этот момент, ключ останется в памяти навсегда.

Redis хранит срок жизни как абсолютную временную метку, а не как обратный отсчёт. Поэтому, пока сервер выключен, часы продолжают идти, а сильный перевод часов на хосте влияет на то, какие ключи уже считаются просроченными.

## Большинство записей сбрасывает TTL

В эту ловушку попадают новички. Тайм-аут сбрасывают только команды, которые удаляют или перезаписывают ключ целиком, в том числе `DEL`, `SET` и команды `*STORE`. Команды, меняющие значение на месте, тайм-аут не трогают: `INCR` на счётчике, `LPUSH` на списке и `HSET` на поле хеша сохраняют прежний срок.

`SET` относится к первой группе, поэтому обычная перезапись незаметно делает ключ постоянным:

```sh
127.0.0.1:6379> SET session:1001 "alice" EX 60
OK
127.0.0.1:6379> SET session:1001 "alice smith"
OK
127.0.0.1:6379> TTL session:1001
(integer) -1
```

Теперь сессия живёт вечно и тихо занимает память. Исправляет это `KEEPTTL`:

```sh
127.0.0.1:6379> SET session:1001 "alice" EX 60
OK
127.0.0.1:6379> SET session:1001 "alice smith" KEEPTTL
OK
127.0.0.1:6379> TTL session:1001
(integer) 60
```

Отсчёт продолжается с того места, где остановился: выполните `TTL` через несколько секунд, и число окажется меньше. Если же нужно, чтобы перезапись запускала отсчёт заново, снова передайте `EX` и сделайте это явно.

`RENAME` переносит время жизни на новое имя. Если ключ-приёмник уже существовал, он наследует от источника всё, включая тайм-аут или его отсутствие.

## Когда истёкший ключ действительно удалён

Истёкший ключ никогда не виден клиенту. Как только срок проходит, `GET` возвращает `(nil)`, а `TTL` — `-2`. Удаление ключа из памяти — отдельный вопрос, и Redis решает его двумя способами.

Первый — **ленивое истечение**. Когда клиент обращается к ключу, Redis проверяет его срок и, если тот прошёл, тут же удаляет ключ. Пока к ключу никто не обращается, это ничего не стоит.

Второй — **активный цикл истечения**. Ключ, который больше никто не прочитает, иначе остался бы навсегда, поэтому Redis периодически выбирает несколько случайных ключей среди тех, у которых задан срок жизни, и удаляет уже просроченные. Директива конфигурации `hz` определяет, как часто выполняются такие фоновые задачи; по умолчанию — `10` раз в секунду.

Выборка случайная и частичная, и следствие стоит сформулировать прямо: истёкший ключ может ещё какое-то время занимать память, хотя прочитать его уже нельзя. Не рассчитывайте размер экземпляра так, будто память освобождается ровно в ту секунду, когда истекает TTL.

## Потолок памяти: `maxmemory`

Без ограничения Redis растёт, пока операционная система не откажется выделять ему память, — и это худший способ узнать о проблеме. `maxmemory` задаёт потолок для набора данных:

```sh
127.0.0.1:6379> CONFIG GET maxmemory
1) "maxmemory"
2) "0"
127.0.0.1:6379> CONFIG SET maxmemory 100mb
OK
```

`0` означает отсутствие ограничения и в 64-битных системах действует по умолчанию. `CONFIG SET` меняет только работающий сервер; чтобы настройка пережила перезапуск, запишите `maxmemory 100mb` в `redis.conf`.

Оставляйте запас относительно реальной памяти машины. Буферы, в которых обновления ждут отправки на реплики или в append-only-файл, намеренно не учитываются в `maxmemory`, а поле `mem_not_counted_for_evict` в `INFO memory` показывает, сколько они занимают сейчас.

## Выбор политики вытеснения

Когда занятая память превышает `maxmemory`, Redis применяет `maxmemory-policy`, пока снова не окажется ниже лимита. Политика отвечает на два вопроса: какими ключами можно пожертвовать и какой из них уйдёт первым.

| Политика | Ключи-кандидаты | Кого вытесняют |
| --- | --- | --- |
| `noeviction` | никакие | ничего не вытесняется; записи завершаются ошибкой |
| `allkeys-lru` | все ключи | дольше всех не использовавшийся |
| `allkeys-lfu` | все ключи | реже всех используемый |
| `allkeys-random` | все ключи | случайный ключ |
| `volatile-lru` | ключи с TTL | дольше всех не использовавшийся |
| `volatile-lfu` | ключи с TTL | реже всех используемый |
| `volatile-random` | ключи с TTL | случайный ключ |
| `volatile-ttl` | ключи с TTL | с наименьшим оставшимся TTL |

По умолчанию действует `noeviction`. Политику проверяют и меняют так же, как лимит:

```sh
127.0.0.1:6379> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "noeviction"
127.0.0.1:6379> CONFIG SET maxmemory-policy allkeys-lru
OK
```

При выборе помните о трёх вещах:

- LRU, LFU и `volatile-ttl` — приближения. Redis не просматривает всё пространство ключей, а берёт небольшую выборку, размер которой задаёт `maxmemory-samples` (по умолчанию `5`). Результат близок к настоящему LRU, но не совпадает с ним.
- Политика `volatile-*` ведёт себя в точности как `noeviction`, если ни у одного ключа нет TTL. Выбрав такую политику, убедитесь, что у ключей, которыми вы готовы пожертвовать, действительно есть тайм-аут.
- `allkeys-lru` — разумный выбор по умолчанию для чистого кэша, потому что небольшая часть ключей обычно обслуживает большинство чтений. К `volatile-*` обращайтесь, только когда один экземпляр смешивает данные кэша с ключами, которые не должны исчезать, а по возможности предпочитайте два отдельных экземпляра.

В Redis 8.6 появились ещё две политики, `allkeys-lrm` и `volatile-lrm`, которые выбирают ключ, дольше всех не *изменявшийся*. Метку времени они обновляют только при записи, так что чтения не защищают ключ от вытеснения.

## Счётчики памяти и вытеснения

`INFO` отражает обе половины этого урока. В реальном выводе строк гораздо больше, чем показано здесь, и все значения зависят от вашего сервера:

```sh
127.0.0.1:6379> INFO memory
# Memory
used_memory:1073664
used_memory_human:1.02M
used_memory_peak_human:1.35M
maxmemory:104857600
maxmemory_human:100.00M
maxmemory_policy:allkeys-lru
mem_fragmentation_ratio:1.08
```

Сравните `used_memory` с `maxmemory`, чтобы понять, насколько экземпляр близок к вытеснению, и прочитайте `maxmemory_policy`, чтобы убедиться, какая политика действительно загружена, а не какую вы собирались установить.

Счётчики исчезнувших ключей находятся в другой секции:

```sh
127.0.0.1:6379> INFO stats
# Stats
expired_keys:48213
evicted_keys:0
keyspace_hits:918442
keyspace_misses:20117
```

`expired_keys` считает ключи, удалённые по истечении TTL, а `evicted_keys` — ключи, удалённые ради освобождения памяти. Оба значения накапливаются с момента запуска сервера, поэтому следите за скоростью их роста, а не за абсолютной величиной. Растущий `evicted_keys` вместе с падающей долей попаданий кэша — сигнал, что экземпляр слишком мал или его политика не соответствует характеру доступа.

## Вытеснение на разных узлах Redis Cluster

В Redis Cluster `maxmemory` и `maxmemory-policy` — настройки отдельного узла, и каждый узел хранит только ключи своих хеш-слотов. Узел, в чьих слотах оказались крупные или многочисленные значения, может достичь лимита и начать вытеснение, пока все остальные узлы далеки от своего потолка. Redis не переносит ключи на узел со свободной памятью.

`CONFIG SET` тоже действует только на тот узел, к которому подключён ваш сеанс `redis-cli`. Чтобы изменить лимит во всём кластере, примените его на каждом узле. Разбираясь с вытеснением, читайте `INFO` на каждом узле, а не на том, к которому случайно подключились.

## Любой ключ может пропасть

На этой мысли строится весь остальной курс. Как только вытеснение включено, любой ключ может исчезнуть раньше своего TTL, поэтому каждое чтение должно обрабатывать промах и заново вычислять или запрашивать значение. Запись кэша, счётчик rate limiting и блокировка — всё это ключи, и на все три распространяется одно и то же правило.

Альтернатива — не надёжность, а просто другой вид отказа. При `noeviction` заполненный экземпляр перестаёт принимать записи и возвращает клиенту ошибку:

```text
OOM command not allowed when used memory > 'maxmemory'.
```

Команды чтения продолжают работать, а политика `volatile-*` без подходящих кандидатов выдаёт ту же ошибку. Так что выбирать приходится между потерей ключей, которые выбрали не вы, и потерей записей, которые вы сделали. Для кэша потеря ключей почти всегда оказывается лучшей сделкой — при условии, что приложение написано с расчётом на неё.

## Проверьте себя

Ответьте на каждый вопрос, прежде чем читать ответы ниже.

1. `TTL orders:pending` возвращает `-1`. Что это говорит о ключе?
2. Вы выполняете `SET cart:77 "[]" EX 900`, а позже `SET cart:77 "[42]"`. Каким будет TTL после этого и какой параметр это предотвращает?
3. `maxmemory-policy` равна `volatile-lru`, и ни у одного ключа в экземпляре нет TTL. Память достигает `maxmemory`. Что произойдёт со следующей записью?
4. `INFO stats` показывает, что `evicted_keys` стабильно растёт. Назовите две настройки, которые стоит проверить первыми.
5. В вашем кластере три узла. Один сообщает об активном вытеснении, остальные — об его отсутствии. Это неисправность?

Ответы: (1) ключ существует и не имеет срока жизни — это не то же самое, что `-2`, то есть отсутствующий ключ; (2) TTL пропал, потому что `SET` его сбрасывает, а `KEEPTTL` сохранил бы его; (3) запись завершится ошибкой `OOM`, потому что политика `volatile-*` без кандидатов ведёт себя как `noeviction`; (4) `maxmemory`, который может быть просто слишком мал, и `maxmemory-policy`, которая может вытеснять не те ключи; (5) нет: `maxmemory` действует на каждый узел отдельно, и неравномерное распределение ключей по хеш-слотам даёт именно такую картину.
