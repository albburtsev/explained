**Кэш** — это быстрая копия ответа, который дорого получать. Чаще всего такой ответ приходит из реляционной базы данных: это запрос, соединяющий несколько таблиц, или строка, которую тысячи запросов читают каждую минуту. Готовый ответ кладут в Redis под определённым ключом, и последующие запросы обслуживаются из этого ключа, а не новым обращением к базе. Кэширование — самая частая причина, по которой команда вообще добавляет Redis в систему.

Главное слово здесь — **копия**. Данными по-прежнему владеет база. Redis хранит дубликат, которому позволено исчезнуть, позволено слегка устареть, но никогда не позволено оказаться единственным местом, где значение существует. Из этого одного правила вытекает каждое решение в этом уроке.

## Чтение по схеме cache-aside

**Cache-aside**, или ленивая загрузка (lazy loading), — схема кэширования по умолчанию. Приложение работает с обоими хранилищами и обращается к ним в строгом порядке:

1. Прочитать ключ кэша.
2. При попадании вернуть значение из кэша и на этом закончить.
3. При промахе загрузить значение из базы данных.
4. Записать значение обратно в Redis с TTL.
5. Вернуть значение.

Пока никто не спросил, ничего не кэшируется. Кэш наполняется сам, из реального трафика.

Пройдём путь промаха в `redis-cli`. Первый запрос к товару 42 ничего не находит:

```sh
127.0.0.1:6379> GET product:42:summary
(nil)
```

Так `redis-cli` выводит пустой ответ: `(nil)` означает, что ключа нет. Это не ошибка, и приложение не должно считать её таковой. Промах — обычный первый шаг в жизни любого ключа.

Теперь приложение выполняет свой обычный запрос к базе и получает строку с товаром. Оно сериализует её и записывает обратно вместе со сроком жизни:

```sh
127.0.0.1:6379> SET product:42:summary '{"id":42,"name":"Red Kettle","price":2490}' EX 300
OK
```

`EX 300` задаёт время жизни в 300 секунд той же командой, что записывает значение. Делайте так каждый раз. Обычный `SET` без параметра срока жизни сбрасывает TTL, который у ключа уже был, поэтому значение, записанное без `EX`, остаётся в памяти, пока его что-нибудь не удалит.

Следующий запрос к тому же товару попадает в кэш:

```sh
127.0.0.1:6379> GET product:42:summary
"{\"id\":42,\"name\":\"Red Kettle\",\"price\":2490}"
```

При выводе строки `redis-cli` экранирует внутренние двойные кавычки, но сами сохранённые байты не меняются. Можно убедиться, что обратный отсчёт идёт:

```sh
127.0.0.1:6379> TTL product:42:summary
(integer) 300
```

Вот и весь путь чтения: две команды Redis и один запрос к базе, который выполняется лишь при необходимости.

## Всё, что меняет значение, — в ключ

В уроке о проектировании ключей мы ввели соглашение `object-type:id:field`. Ключ кэша строится так же, но с одним дополнительным требованием: **ключ должен содержать каждый входной параметр, от которого зависит значение**. Если два разных ответа могут оказаться под одним ключом, кэш однажды выдаст одному пользователю ответ, предназначенный другому.

Спросите себя, от каких входных данных зависит кэшируемое значение, и включите в ключ каждое из них:

```sh
127.0.0.1:6379> SET cache:v3:product:42:summary:en-us:usd '{"name":"Red Kettle","price":"$24.90"}' EX 300
OK
127.0.0.1:6379> SET cache:v3:product:42:summary:de-de:eur '{"name":"Roter Kessel","price":"22,90 €"}' EX 300
OK
```

У каждой части своя задача:

- `cache:` отделяет кэшированные копии от ключей с настоящим состоянием, так что с первого взгляда видно, что можно безопасно удалить.
- `v3` — метка версии формата хранимого значения. Меняйте её вместе с форматом сериализации, и все старые ключи разом станут недоступны.
- `product:42` указывает на сущность.
- `summary` говорит, какое именно представление сущности здесь лежит. Краткое (`summary`) и полное (`full`) представления товара 42 — два разных значения, и им нужны два разных ключа.
- `en-us` и `usd` — входные параметры, которые меняют итоговый ответ.

Обратная ошибка — ключ вроде `product:42` для значения, которое уже зависит от языка и валюты. Такой ключ ошибается не всегда, а время от времени и лишь для части пользователей, и потому эту ошибку очень трудно найти.

Никогда не добавляйте идентификатор пользователя в ключ с общими данными и никогда не храните общие данные под ключом конкретного пользователя. Сначала решите, что перед вами, а затем назовите это честно.

## Удаление ключа при изменении базы

TTL — это не инвалидация. Если цена товара 42 изменилась, а ключу в кэше осталось жить ещё 280 секунд, каждый читатель будет видеть старую цену все эти 280 секунд. TTL ограничивает, как долго длится вред, но не предотвращает его.

Сбрасывайте кэш явно. Когда запись в базу зафиксирована, удалите ключ:

```sh
127.0.0.1:6379> DEL cache:v3:product:42:summary:en-us:usd
(integer) 1
```

`DEL` возвращает число удалённых ключей, поэтому `(integer) 0` означает лишь, что ключа уже не было. Это нормальный результат, а не сбой.

Порядок важен: сначала запись в базу, потом удаление ключа. Если удалить ключ раньше, параллельный читатель может получить промах, загрузить старую строку и записать её обратно до того, как ваша запись будет зафиксирована. Тогда кэш окажется устаревшим, и никакого обновления TTL в ближайшее время не предвидится.

Обновлять кэш при записи можно двумя способами, и они не равноценны:

- **Delete-on-write** удаляет ключ и оставляет следующему читателю восстановить его из базы. Восстановленное значение всегда берётся из системы учёта (system of record), поэтому не может оказаться неверно собранным. Цена — лишний промах после каждой записи.
- **Write-through** записывает новое значение в Redis одновременно с базой. Кэш остаётся прогретым, но пишущему коду приходится уметь строить каждое кэшируемое представление строки, а два параллельных писателя могут попасть в Redis в порядке, обратном порядку в базе. Тогда кэш остаётся неверным до тех пор, пока его не спасёт TTL.

Предпочитайте delete-on-write. Этот способ короче, в нём меньше состояний гонки, и база остаётся единственным источником истины. К write-through стоит обращаться, только если промах после записи действительно обходится слишком дорого.

## TTL как бюджет устаревания

Не спрашивайте, как долго значение остаётся верным. Задайте другой вопрос: **сколько времени читатель может видеть старое значение, прежде чем это начнёт иметь значение?** Ответ и будет вашим TTL.

- Короткий TTL, измеряемый секундами, держит данные свежими, но направляет больше трафика в базу.
- Длинный TTL, измеряемый часами, защищает базу, но расширяет окно, в котором пропущенная инвалидация остаётся незамеченной.

Считайте TTL страховкой на случай инвалидации, которую вы забыли написать, а не основным механизмом свежести. Значение, для которого на каждом пути записи есть `DEL`, может позволить себе длинный TTL. Значению вовсе без инвалидации нужен TTL настолько короткий, чтобы худший случай был приемлем каждый раз.

Кроме того, ограничивайте кэш сверху, отказываясь кэшировать то, что от этого не выигрывает. Значение, которое читают раз в час, занимает память и ничего не даёт взамен.

## Как остановить лавину запросов

**Лавина запросов к кэшу** (cache stampede) случается, когда истекает срок жизни одного популярного ключа и множество параллельных запросов одновременно получают промах. Каждый из них выполняет один и тот же дорогой запрос, и база в одно мгновение получает ту самую нагрузку, от которой кэш и должен был её защищать. Кэш работал безупречно — до того момента, когда его помощь была нужнее всего.

Большинство случаев покрывают две меры.

Добавьте к TTL случайный разброс (jitter). Если заполнить тысячу ключей одновременно с `EX 300`, все они и истекут одновременно. Вместо этого выбирайте случайное значение из диапазона, например любое число секунд от 240 до 360, чтобы моменты истечения рассыпались во времени:

```sh
127.0.0.1:6379> SET cache:v3:product:42:summary:en-us:usd '{"name":"Red Kettle","price":"$24.90"}' EX 287
OK
```

Пусть восстанавливает значение только один запрос за раз. Прежде чем браться за дорогую работу, попробуйте занять короткоживущий ключ, запись которого удаётся, лишь если его никто не держит:

```sh
127.0.0.1:6379> SET rebuild:product:42:summary 1 NX EX 5
OK
127.0.0.1:6379> SET rebuild:product:42:summary 1 NX EX 5
(nil)
```

`NX` означает «записать, только если ключа нет», поэтому первый вызывающий получает `OK`, а остальные — `(nil)`. Победитель обращается к базе и записывает кэш; проигравшие немного ждут и снова читают ключ или возвращают чуть более старое значение. `EX 5` гарантирует, что захват освободится сам, если победитель упадёт. Это простейшее применение `SET NX EX`. Что такой ключ может и чего не может обещать, когда серверов несколько, разобрано в уроке о распределённых блокировках.

## Кэшированный ключ может исчезнуть раньше срока

Как показал урок об истечении срока жизни и вытеснении, ключ может пропасть раньше, чем истечёт его TTL. Когда память упирается в `maxmemory`, Redis вытесняет ключи согласно настроенной политике, и ключа, записанного несколько секунд назад, может уже не быть. Читателя об этом никто не предупреждает.

Отсюда три следствия, и все три должны быть учтены в пути чтения:

- **Никогда не храните в кэше единственную копию.** Если потеря ключа означает потерю данных, то это значение — состояние, а не кэш, и ему не место под TTL и под прицелом политики вытеснения.
- **Считайте каждое чтение возможным промахом.** Промах — не аномалия, о которой нужно громко писать в лог. Это шаг 3 схемы.
- **Будьте готовы к тому, что Redis недоступен.** Если `GET` не удался, потому что Redis лежит или соединение отвалилось по тайм-ауту, обратитесь напрямую к базе и обслужите запрос. Отказ кэша должен замедлять систему, но никогда не ломать её. Держите тайм-аут коротким, чтобы зависший кэш не превращался в зависший запрос, и не позволяйте неудачной обратной записи обернуться ошибкой, которую увидит пользователь.

К тому же вытеснение группируется во времени. Нехватка памяти приходит, когда трафик высок, поэтому множество ключей исчезает как раз тогда, когда база нагружена сильнее всего. По форме это та же лавина, и потому разброс TTL и ключ восстановления помогают и здесь.

## Осторожная инвалидация в Redis Cluster

Redis Cluster делит пространство ключей на 16384 хеш-слота и выдаёт каждому master-узлу свой диапазон. Ключи кэша проектируются так, чтобы распределяться равномерно, поэтому группа связанных ключей обычно оказывается на нескольких разных узлах. Здесь ломаются две привычки.

Многоключевой `DEL` перестаёт быть одной командой. В кластере `DEL` требует, чтобы все его ключи лежали в одном слоте; ключи из разных слотов приводят к ошибке `CROSSSLOT Keys in request don't hash to the same slot`. Чтобы сбросить двадцать ключей, нужно двадцать команд — или хеш-тег вроде `{product:42}` в каждом связанном ключе, который принудительно отправит их в один слот. Но хеш-тег заодно сосредотачивает их нагрузку на одном узле, так что применяйте его только для небольших групп связанных ключей.

Инвалидация по шаблону перестаёт быть глобальной. `SCAN` перебирает ключи того узла, к которому вы подключены, а не всего кластера, поэтому очистку на основе `SCAN` приходится запускать отдельно на каждом master-узле и повторять, если во время её работы кластер был перешардирован.

Обе проблемы — веский довод в пользу метки версии в ключе. Смена `cache:v3` на `cache:v4` отправляет в отставку целое поколение ключей, ничего не удаляя, а брошенные ключи истекут сами.

## Проверьте себя

Попробуйте ответить на каждый вопрос, прежде чем читать дальше:

1. `GET cache:v3:product:42:summary:en-us:usd` возвращает `(nil)`. Что приложение делает дальше?
2. Описание товара обновили в базе. Ключу в кэше осталось 280 секунд TTL. Что увидит читатель, если полагаться только на TTL?
3. Почему `SET cache:v3:product:42:summary:en-us:usd '...'` без `EX` создаёт проблему, хотя мгновение назад у ключа был TTL?
4. Чем `SET rebuild:product:42:summary 1 NX EX 5` лучше, чем `SET rebuild:product:42:summary 1 NX`?
5. Почему в кластере `DEL` для пятидесяти ключей кэша может завершиться ошибкой?

Ответы: (1) Загружает значение из базы, записывает его обратно через `SET ... EX` и возвращает. (2) Старое описание — ещё до 280 секунд, потому что TTL — это страховка, а не инвалидация; вместо этого удаляйте ключ после записи. (3) Успешный `SET` отбрасывает существующий TTL, так что ключ перестаёт истекать и может бесконечно хранить устаревшее значение. (4) Без `EX` вызывающий, упавший после захвата ключа, оставит его навсегда, и это значение больше никто не восстановит. (5) Ключи хешируются в разные слоты, а многоключевой `DEL` в кластере должен обращаться к одному слоту, поэтому он возвращает `CROSSSLOT Keys in request don't hash to the same slot`.
