**Redis** — это хранилище структур данных в оперативной памяти. Весь набор данных он держит в RAM, к каждому значению обращается по ключу и предлагает команды, которые работают со структурой значения, а не с непрозрачным набором байтов. Название расшифровывается как Remote Dictionary Server, и это вполне честная первая мысленная модель: словарь, который живёт в одном процессе и до которого любой сервер вашей системы может дотянуться по сети.

Простейший вариант этой модели — строковое значение под ключом:

```sh
127.0.0.1:6379> SET session:9f2c "user:412"
OK
127.0.0.1:6379> GET session:9f2c
"user:412"
```

Больше команд в этом уроке не понадобится: практика начнётся в следующем. Сейчас важнее другое — почему так много систем ставят подобное хранилище рядом со своей базой данных и где это решение даёт сбой.

## «Хранилище структур данных» в буквальном смысле

Redis часто представляют как кэш, и кэширование действительно его самая частая работа. Но набор его команд объясняет другое определение — **хранилище структур данных**: значение здесь не просто строка байтов, которую перезаписывают целиком, а структура, которую сервер понимает и умеет менять на месте.

Среди прочего это даёт:

- **Строки** для простых значений, в том числе чисел, которые можно атомарно увеличивать.
- **Списки** строк в порядке вставки, пригодные для очередей.
- **Множества** уникальных строк с проверкой принадлежности и алгеброй множеств.
- **Sorted sets**, в которых у каждого элемента есть score, поддерживающий коллекцию упорядоченной, — основа таблиц лидеров и временных окон.
- **Хеши** — записи из пар «поле — значение», позволяющие обновить одно поле, не переписывая весь объект.
- **Streams** — журнал записей, в который можно только дописывать, с отслеживанием потребителей.

Практическая разница в том, где выполняется работа. Чтобы добавить один элемент в множество в обычном кэше, нужно получить значение, декодировать его, изменить, закодировать и записать обратно. Это два сетевых round trip и гонка с потерянным обновлением, если другой сервер делает то же самое. В Redis это одна команда, которую сервер выполняет атомарно. В одном из следующих уроков мы подберём подходящий тип для каждой задачи, а пока просто перестаньте понимать «Redis» как «быстрый кэш непрозрачных блобов».

## Куда уходит время

Большую часть поведения Redis объясняют два проектных решения.

Первое — память. Реляционная база хранит строки на диске и держит в памяти кэш горячих страниц. Если чтение промахивается мимо этого кэша, ему приходится идти до слоя хранения. У Redis таких промахов не бывает: каждое значение уже лежит готовой структурой в куче процесса, поэтому прочитать его — значит перейти по указателю, а не выполнить операцию ввода-вывода.

Второе — цикл обработки команд. Redis устроен в основном однопоточно: один процесс обслуживает все клиентские соединения через мультиплексирование, а команды выполняются по одной, строго по очереди. Здесь нет ни борьбы клиентов за блокировки, ни менеджера транзакций, ни накладных расходов на координацию для каждой команды.

Вместе эти решения делают собственное время обработки на сервере исчезающе малым. Документация Redis оценивает его для обычных команд в доли микросекунды. На практике число, которое вы измеряете из приложения, определяется в основном сетевым round trip — около 200 микросекунд в типичной гигабитной сети. Отсюда и «Redis быстрее миллисекунды»: сама работа почти ничего не стоит, и остаётся лишь провод.

У последовательного выполнения есть два следствия, которые стоит запомнить с самого начала.

- **Каждая команда атомарна.** Ни один другой клиент не увидит команду применённой наполовину, и ничто не вклинится между чтением и записью внутри одной команды. Поэтому Redis хорошо подходит для счётчиков и блокировок, и на этом держатся последующие уроки о rate limiting (ограничении частоты запросов) и блокировках.
- **Одна медленная команда задерживает всех.** `GET`, `SET` и `LPUSH` выполняются за малое постоянное время, но команды, затрагивающие много элементов, — `SORT`, `SUNION` или `KEYS` на большом пространстве ключей — занимают единственный поток на всё время своей работы. Все остальные клиенты ждут. Считайте медленную команду в Redis медленной для всего экземпляра.

## Redis и дисковая база данных

Redis и реляционная база — не конкуренты, различающиеся цифрами производительности. Они дают разные обещания.

| Вопрос | Реляционная база данных | Redis |
| --- | --- | --- |
| Где живут данные? | На диске, с кэшем в памяти | В памяти, с необязательной копией на диске |
| Насколько большими они могут быть? | Больше RAM | Не больше RAM |
| Как запрашивать данные? | SQL, join, произвольные запросы, планировщик | По ключу плюс команды для типа этого значения |
| Что происходит при сбое? | Подтверждённые транзакции сохраняются | Недавние записи могут потеряться — в зависимости от настройки |
| Как ведут себя одновременные писатели? | Транзакции и уровни изоляции | По одной команде за раз на экземпляр |

Читайте эту таблицу как разделение труда, а не как рейтинг. Обычно система устроена так: надёжная база данных хранит истину, а Redis — её быструю и одноразовую проекцию: строки, которые читают чаще всего, счётчики, которые чаще всего обновляют, и состояние координации, важное лишь в ближайшие секунды.

## Задачи, которые поручают Redis

Четыре шаблона покрывают бо́льшую часть использования Redis в продакшене, и курс разбирает каждый из них.

- **Кэширование.** Результат дорогого запроса или вычисления сохраняется под ключом со сроком жизни, и последующие чтения обслуживаются из памяти. Истина остаётся в базе данных, а Redis принимает на себя повторные чтения.
- **Счётчики и rate limiting.** Атомарные инкременты делают Redis естественным местом, чтобы считать запросы каждого пользователя в минуту, отслеживать расход квоты или вести таблицу лидеров.
- **Координация.** Нескольким серверам приложения нужно договориться, что задачу выполняет только один из них. Ключ, который может создать лишь один владелец, со сроком жизни, чтобы упавший владелец не заблокировал всех навсегда, даёт грубую распределённую блокировку.
- **Эфемерный обмен сообщениями.** Вы публикуете событие, и его получают те серверы, которые слушают прямо сейчас. Так строят живые дашборды, отслеживание присутствия или сигналы об инвалидации кэша.

Всех их объединяет одно: данные небольшие, горячие и либо восстановимы, либо быстро теряют ценность. Именно здесь Redis на своём месте.

## Долговечность как осознанный выбор

Redis вовсе не обязан терять данные при выключении. У него есть настоящие механизмы персистентности, и стоит знать, что на самом деле обещает каждый из них.

- **RDB** с заданными интервалами делает снимки состояния на определённый момент. Восстановление из снимка проходит быстро, и сами снимки — хорошие резервные копии. Но при некорректной остановке теряется всё, что записано после последнего снимка, — обычно последние несколько минут.
- **AOF** дописывает каждую команду записи в журнал и воспроизводит его при запуске. Его долговечность зависит от `appendfsync`: `always` вызывает fsync на каждую запись и работает медленно, `everysec` — значение по умолчанию, при котором можно потерять около секунды записей, а `no` оставляет сброс на диск операционной системе.
- **Оба механизма вместе** — рекомендуемая настройка, если нужна сохранность данных, сравнимая с традиционной базой данных.

Репликация добавляет вторую оговорку. По умолчанию Redis реплицирует асинхронно, поэтому основной узел может подтвердить запись клиенту и отказать раньше, чем она дойдёт до какой-либо реплики. Документация прямо говорит, что подтверждённые записи всё равно могут потеряться при failover.

Поэтому честная формулировка звучит не как «Redis теряет данные». Сделать Redis источником истины — сознательное решение с измеримым окном потерь, и это окно нужно выбрать намеренно. Большинство команд предпочитает так не делать и хранит истину в базе данных, созданной для того, чтобы её защищать.

## Когда Redis — не тот инструмент

В этих случаях выбирайте что-то другое.

- **Данные, потерю которых нельзя допустить.** Платежи, заказы, бухгалтерские книги, журналы аудита. Даже с AOF и репликацией вы лишь выбираете небольшое окно потерь, а не устраняете его.
- **Набор данных больше RAM.** У Redis нет дискового хранилища для холодных данных: весь набор обязан помещаться в память. Когда достигнут лимит `maxmemory`, Redis либо вытесняет ключи по выбранной вами политике, либо — с политикой по умолчанию `noeviction` — начинает отклонять записи с ошибкой, продолжая обслуживать чтения. Истечению срока жизни и вытеснению подробно посвящён один из следующих уроков.
- **Сложные запросы и join.** Здесь нет SQL, нет планировщика запросов и нет способа соединить два ключа. В Redis Open Source есть движок поиска и запросов, который умеет индексировать хеши и JSON-документы, но это вторичный индекс поверх пространства ключей, а не универсальный реляционный движок.
- **Отчёты и аналитика.** Обход всего пространства ключей ради агрегата идёт против однопоточного устройства и блокирует живой трафик. Отправляйте такую работу в базу данных, аналитическое хранилище или на реплику.

Полезная проверка перед тем, как добавить Redis: спросите себя, что сломается, если экземпляр перезапустится пустым. Если ответ — «несколько следующих запросов будут медленнее», Redis подходит. Если ответ — «мы потеряли записи», найдите для этих данных другой дом.

## Как Redis масштабируется горизонтально

Всё сказанное выше исходит из одного экземпляра Redis, как и бо́льшая часть курса. Горизонтально Redis масштабируется с помощью **Redis Cluster**, который шардирует пространство ключей по нескольким узлам. Каждый ключ отображается на один из 16384 хеш-слотов, а каждый узел владеет диапазоном слотов.

Шардирование меняет одно правило, на которое опираются несколько следующих шаблонов: команда, затрагивающая несколько ключей, работает, только если все эти ключи лежат в одном хеш-слоте. Этого можно добиться, поместив в имена ключей общий *хеш-тег* в фигурных скобках: `user:{123}:profile` и `user:{123}:account` попадают в один слот, потому что хешируется только текст внутри скобок.

Каждый урок исходит из одного экземпляра и добавляет короткое примечание там, где Cluster меняет ответ.

## Проверьте себя

Ответьте на вопросы, прежде чем читать дальше.

1. Почему чтение в Redis не страдает от промахов кэша, как чтение в реляционной базе?
2. У вашего экземпляра внезапно выросла задержка для всех клиентов, а одно приложение по таймеру выполняет `KEYS` на большом пространстве ключей. Связано ли одно с другим?
3. Коллега предлагает хранить единственную копию оплаченных счетов в Redis с включённым AOF. Назовите два риска.
4. Закэшированный набор данных перерос память, выделенную Redis. Что произойдёт при политике вытеснения по умолчанию?
5. Что из этого подходит для Redis: хранилище сессий, ежемесячный отчёт о выручке, счётчик запросов для каждого IP, адресная книга клиентов, которая должна пережить перезапуск?

Ожидаемые ответы: 1. Весь набор данных уже в памяти, поэтому чтение — это переход по указателю, а не дисковый ввод-вывод. 2. Да: команды выполняются последовательно в одном потоке, поэтому медленный обход `KEYS` останавливает всех остальных клиентов. 3. С `appendfsync everysec` при сбое можно потерять около секунды записей, а из-за асинхронной репликации подтверждённая запись может исчезнуть при failover. 4. `noeviction` сохраняет данные, но отклоняет дальнейшие записи с ошибкой; чтения продолжают работать. 5. Хранилище сессий и счётчик по IP подходят; отчёту о выручке нужны запросы и агрегация, а адресной книге — долговечность.
