**Pub/Sub** — схема обмена сообщениями, при которой издатель отправляет сообщение не конкретному получателю, а в именованный **канал**. Redis доставляет это сообщение каждому клиенту, который в данный момент подписан на канал. Издатель не знает, сколько существует подписчиков, а подписчики не знают, кто опубликовал сообщение. В этой развязке и состоит весь смысл: слушателей можно добавлять и убирать, не меняя код, который отправляет сообщения.

Pub/Sub никак не связан с пространством ключей. Каналы — это не ключи: они не хранятся, и на них не распространяются правила истечения срока жизни и вытеснения, о которых шла речь ранее в этом курсе. Канал существует лишь до тех пор, пока на него подписан хотя бы один клиент.

## Первое сообщение между двумя терминалами

Откройте два окна терминала. В первом запустите `redis-cli` и подпишитесь на канал:

```sh
redis-cli
```

```sh
127.0.0.1:6379> SUBSCRIBE news
Reading messages... (press Ctrl-C to quit)
1) "subscribe"
2) "news"
3) (integer) 1
```

Ответ из трёх элементов — это подтверждение подписки от сервера: вид сообщения, канал и число каналов и шаблонов, на которые теперь подписано это соединение. Терминал блокируется и ждёт.

Во втором окне запустите ещё один `redis-cli` и опубликуйте сообщение:

```sh
127.0.0.1:6379> PUBLISH news "hello"
(integer) 1
```

`PUBLISH` возвращает целое число — количество клиентов, которым было отправлено сообщение. Здесь это `1`, ваш подписчик. Взгляните на первое окно: там появилось новое сообщение.

```sh
1) "message"
2) "news"
3) "hello"
```

Теперь нажмите `Ctrl-C` в первом окне, чтобы выйти из режима подписки, и опубликуйте сообщение снова:

```sh
127.0.0.1:6379> PUBLISH news "anyone there?"
(integer) 0
```

Ответ — `0`. Сообщение никому не доставлено и исчезло. Ничего не сохранилось, и никакой ошибки не произошло. Запомните этот результат: в нём суть всего урока.

## Подписка на множество каналов одним шаблоном

`PSUBSCRIBE` подписывает не на точные имена каналов, а на шаблоны в стиле glob. Подписчику, которому нужны все новостные рубрики, не приходится перечислять их:

```sh
127.0.0.1:6379> PSUBSCRIBE "news.*"
Reading messages... (press Ctrl-C to quit)
1) "psubscribe"
2) "news.*"
3) (integer) 1
```

Из другого окна опубликуйте сообщение в канал, подходящий под шаблон:

```sh
127.0.0.1:6379> PUBLISH news.music.jazz "new set list"
(integer) 1
```

Подписчик на шаблон получает сообщение из четырёх элементов вида `pmessage`, в котором добавлен сработавший шаблон:

```sh
1) "pmessage"
2) "news.*"
3) "news.music.jazz"
4) "new set list"
```

Обратите внимание, что это отдельный вид сообщения. Клиент, подписанный и на `news`, и на `new*`, получит две копии сообщения, опубликованного в `news`: одно `message` и одно `pmessage`. Redis не устраняет дубликаты.

`UNSUBSCRIBE` снимает подписки на каналы, а `PUNSUBSCRIBE` — подписки на шаблоны. Без аргументов каждая из команд снимает их все. Сервер подтверждает это ответом той же формы из трёх элементов, где последний элемент — число оставшихся подписок:

```sh
1) "unsubscribe"
2) "news"
3) (integer) 0
```

Когда это число доходит до нуля, соединение выходит из состояния Pub/Sub. В `redis-cli` нельзя набрать `UNSUBSCRIBE`, пока вы подписаны, потому что строка ввода занята чтением сообщений; вместо этого нажмите `Ctrl-C`. Настоящая клиентская библиотека отправляет эту команду по соединению.

## Кто слушает

`PUBSUB` сообщает текущее состояние подписок, и выполнить эту команду можно из любого обычного соединения:

```sh
127.0.0.1:6379> PUBSUB CHANNELS
1) "news"
2) "cache:invalidate"
```

`PUBSUB CHANNELS` перечисляет активные каналы, то есть каналы, у которых есть хотя бы один подписчик. Клиенты, подписанные только через шаблоны, не учитываются. Чтобы сузить список, передайте необязательный glob-шаблон:

```sh
127.0.0.1:6379> PUBSUB CHANNELS "cache:*"
1) "cache:invalidate"
```

`PUBSUB NUMSUB` подсчитывает подписчиков каждого канала и отвечает чередующимися именами каналов и числами:

```sh
127.0.0.1:6379> PUBSUB NUMSUB news sports
1) "news"
2) (integer) 1
3) "sports"
4) (integer) 0
```

Подписчики на шаблоны здесь тоже не учитываются; число различных шаблонов вместо этого возвращает `PUBSUB NUMPAT`. Эти команды — ваши инструменты отладки. Когда кажется, что сообщение потерялось, проверьте, был ли вообще кто-нибудь подписан.

## Ограничения подписанного соединения

В протоколе RESP2 соединение в состоянии подписки принимает лишь небольшой набор команд: `SUBSCRIBE`, `UNSUBSCRIBE`, `PSUBSCRIBE`, `PUNSUBSCRIBE`, `SSUBSCRIBE`, `SUNSUBSCRIBE`, `PING`, `RESET` и `QUIT`. Отправьте по такому соединению `GET` или `SET`, и сервер вместо выполнения ответит ошибкой.

На практике это значит, что подписчику нужно собственное выделенное соединение. Приложение, которое и слушает события, и читает значения из кэша, должно держать два соединения, поэтому клиентские библиотеки открывают для Pub/Sub отдельное. В RESP3, который согласуется командой `HELLO 3`, это ограничение снято, и клиент может выполнять любые команды, будучи подписанным, потому что push-сообщения передаются как отдельный тип ответа.

## Рассылка живых обновлений

Pub/Sub подходит для задач, где множеству процессов нужно узнать о чём-то в один и тот же момент.

Представьте приложение, работающее на нескольких серверах, каждый из которых держит открытые WebSocket-соединения с браузерами. Пользователь оставляет комментарий на одном из серверов. Этот сервер публикует его один раз:

```sh
127.0.0.1:6379> PUBLISH room:42 "{\"user\":\"ada\",\"text\":\"shipped\"}"
(integer) 3
```

Все три сервера подписаны на `room:42`, поэтому каждый получает сообщение и пересылает его своим браузерам. Публикующему серверу вовсе не нужен список соседей.

Та же схема решает задачу инвалидации кэша. В уроке о кэшировании вы удаляли ключ кэша после записи. Если каждый сервер вдобавок держит небольшой локальный кэш внутри процесса, удалить ключ в Redis недостаточно: копии внутри других процессов остаются устаревшими. Вместо этого опубликуйте инвалидацию:

```sh
127.0.0.1:6379> DEL user:1001
(integer) 1
127.0.0.1:6379> PUBLISH cache:invalidate "user:1001"
(integer) 3
```

Каждый сосед, подписанный на `cache:invalidate`, выбрасывает свою локальную копию. Это работает, потому что пропущенная инвалидация не смертельна: в худшем случае один сервер будет отдавать устаревшие данные, пока не истечёт срок жизни его собственной записи.

## Доставка по принципу «отправил и забыл»

Это самое важное, что стоит вынести из урока. У Pub/Sub в Redis семантика доставки **at-most-once**: сообщение доставляется не более одного раза, если вообще доставляется. Разберёмся точно, что это значит:

- **Никакого хранения.** Сообщение никогда не записывается ни в пространство ключей, ни в файл RDB, ни в AOF. Оно существует лишь пока Redis отправляет его в сокеты.
- **Никакой доставки отсутствующим подписчикам.** Подписчик, который в момент `PUBLISH` отключён или перезапускается, не получает ничего. Нет очереди, которая придержала бы сообщение до его возвращения.
- **Никаких подтверждений.** Издатель узнаёт, скольким клиентам сообщение было *отправлено*, но не скольким оно обработано. Подписчик, упавший посреди обработки, неотличим от того, кто справился успешно.
- **Никакого повторного воспроизведения.** Запросить пропущенные сообщения невозможно. Отправленное сообщение исчезает.
- **Никаких повторных попыток.** Redis никогда не отправляет сообщение второй раз.

Есть и ещё один сценарий отказа, который застаёт людей врасплох. Redis буферизует вывод для каждого клиента, и у подписчика, читающего медленнее, чем приходят сообщения, буфер растёт. Для клиентов Pub/Sub Redis ограничивает этот буфер — по умолчанию жёстким лимитом в 32 мегабайта и мягким лимитом в 8 мегабайт, если он держится 60 секунд, — и при достижении лимита **закрывает соединение**. Поэтому медленный потребитель не просто отстаёт: его отключают, и все сообщения, опубликованные, пока он переподключается, теряются.

Отсюда прямо следует правило проектирования: используйте Pub/Sub, только когда потеря сообщения допустима. Индикаторы присутствия в сети, бегущие строки на дашбордах, рассылка сообщений чата и инвалидация кэша этому условию отвечают. Подтверждения заказов, платежи и распределение задач — нет.

## Осторожно: Redis Cluster

Классический Pub/Sub не обращает внимания на слоты. Канал — не ключ, он ни во что не хешируется, поэтому Redis Cluster пересылает каждое опубликованное сообщение по шине кластера на **каждый узел**, есть там подписчик или нет. Благодаря этому клиенты могут публиковать на любом узле и подписываться на любом узле, и сообщение всё равно дойдёт. Но за удобство приходится платить пропускной способностью, которая растёт с числом узлов, поэтому глобальный Pub/Sub нельзя масштабировать добавлением узлов.

Из того же устройства вытекают две детали поменьше. `PUBLISH` возвращает лишь число клиентов, подключённых к *тому же узлу*, что и издатель, так что это не сумма по всему кластеру. `PUBSUB CHANNELS` и `PUBSUB NUMSUB` точно так же сообщают только о том узле, который вы спросили, а не обо всём кластере.

Чтобы решить проблему пропускной способности, в Redis 7.0 появился **шардированный Pub/Sub** (sharded Pub/Sub). `SSUBSCRIBE`, `SUNSUBSCRIBE` и `SPUBLISH` обращаются с именем шард-канала как с ключом: оно хешируется в слот, и сообщение распространяется только внутри шарда, которому принадлежит этот слот.

```sh
127.0.0.1:6379> SPUBLISH orders "hello"
(integer) 1
```

Подписчики должны подключаться к узлу, владеющему слотом, или к одной из его реплик. Взамен трафик сообщений остаётся внутри одного шарда, так что добавление шардов наращивает ёмкость Pub/Sub, а не умножает трафик. На одиночном экземпляре оба семейства команд ведут себя одинаково; разница проявляется только в кластере.

## Streams, когда нужны гарантии

Если потеря сообщения недопустима, выход не в более хитром использовании Pub/Sub, а в другом типе данных.

**Redis Stream** — это журнал, в который можно только дописывать, хранящийся под обычным ключом. Записи сохраняются, несут упорядоченные идентификаторы и остаются доступны для последующих читателей. `XADD` добавляет запись, `XREAD` читает записи после заданного идентификатора, а `XREADGROUP` читает от имени **группы потребителей** (consumer group), которая распределяет записи между обработчиками и отслеживает, какие из них каждый потребитель ещё не подтвердил. Это сочетание даёт то, чего не может Pub/Sub: подписчик, который был офлайн, может вернуться и прочитать пропущенное, а запись остаётся в ожидании, пока её не подтвердят.

Эти команды — лишь указатели, а не материал этого урока. Сейчас от вас требуется одно: знать, какой вопрос задать. *Можно ли потерять это сообщение?* Если да, Pub/Sub — самый простой подходящий инструмент. Если нет, начните со Streams, а если нужны надёжная маршрутизация, обработка недоставленных сообщений (dead-letter) или гарантии доставки между системами, честный ответ — специализированный брокер сообщений, а не хранилище данных, которое вы пытаетесь им сделать.

## Проверьте себя

Ответьте, прежде чем читать дальше:

1. Вы выполняете `PUBLISH alerts "disk full"` и получаете `(integer) 0`. Встало ли сообщение в очередь для следующего подписчика?
2. Подписчик перезапускается, и на переподключение у него уходит четыре секунды. Какие сообщения за этот промежуток он получит?
3. Клиент выполняет `SUBSCRIBE news`, а затем `GET user:1` по тому же соединению RESP2. Что произойдёт?
4. Клиент подписан на `news` и на шаблон `ne*`. Сколько сообщений он получит от одного `PUBLISH news "hi"`?
5. В кластере из шести узлов один клиент публикует сообщение через `PUBLISH`. Как далеко распространится это сообщение?

Ответы: (1) Нет: сообщение отброшено, а `0` означает лишь, что в тот момент ни один клиент не был подписан. (2) Никакие: нет ни буфера, ни повторного воспроизведения, так что этот промежуток — невосполнимая дыра. (3) Сервер отклонит `GET` с ошибкой, потому что подписанное соединение RESP2 принимает только команды подписки, `PING`, `RESET` и `QUIT`. (4) Два — одно `message` и одно `pmessage`, потому что Redis не устраняет дубликаты между видами подписок. (5) До всех шести узлов по шине кластера, поскольку классические каналы не привязаны к слотам; `SPUBLISH` ограничил бы его одним шардом.

Теперь перед вами весь курс целиком. Redis — быстрое хранилище в памяти: его типы данных вы выбираете осознанно, ключи называете так, чтобы они оставались понятными, а правила истечения срока жизни и вытеснения решают, что уцелеет. На этой основе вы построили четыре схемы, которые встраивают Redis в распределённую систему: кэш перед медленной базой данных, счётчик, ограничивающий частоту запросов, блокировку, которая истекает, чтобы павший владелец не мог заблокировать систему навечно, и, наконец, канал, вещающий всем, кто слушает. Через все четыре проходит один и тот же компромисс: Redis даёт скорость, держа данные в памяти, поэтому каждая построенная на нём схема должна оставаться корректной, когда эти данные исчезают. Проектируйте с учётом этого, и Redis станет надёжной частью вашей архитектуры, а не скрытой единой точкой отказа.
