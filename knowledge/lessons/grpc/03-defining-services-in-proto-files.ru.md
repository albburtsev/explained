Файл `.proto` — общий контракт между клиентом и сервером gRPC. В нём перечислены операции, которые предлагает сервер, и описаны сообщения, передаваемые в каждую сторону. Разработчику клиента стоит прочитать этот файл до того, как писать вызов: из него видно, какой метод вызывать и какие поля заполнять.

Вот контракт, на котором построены следующие уроки. Сохраните его как `inventory/v1/inventory.proto`, если позже захотите сгенерировать по нему клиент:

```proto
syntax = "proto3";

package inventory.v1;

option go_package = "example.com/inventory/gen/inventory/v1;inventoryv1";

service InventoryService {
  rpc GetItem(GetItemRequest) returns (Item);
  rpc WatchItems(WatchItemsRequest) returns (stream Item);
}

message GetItemRequest {
  string sku = 1;
}

message WatchItemsRequest {
  string category = 1;
}

message Item {
  string sku = 1;
  string name = 2;
  int32 quantity = 3;
}
```

## Читаем сервис

Строка `syntax = "proto3";` выбирает язык proto3. Директива `package` помещает эти определения в пространство имён protobuf `inventory.v1`, чтобы их имена не столкнулись с определениями из другого API. Опция `go_package` задаёт путь импорта сгенерированного кода на Go, а после точки с запятой — имя пакета Go, `inventoryv1`. На пространство имён protobuf она не влияет.

`service` объединяет удалённые методы. Каждое `rpc` объявляет один тип запроса и один тип ответа:

- `GetItem` принимает один `GetItemRequest` и возвращает один `Item`. Это унарный вызов.
- `WatchItems` принимает один `WatchItemsRequest` и возвращает поток сообщений `Item`. Ключевое слово `stream` обозначает вызов с server streaming: в ответ на один запрос клиент может получить несколько товаров.

Определение сервиса описывает форму сообщений и направление вызова. Оно не говорит, что произойдёт, если SKU не существует, присылает ли `WatchItems` снимок текущего состояния или обновления в реальном времени и когда поток заканчивается. Такое поведение должно быть описано в контракте API за пределами этого синтаксиса.

## Читаем сообщения

`message` — это структурированный запрос или ответ. В `GetItemRequest` поле `sku` имеет строковый тип. В `Item` поле `quantity` — знаковое 32-битное целое. Число после `=` — идентификатор поля в передаваемых данных, а не его порядковый номер при отображении. Номера полей должны быть уникальны *в пределах одного сообщения*; поля `sku = 1` в двух разных сообщениях друг другу не мешают.

Разбирая незнакомый контракт, идите от сигнатуры метода к определениям его сообщений. Для `GetItem` вы отправляете запрос с SKU и получаете товар с SKU, названием и количеством. Для `WatchItems` вы отправляете категорию и читаете последовательность товаров. У скалярных типов proto3, таких как `string` или `int32`, есть неявное нулевое значение, которое подставляется, когда поле отсутствует; поэтому сам по себе `GetItemRequest` не гарантирует, что вызывающая сторона передала непустой SKU. Такая проверка — часть поведения API.

## Не меняйте номера полей

Как только сообщением начали пользоваться клиенты и серверы, номер уже существующего поля менять нельзя. Например, если заменить у `Item.name` номер `2` на `4`, старые и новые программы будут читать из передаваемых данных разные поля. Добавить новое поле с незанятым номером, как правило, безопасно с точки зрения двоичной совместимости protobuf: старые программы просто пропустят незнакомое поле. Однако API всё равно должен определить, что означает отсутствие значения.

Если вы удаляете поле, зарезервируйте его прежний номер, чтобы позже его нельзя было отдать полю с другим смыслом. Можно зарезервировать и имя — это защитит текстовое и JSON-представления. Например, после удаления из `Item` старого поля `legacy_code = 4` определение могло бы выглядеть так:

```proto
message Item {
  reserved 4;
  reserved "legacy_code";

  string sku = 1;
  string name = 2;
  int32 quantity = 3;
}
```

Попробуйте разобрать оба метода из первого контракта: назовите тип запроса, тип ответа и определите, приходит ли в ответ одно сообщение или поток. Затем найдите номер поля `Item`, который будущий клиент должен и дальше использовать для `quantity`. Ответы: `GetItemRequest` → один `Item`, `WatchItemsRequest` → поток `Item`, а для `quantity` — `3`.
