Файл `.proto` — общий контракт между клиентом и сервером gRPC. В нём перечислены операции, которые предлагает сервер, и описаны сообщения, передаваемые в каждую сторону. Обе стороны генерируют по нему код, поэтому прочитайте его, прежде чем писать вызов или сервис.

В этом уроке вы начнёте проект, на котором построен весь остальной курс, — небольшой сервис склада. Вот его контракт:

```proto
syntax = "proto3";

package inventory.v1;

service InventoryService {
  rpc GetItem(GetItemRequest) returns (Item);
  rpc WatchItems(WatchItemsRequest) returns (stream Item);
}

message GetItemRequest {
  string sku = 1;
}

message WatchItemsRequest {
  string category = 1;
}

message Item {
  string sku = 1;
  string name = 2;
  string category = 3;
  int32 quantity = 4;
}
```

## Читаем сервис

Строка `syntax = "proto3";` выбирает язык proto3. Директива `package` помещает эти определения в пространство имён protobuf `inventory.v1`, чтобы их имена не столкнулись с определениями из другого API. Суффикс `v1` — распространённый способ указать версию контракта.

`service` объединяет удалённые методы. Каждое `rpc` объявляет один тип запроса и один тип ответа:

- `GetItem` принимает один `GetItemRequest` и возвращает один `Item`. Это унарный вызов.
- `WatchItems` принимает один `WatchItemsRequest` и возвращает поток сообщений `Item`. Ключевое слово `stream` обозначает вызов с server streaming: в ответ на один запрос клиент может получить много товаров.

Определение сервиса описывает форму сообщений и направление вызова. Оно не говорит, что произойдёт, если SKU не существует, и когда закончится поток `WatchItems`. Такое поведение команда, которая отвечает за сервис, должна описать отдельно — например, в комментариях или документации.

## Читаем сообщения

`message` — это структурированный запрос или ответ. В `GetItemRequest` поле `sku` имеет строковый тип. В `Item` поле `quantity` — знаковое 32-битное целое. Число после `=` — это `номер поля` (field number): он обозначает поле в двоичных данных и не имеет отношения к порядку отображения. Номера полей должны быть уникальны *в пределах одного сообщения*; поля `sku = 1` в двух разных сообщениях друг другу не мешают.

Разбирая незнакомый контракт, идите от сигнатуры метода к определениям его сообщений. Для `GetItem` вы отправляете запрос с SKU и получаете товар с SKU, названием, категорией и количеством. Для `WatchItems` вы отправляете категорию и читаете последовательность товаров.

В proto3 у отсутствующего скалярного поля есть нулевое значение — пустая строка или `0`. Поэтому сам по себе `GetItemRequest` не гарантирует, что вызывающая сторона передала непустой SKU. Сервер должен проверять это сам; в одном из следующих уроков вы добавите такую проверку.

## Не меняйте номера полей

Как только сообщением начали пользоваться клиенты и серверы, номер уже существующего поля менять нельзя. Например, если заменить у `Item.name` номер `2` на `5`, старые и новые программы будут читать из одних и тех же данных разные поля. Добавить новое поле с незанятым номером, как правило, безопасно: старые программы просто пропустят незнакомое поле. Однако API всё равно должен определить, что означает отсутствие значения.

Если вы удаляете поле, зарезервируйте его прежний номер, чтобы позже никто не отдал его полю с другим смыслом. Можно зарезервировать и имя — это защитит JSON-представление сообщения. Например, после удаления из `Item` старого поля `legacy_code = 5` определение могло бы выглядеть так:

```proto
message Item {
  reserved 5;
  reserved "legacy_code";

  string sku = 1;
  string name = 2;
  string category = 3;
  int32 quantity = 4;
}
```

## Практика

1. Создайте проект курса на macOS. Понадобится Node.js v20+. Выполните в терминале:

   ```sh
   mkdir inventory
   cd inventory
   npm init -y
   mkdir -p proto/inventory/v1
   ```

   Сохраните контракт из начала урока как `proto/inventory/v1/inventory.proto`. Не меняйте его: следующие уроки генерируют код именно по этому файлу.

2. Разберите оба метода контракта: назовите тип запроса, тип ответа и определите, приходит ли в ответ одно сообщение или поток. Ответы: `GetItemRequest` → один `Item`, `WatchItemsRequest` → поток `Item`.

3. Представьте будущую версию `Item` без поля `category`. Напишите строки, которые защитят его прежние номер и имя. Ответ: `reserved 3;` и `reserved "category";`. Номер `4` должен остаться за `quantity`.
