С `gRPC` клиент вызывает метод, который реализован в другом процессе. Это `удалённый вызов процедуры` (remote procedure call, RPC): в клиентском коде он выглядит как обычный вызов метода, но прежде чем сервер его выполнит, запрос проходит через сеть.

Допустим, клиенту нужно название книги. Общий контракт `.proto` мог бы объявить следующее:

```proto
syntax = "proto3";
package catalog.v1;

service Catalog {
  rpc GetBook (GetBookRequest) returns (GetBookResponse);
}

message GetBookRequest {
  string id = 1;
}

message GetBookResponse {
  string title = 1;
}
```

Здесь `service` объединяет доступные для вызова операции, `GetBook` — это `метод` (method), а каждое `message` задаёт форму данных, которые передаются в одну сторону. Клиент отправляет `GetBookRequest` с идентификатором; в случае успеха сервер возвращает `GetBookResponse` с названием. Синтаксис контракта подробно разобран в одном из следующих уроков.

## Путь одного вызова

1. Клиентский код генерируется из того же контракта, который реализует сервер. Сгенерированный клиент, его ещё называют `stub`, предоставляет метод `GetBook` с объявленными типами запроса и ответа.
2. Приложение вызывает этот метод и передаёт ему сообщение запроса. Среда выполнения gRPC сериализует сообщение, отправляет его на сервер по HTTP/2 и указывает, какой сервис и какой метод нужно вызвать.
3. Сервер декодирует запрос, выполняет свою реализацию `GetBook` и, если вызов прошёл успешно, отправляет ответ.
4. Клиент получает либо ответ со `статусом` (status) OK, либо статус, отличный от OK, который объясняет, почему вызов не удался.

По умолчанию gRPC использует `Protocol Buffers`, чтобы описывать контракт и кодировать сообщения. Клиент и сервер могут быть написаны на разных языках — достаточно, чтобы они следовали одному контракту. В примере показан `унарный` (unary) вызов: на один запрос приходит один ответ. Кроме того, gRPC поддерживает вызовы, в которых сообщения передаются потоком в одну или в обе стороны.

## Помните о границе сети

Сгенерированный метод делает вызов удобным, но не делает его локальным. Вызов может занять время, потерять соединение или завершиться на сервере уже после того, как клиент перестал ждать. Поэтому клиентский код должен обрабатывать статусы и задавать `deadline` — предел того, сколько он готов ждать. В следующих уроках показано, как сделать и то и другое на Go.

Чтобы проверить себя, найдите в контракте выше сервис, метод, тип запроса и тип ответа. Затем спросите себя: что клиент должен знать, прежде чем обратиться к серверу? Ему нужны контракт сервиса, сгенерированный клиентский код и способ связаться с сервером; код реализации сервера ему не нужен.
