`REST` — архитектурный стиль, в центре которого ресурсы и единообразный интерфейс. `gRPC` — фреймворк для вызова именованных методов сервиса. Задачи, которые они решают при построении API, во многом пересекаются, но интерфейсы они описывают разного рода.

Представьте API, который возвращает заказ. Типичный HTTP API, построенный вокруг ресурсов, мог бы предоставить `GET /orders/42`: клиент формирует HTTP-запрос, а затем разбирает статус ответа и полученное представление. gRPC API мог бы определить метод `OrderService.GetOrder` с сообщением `GetOrderRequest`, в котором передаётся идентификатор заказа; клиент вызывает этот метод через сгенерированный клиент и получает типизированное сообщение `Order`. Это два условных варианта устройства API, а не два формата передачи для одного и того же endpoint.

| Вопрос | HTTP API, построенный вокруг ресурсов | gRPC API |
| --- | --- | --- |
| Что определяет операцию? | HTTP-метод и URI ресурса, например `GET /orders/42`. | Метод сервиса, например `OrderService.GetOrder`. |
| Где находится контракт? | В семантике HTTP и документации API; иногда к ним прилагается машиночитаемое описание, например OpenAPI. | Обычно в файле `.proto`, где определены сервисы, методы и типы сообщений. |
| Как клиент передаёт данные? | HTTP-запросами в представлении, которое выбрал конкретный API, часто в JSON. | Обычно сообщениями Protocol Buffers, которые gRPC передаёт по HTTP/2. |
| Как сообщается результат? | Через HTTP-статус ответа, заголовки и представление. | Через сообщения ответа, статус gRPC и необязательные metadata. |
| Как быть со streaming? | API должен отдельно описать подходящий механизм. | Методы могут объявлять потоки сообщений от сервера, от клиента или в обе стороны. |

Колонка REST описывает распространённый стиль HTTP API, а не все возможные реализации REST. REST не требует ни JSON, ни HTTP/1.1, а HTTP API тоже умеют передавать данные потоком. Колонка gRPC описывает привычную связку Protocol Buffers и HTTP/2; при этом gRPC может работать и с другими форматами сообщений.

## Что меняется для разработчика клиента?

С HTTP API, построенным вокруг ресурсов, вы по документации выбираете URL, метод, представление и способ обработки ответа. С gRPC нужно получить контракт `.proto` сервиса и сгенерировать совместимый клиент или взять готовый. Основным интерфейсом, с которым вы работаете, становятся сгенерированный метод и типы сообщений, а кодирование и транспорт берёт на себя библиотека gRPC.

Проверяйте **фактический контракт API** сервера, а не только то, работает ли он поверх HTTP. Метод gRPC, как правило, нельзя вызвать, отправив JSON-запрос на похожий по виду URL. И наоборот: HTTP endpoint, который возвращает Protocol Buffers, ещё не становится от этого сервисом gRPC. Планируя клиент, определите нужный метод, сообщения его запроса и ответа, схему вызова и то, как сообщается об ошибках.

Для практики возьмите пример выше и перечислите, что вам понадобится знать, прежде чем писать каждый из клиентов: для HTTP API — путь и представление ответа, для gRPC — определение сервиса и поля сообщений. В следующем уроке показано, как читать такое определение в `.proto`.
