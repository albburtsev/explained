В прошлом уроке `sw.js` сохранил app shell в кеш. Теперь обработчик `fetch` должен решить, чем ответить на каждый запрос: копией из кеша, ответом из сети или тем и другим сразу. `Стратегия кеширования` (caching strategy) — это неизменное правило, по которому принимается такое решение. Распространённых стратегий всего несколько, и каждая умещается в короткую функцию.

Любая стратегия ищет равновесие между тремя целями: скоростью, свежестью данных и работой без сети. Ни одна не выигрывает сразу по всем трём, поэтому хороший сервис-воркер применяет разные стратегии к разным видам файлов.

## Исходная точка

После урока 9 в начале `sw.js` объявлены имя кеша и список файлов app shell — примерно так:

```js
const CACHE_NAME = 'daily-quote-v2';
const APP_SHELL = [
  '/',
  '/index.html',
  '/about.html',
  '/style.css',
  '/app.js',
  '/manifest.webmanifest',
  '/icons/icon-192.png',
  '/icons/icon-512.png',
];
```

Обработчики `install` и `activate` вместе с их вспомогательными функциями оставьте как есть. В этом уроке добавятся функции стратегий, а обработчик `fetch` будет заменён.

Два правила Cache Storage API действуют для любой стратегии. Во-первых, в кеше хранятся только запросы `GET`. Во-вторых, тело ответа можно прочитать лишь один раз. Чтобы и отдать ответ странице, и сохранить его, вызовите `response.clone()` и положите в кеш копию.

## Cache first

`Cache first` (сначала кеш, затем сеть) ищет ответ в кеше и, если находит, возвращает его. В сеть стратегия обращается только при промахе, а полученный ответ сохраняет на будущее.

```js
async function cacheFirst(request) {
  const cached = await caches.match(request);
  if (cached) {
    return cached;
  }

  const response = await fetch(request);
  if (response.ok) {
    const cache = await caches.open(CACHE_NAME);
    await cache.put(request, response.clone());
  }
  return response;
}
```

Это та же логика, что и в `fromCacheOrNetwork` из урока 9, так что функцию можно просто переименовать в `cacheFirst`. Из всех стратегий эта самая быстрая, а после того как файл попал в кеш, она работает и без сети. Расплачиваться приходится свежестью: файл в кеше не меняется, пока вы не измените сам кеш. Для app shell это приемлемо. Отредактировав `style.css`, вы заодно поднимаете имя кеша до следующей версии, `daily-quote-v3`, и новый сервис-воркер при установке заново кеширует свежие копии — так, как это было в уроках 6 и 9.

## Network first

`Network first` (сначала сеть, затем кеш) первым делом обращается к сети. Если запрос удался, стратегия обновляет кеш; если сеть недоступна, возвращает последнюю сохранённую копию.

```js
async function networkFirst(request) {
  const cache = await caches.open(CACHE_NAME);
  try {
    const response = await fetch(request);
    if (response.ok) {
      await cache.put(request, response.clone());
    }
    return response;
  } catch (error) {
    const cached = await cache.match(request);
    if (cached) {
      return cached;
    }
    throw error;
  }
}
```

`fetch()` отклоняет промис только тогда, когда отказывает сама сеть. HTTP-ошибка вроде `404` всё равно приходит как ответ, и функция передаёт его странице.

Пока сеть есть, пользователь всегда получает самые свежие данные. Цена — скорость: каждый запрос ждёт сеть, и на медленном соединении страница может долго простаивать, прежде чем дело дойдёт до кеша.

## Stale-while-revalidate

`Stale-while-revalidate` сразу отвечает из кеша и одновременно запрашивает у сети новую копию, чтобы сохранить её для следующего запроса. Если в кеше пока ничего нет, стратегия ждёт ответа сети.

```js
function staleWhileRevalidate(event) {
  const { request } = event;

  const network = fetch(request).then(async (response) => {
    if (response.ok) {
      const cache = await caches.open(CACHE_NAME);
      await cache.put(request, response.clone());
    }
    return response;
  });

  // Keep the worker alive until the background update finishes.
  event.waitUntil(network.catch(() => {}));

  return caches.match(request).then((cached) => cached || network);
}
```

Эта функция принимает всё событие, а не только запрос. Страница может получить ответ из кеша задолго до того, как отзовётся сеть, а простаивающий сервис-воркер браузер вправе остановить — и тогда обновление пропадёт. `event.waitUntil()` просит браузер не останавливать сервис-воркер, пока промис не завершится. `catch` превращает неудачное обновление в тихую пустую операцию: свой ответ страница уже получила.

Получается быстро и без зависимости от сети. Цена в том, что пользователь видит данные, отстающие на одно посещение: изменение на сервере проявится при следующей загрузке, а не при текущей.

## Network only и cache only

Ещё две стратегии настолько просты, что кода почти не требуют.

`Network only` всегда обращается к сети и вовсе не трогает кеш. Она получается сама собой, если обработчик `fetch` не вызывает `event.respondWith()`: тогда браузер обрабатывает запрос обычным образом. Подходит она для запросов, которые нельзя кешировать, например `POST`-запросов или аналитики.

`Cache only` отвечает только из кеша:

```js
async function cacheOnly(request) {
  const cached = await caches.match(request);
  return cached || Response.error();
}
```

`Response.error()` завершает запрос так же, как сетевая ошибка. Cache only безопасна лишь для файлов, которые заведомо закешированы заранее. На практике те же файлы покрывает cache first, которая к тому же умеет справиться с промахом.

## Распределение запросов по типам

Теперь свяжем стратегии с запросами Daily Quote. Замените обработчик `fetch` из урока 9 таким:

```js
self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);

  // Network only: other methods and other origins go to the browser.
  if (request.method !== 'GET' || url.origin !== self.location.origin) {
    return;
  }

  // Data: answer fast, refresh in the background.
  if (url.pathname === '/quotes.json') {
    event.respondWith(staleWhileRevalidate(event));
    return;
  }

  // App shell and other static files: cache first.
  event.respondWith(cacheFirst(request));
});
```

Порядок проверок важен. Первая пропускает прямо в сеть всё, чем сервис-воркеру заниматься не следует. Вторая выделяет файл с данными. Всё остальное — это app shell или другие статические файлы: страницы, таблицы стилей, скрипты, иконки.

## Какую стратегию выбрать для quotes.json

`quotes.json` — единственный файл, который меняется без выпуска новой версии приложения: добавить цитату на сервере можно в любой момент. Поэтому cache first ему не подходит — пользователи не увидели бы новых цитат до следующей версии кеша. И network first, и stale-while-revalidate сохраняют данные свежими и работают без сети.

Выбор зависит от того, во что обходится устаревшая копия. Daily Quote показывает одну случайную цитату из списка, и список, отстающий на одно посещение, остаётся вполне хорошим списком. Важнее здесь скорость: со stale-while-revalidate цитата появляется сразу, даже на медленном соединении. Поэтому Daily Quote использует stale-while-revalidate.

Network first стоит выбрать, когда устаревшие данные — настоящая проблема: баланс счёта, статус заказа или новостная страница, на которой читатель ждёт последнюю версию. Тогда при наличии сети пользователь ждёт чуть дольше, зато, пока сеть работает, никогда не видит устаревших данных.

## Сравнение компромиссов

| Стратегия | Скорость | Свежесть | Без сети | Где уместна |
| --- | --- | --- | --- | --- |
| Cache first | Самая высокая после первой загрузки | Устаревает, пока не изменится кеш | Да, после кеширования | App shell с версиями, иконки, шрифты |
| Network first | Ждёт сеть | Самые свежие данные при наличии сети | Да, последняя сохранённая копия | Данные, которые должны быть актуальными |
| Stale-while-revalidate | Высокая после кеширования | Отстаёт на одно посещение | Да, после кеширования | Данные, для которых слегка устаревшая копия допустима |
| Network only | Ждёт сеть | Всегда свежие | Нет | `POST`-запросы, аналитика, платежи |
| Cache only | Самая высокая | Только то, что закешировано заранее | Да | Файлы, которые заведомо закешированы заранее |

## Попробуйте

1. Добавьте в `sw.js` функции стратегий и новый обработчик `fetch`.
2. Выполните `npx http-server -c-1` в папке `daily-quote/` и откройте `http://localhost:8080` в Chrome.
3. Активируйте обновлённый сервис-воркер так же, как в уроке 7. Например, включите **Update on reload** в DevTools в разделе **Application > Service workers**, перезагрузите страницу и снова выключите этот параметр.
4. Откройте **Application > Storage > Cache storage**, выберите `daily-quote-v2` и убедитесь, что там появилась запись для `/quotes.json`.
5. Добавьте в `quotes.json` новую цитату и перезагрузите страницу один раз. Страница всё ещё берёт старый список, но в закешированном `/quotes.json` уже есть ваша цитата. Если содержимое кеша на экране выглядит устаревшим, нажмите **Refresh**. Следующая перезагрузка возьмёт новый список.
6. На панели **Network** выберите в регулировке скорости (throttling) значение **Offline** и перезагрузите страницу. Страница и цитата по-прежнему появятся, потому что обе берутся из кеша.

Закончив, верните значение **No throttling**.

## Библиотеки со стратегиями

В большом проекте эти функции редко пишут вручную. Библиотеки вроде [Workbox](https://developer.chrome.com/docs/workbox) предлагают те же стратегии в виде готовых классов и добавляют удобства: например, тайм-аут сети для network first и ограничение размера кеша. В их основе те же идеи, так что выбор стратегии по-прежнему определяется компромиссами из этого урока.

В следующем уроке появится резервная страница для работы без сети — на случай запросов, которых нет в кеше и до которых нельзя дотянуться по сети.
