Благодаря манифесту Daily Quote можно установить. Но установленное приложение по-прежнему зависит от сети: откройте его без подключения, и оно не загрузится. Чтобы это изменить, нужен код, который работает вне страницы и сам решает, чем ответить на каждый запрос. Такой код и называется сервис-воркером. В этом уроке мы сложим о нём ясное представление, а в следующих зарегистрируем его и заставим работать.

## Прокси, написанный на JavaScript

`Сервис-воркер` (service worker) — это JavaScript-файл, который браузер выполняет отдельно от ваших страниц. Он служит `программируемым прокси` (programmable proxy) между страницами одного origin и сетью.

Без сервис-воркера запрос страницы уходит прямо в сеть:

```text
page ──────────────────────▶ network
```

Когда сервис-воркер есть, запросы подконтрольных ему страниц сначала проходят через него:

```text
page ──▶ service worker ──▶ network
                │
                └──▶ cache
```

Ответ на каждый запрос выбирает ваш код. Он может, как обычно, отправить запрос в сеть, может вернуть сохранённую копию из кеша, а может и собрать ответ с нуля — например, страницу для работы без сети. Из этой единственной способности вырастают и офлайн-режим, и стратегии кеширования, и обновления.

Один сервис-воркер обслуживает множество страниц. В Daily Quote один и тот же воркер будет обрабатывать запросы и `index.html`, и `about.html` — во всех открытых вкладках. Какими страницами он управляет, определяет его `область действия` (scope); её вы зададите в следующем уроке.

## Он откликается на события

Сервис-воркер `управляется событиями` (event-driven). У него нет главного цикла и нет кода, который выполнялся бы постоянно. Браузер запускает его, когда появляется событие, требующее обработки, и ваш код на это событие отвечает. В курсе нам понадобятся такие события:

- `install` — браузер устанавливает новый или изменившийся воркер. Здесь удобно подготовить файлы для работы без сети.
- `activate` — новый воркер становится активным и сменяет прежнюю версию, если она была. Здесь удаляют старые кеши.
- `fetch` — подконтрольная страница выполнила запрос: за самой страницей, скриптом, изображением или через вызов `fetch()`.
- `push` — с вашего сервера пришло push-сообщение. Это может случиться, даже когда ни одна страница приложения не открыта.

Вот минимальная заготовка, которая лишь записывает события в лог:

```js
// sw.js — a skeleton that only logs events
self.addEventListener('install', (event) => {
  console.log('install');
});

self.addEventListener('activate', (event) => {
  console.log('activate');
});

self.addEventListener('fetch', (event) => {
  console.log('fetch', event.request.url);
});

self.addEventListener('push', (event) => {
  console.log('push');
});
```

Внутри сервис-воркера `self` — его глобальный объект, так же как `window` на странице. Все обработчики подключаются к нему. Сам по себе этот файл пока ничего не делает: браузер запустит его только после того, как страница его зарегистрирует, а регистрации посвящён следующий урок.

## Правила, по которым он живёт

Сервис-воркер обладает большой властью, поэтому браузер держит его в строгих рамках. Каждое из этих правил влияет на то, как пишется код.

**Никакого DOM.** Воркер выполняется в собственном потоке, а не в потоке страницы. У него нет ни `document`, ни `window`, поэтому прочитать или изменить страницу он не может. Когда страницу нужно обновить, воркер и страница обмениваются сообщениями.

**Только защищённый контекст.** Браузер предоставляет сервис-воркеры лишь в `защищённом контексте` (secure context) — на странице, загруженной по HTTPS, или, для локальной разработки, с `localhost`. Воркер способен подменить любой ответ сайта, и при обычном HTTP злоумышленник в сети мог бы подсунуть вместо него собственный скрипт. Поэтому `http://localhost:8080` работает, а то же приложение, открытое по обычному HTTP через IP-адрес вашего Mac в локальной сети, — нет.

**Браузер может остановить его в любой момент.** Когда обрабатывать нечего, браузер после недолгого простоя останавливает воркер и снова запускает его к следующему событию. При каждом перезапуске скрипт выполняется с самого начала, и значения глобальных переменных теряются:

```js
let requestCount = 0;

self.addEventListener('fetch', () => {
  requestCount += 1; // starts again from 0 after every restart
});
```

Не храните состояние в глобальных переменных. Всё, что понадобится позже, сохраняйте в Cache Storage API или IndexedDB.

**Только асинхронные API.** Сервис-воркер ни в коем случае не должен блокироваться. Синхронные API, такие как `localStorage` и синхронный `XMLHttpRequest`, ему недоступны. Вместо них используются асинхронные: `fetch()`, Cache Storage API и IndexedDB. Все они возвращают промисы или порождают события.

## Сервис-воркер и Web Worker

Возможно, вам знаком обычный `Web Worker`. Страница создаёт его вызовом `new Worker('worker.js')`, чтобы вынести тяжёлую работу из главного потока. Оба вида воркеров выполняются в отдельном потоке и не имеют доступа к DOM. В остальном они различаются:

| Свойство | Web Worker | Сервис-воркер |
| --- | --- | --- |
| Назначение | Тяжёлые вычисления вне главного потока | Прокси между страницами и сетью |
| Как создаётся | `new Worker()` на странице | Регистрацией в браузере |
| Кого обслуживает | Страницу, которая его создала | Все страницы в своей области действия |
| Время жизни | Живёт, пока жива его страница | Запускается и останавливается браузером |
| Работает без открытой страницы | Нет | Да, для таких событий, как `push` |
| Перехватывает сетевые запросы | Нет | Да, через событие `fetch` |
| Требует защищённого контекста | Нет | Да |

Коротко говоря, Web Worker помогает считать одной странице, а сервис-воркер обслуживает всё приложение и может работать, когда ни одна страница не открыта.

## Проверьте, готов ли браузер

Запустите Daily Quote из папки проекта командой `npx http-server -c-1` и откройте `http://localhost:8080` в Chrome. Откройте консоль DevTools сочетанием Option-Command-J и выполните:

```js
window.isSecureContext;
'serviceWorker' in navigator;
```

Обе строки вернут `true`. Первая подтверждает, что `localhost` считается защищённым контекстом, вторая — что страница может зарегистрировать сервис-воркер. В незащищённом контексте `navigator.serviceWorker` отсутствует, поэтому вторая строка вернёт `false`.
