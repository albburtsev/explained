**Роль** — это учётная сущность PostgreSQL, которая может владеть объектами, получать права и состоять в других ролях. Обычно роли служат одной из двух целей:

- **Роль для входа** представляет человека или приложение, которые подключаются к базе.
- **Групповая роль**, как правило, подключаться не может. Она собирает права, нужные для определённой работы, например для чтения отчётов.

**Привилегии на объекты** разрешают конкретные операции, например чтение таблицы. Следуйте **принципу минимальных привилегий**: давайте каждой роли для входа только те права, которые нужны для её работы, и обычно — через членство в группах.

## Роли для учётных записей и для полномочий

Создавать роли может суперпользователь или роль с атрибутом `CREATEROLE`. Для этих примеров подключитесь под локальным суперпользователем, которого создала настройка курса. Создайте одну роль для входа и две групповые роли:

```sql
CREATE ROLE app_ada LOGIN;
CREATE ROLE catalog_reader;
CREATE ROLE catalog_editor;
```

По умолчанию `CREATE ROLE` подразумевает `NOLOGIN`, поэтому групповые роли подключиться не смогут. `CREATE USER app_ada` — лишь другая запись для `CREATE ROLE app_ada LOGIN`.

`LOGIN` даёт роли возможность начинать сеанс. Но примет ли сервер конкретное подключение, по-прежнему решает его конфигурация аутентификации. В примерах ниже права проверяются через `SET ROLE`, чтобы не трогать настройки аутентификации.

Роли принадлежат **кластеру** — набору баз данных, которыми управляет один экземпляр сервера PostgreSQL. После создания роль `app_ada` известна во всех этих базах, но доступа к их таблицам ещё не имеет. Привилегии на объекты действуют только на те объекты, которые названы при их выдаче.

Посмотрите роли и их атрибуты в `psql`:

```text
\du
```

Не давайте обычным ролям приложений широких атрибутов вроде `SUPERUSER`, `CREATEDB`, `CREATEROLE` и `BYPASSRLS`. Суперпользователь минует почти все проверки прав, так что выдача привилегий на уровне объектов по-настоящему ограничить его не может.

## Выдача прав через членство

Сделайте роль для входа членом групповой роли:

```sql
GRANT catalog_reader TO app_ada;
```

По умолчанию роль наследует обычные привилегии ролей, в которых состоит. Поэтому членство может заменить повторную выдачу одних и тех же привилегий каждой роли для входа. Если убрать членство, исчезнет и этот путь доступа:

```sql
REVOKE catalog_reader FROM app_ada;
```

Для остальных примеров снова выдайте членство:

```sql
GRANT catalog_reader TO app_ada;
```

`SET ROLE` меняет активную роль сеанса. Оставаясь локальным суперпользователем, проверьте права новой роли для входа, не открывая второго подключения:

```sql
SET ROLE app_ada;

SELECT session_user, current_user;

RESET ROLE;
```

`session_user` остаётся ролью, которая открыла подключение, а `current_user` до `RESET ROLE` становится `app_ada`. Унаследованные привилегии обычно доступны и без переключения ролей. Переключение меняет и владельца объектов, созданных после него. Обычной роли, чтобы переключиться на другую, нужно членство с параметром `SET`.

## Доступ и к пространству имён, и к объекту

От имени исходной административной роли создайте отдельную схему и таблицу:

```sql
CREATE SCHEMA course_catalog;

CREATE TABLE course_catalog.books (
  isbn text PRIMARY KEY,
  title text NOT NULL,
  in_stock boolean NOT NULL DEFAULT true
);

INSERT INTO course_catalog.books (isbn, title)
VALUES ('978-0-00-000001-1', 'Reliable SQL');
```

Право `USAGE` на схему позволяет роли находить объекты в ней. Привилегия на таблицу, например `SELECT`, разрешает соответствующую операцию с этой таблицей. Выдайте обе:

```sql
GRANT USAGE ON SCHEMA course_catalog TO catalog_reader;
GRANT SELECT ON course_catalog.books TO catalog_reader;
```

Проверьте результат от имени роли для входа:

```sql
SET ROLE app_ada;

SELECT * FROM course_catalog.books;

UPDATE course_catalog.books
SET in_stock = false
WHERE isbn = '978-0-00-000001-1';
-- ERROR: permission denied for table books

RESET ROLE;
```

Чтение проходит, а запись отклоняется, потому что у `catalog_reader` есть только `SELECT`. Выдайте отдельный набор привилегий на редактирование и добавляйте его роли для входа, только когда ей действительно нужна эта работа:

```sql
GRANT USAGE ON SCHEMA course_catalog TO catalog_editor;
GRANT SELECT, INSERT, UPDATE, DELETE
ON course_catalog.books
TO catalog_editor;

GRANT catalog_editor TO app_ada;
```

Если роль должна выполнять известный набор операций, перечисляйте привилегии явно, а не пишите `ALL PRIVILEGES`. Привилегии на таблицу не распространяются на её последовательности. Если вставка берёт значения из отдельно управляемой последовательности, например созданной для столбца `serial`, выдайте и соответствующую привилегию на последовательность.

Посмотрите права доступа к схемам и отношениям в `psql`:

```text
\dn+ course_catalog
\dp course_catalog.*
```

## Владение и фактический доступ

Обычно владельцем объекта становится тот, кто его создал. Владелец может изменить или удалить объект, а после отзыва привилегий — выдать их снова. Оставляйте владение за контролируемыми ролями развёртывания: отзыв привилегий не способен надёжно ограничить владельца.

Фактический доступ роли складывается из привилегий, выданных:

- напрямую самой роли;
- через каждое унаследованное членство в ролях;
- `PUBLIC` — неявной группе, в которую входят все роли.

Один `REVOKE` может оставить доступ открытым по другому пути. Разбираясь с правами, проверяйте все три источника.

Передать привилегию на объект другой роли обычно может только владелец объекта, суперпользователь или роль, получившая право передачи этой привилегии. Не используйте `WITH GRANT OPTION`, если получатель не должен сознательно отвечать за дальнейшую раздачу этого доступа.

## Привилегии для будущих объектов

Привилегии на существующие таблицы не распространяются автоматически на таблицы, созданные позже. Если роль должна получать тот же доступ к будущим объектам, настройте привилегии по умолчанию:

```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA course_catalog
GRANT SELECT ON TABLES TO catalog_reader;
```

Эта команда затрагивает только будущие таблицы, которые создаст роль, выполнившая её. Существующие таблицы и настройки по умолчанию для других создателей останутся прежними. Администратор с нужными полномочиями может с помощью `FOR ROLE` настроить привилегии по умолчанию для другого создателя. В следующем примере предполагается, что роль `catalog_owner` уже существует:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE catalog_owner
IN SCHEMA course_catalog
GRANT SELECT ON TABLES TO catalog_reader;
```

Включайте выдачу привилегий и привилегии по умолчанию в развёртывание схемы, чтобы и существующие, и будущие объекты получали задуманный доступ.

## Практика

Выполните это упражнение в `postgresql_course` под локальной административной ролью, от имени которой создавалась база данных курса:

```sql
CREATE ROLE practice_reader;
CREATE ROLE practice_editor;
CREATE ROLE practice_ada LOGIN;

CREATE SCHEMA practice_access;

CREATE TABLE practice_access.notes (
  id integer PRIMARY KEY,
  body text NOT NULL
);

INSERT INTO practice_access.notes (id, body)
VALUES (1, 'Visible to readers');
```

Выполните следующие задания:

1. Выдайте `practice_reader` привилегии на схему и таблицу, необходимые для чтения `practice_access.notes`.
2. Выдайте `practice_editor` привилегии, необходимые для чтения, вставки, изменения и удаления строк этой таблицы, но не давайте право `CREATE` на схему.
3. Выдайте `practice_ada` только роль `practice_reader`, затем с помощью `SET ROLE practice_ada` убедитесь, что `SELECT` проходит, а `UPDATE` — нет.
4. Сбросьте роль, выдайте `practice_ada` роль `practice_editor`, снова переключитесь и убедитесь, что изменение теперь проходит.
5. От имени исходной роли задайте для `practice_reader` привилегии по умолчанию на таблицы, создайте ещё одну таблицу и под `practice_ada` проверьте, что новую таблицу можно читать без дополнительного обычного `GRANT`.
6. Изучите роли командой `\du`, а права доступа — командами `\dn+ practice_access` и `\dp practice_access.*`.

Задание выполнено, когда `practice_ada` может выполнять только те операции, которые даёт её текущее членство в ролях. Перед уборкой сбросьте активную роль, затем удалите схему и роли:

```sql
RESET ROLE;
ALTER DEFAULT PRIVILEGES IN SCHEMA practice_access
REVOKE SELECT ON TABLES FROM practice_reader;
DROP SCHEMA practice_access CASCADE;
DROP ROLE practice_ada;
DROP ROLE practice_reader;
DROP ROLE practice_editor;
```
