**JSON** представляет данные в виде объектов, массивов и скалярных значений — строк, чисел и логических значений. Тип `jsonb` в PostgreSQL хранит такие данные в разобранном двоичном виде, который поддерживает запросы, обновления и индексы.

JSONB хорошо подходит для изменчивых данных, например атрибутов товаров или ответов внешних API. Значения со стабильными типами, связями или правилами на уровне базы данных держите в обычных столбцах.

## Выбирайте `jsonb` осознанно

В PostgreSQL есть и `json`, и `jsonb`. Входные данные они принимают почти одинаковые, но хранят их по-разному:

| Тип | Как хранит данные | Когда использовать |
| --- | --- | --- |
| `json` | Сохраняет исходный текст как есть, включая незначащие пробелы, порядок ключей и повторяющиеся ключи. При обработке текст приходится разбирать заново. | Точное исходное представление имеет особое значение. |
| `jsonb` | Хранит разобранное представление, отбрасывает незначащие пробелы и порядок ключей, а для повторяющегося ключа оставляет только последнее значение. | Приложению нужно выполнять запросы к данным, обновлять, сравнивать или индексировать их. |

Большинству данных приложения, которые будут обрабатываться внутри PostgreSQL, подходит `jsonb`. Ни в одном из типов не полагайтесь на порядок ключей объекта: объект JSON — это набор именованных членов, а не упорядоченная запись.

У товара храните в столбцах идентификатор, артикул (`sku`) и название, а изменчивые атрибуты — в JSONB:

```sql
CREATE TABLE products (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku text NOT NULL UNIQUE,
  name text NOT NULL,
  attributes jsonb NOT NULL DEFAULT '{}'::jsonb,
  CONSTRAINT products_attributes_object
    CHECK (jsonb_typeof(attributes) = 'object')
);
```

На `sku` наложено ограничение уникальности. Проверка требует, чтобы `attributes` был объектом, и отвергает массивы, скалярные значения и JSON `null`.

Вставьте два товара с разными наборами атрибутов:

```sql
INSERT INTO products (sku, name, attributes)
VALUES
  (
    'BAG-001',
    'Travel bag',
    '{
      "color": "black",
      "tags": ["carry-on", "water-resistant"],
      "dimensions": {"weight_kg": 1.4}
    }'
  ),
  (
    'MUG-001',
    'Ceramic mug',
    '{
      "color": "blue",
      "capacity_ml": 350,
      "dishwasher_safe": true
    }'
  );
```

PostgreSQL проверяет синтаксис JSON и приводит каждую строку к типу столбца `jsonb`. Общую схему документа для всех строк он при этом не выводит.

## Извлекайте значения с нужным типом SQL

От оператора извлечения зависит, останется ли результат JSONB или станет текстом SQL:

- `->` извлекает член объекта или элемент массива как `jsonb`.
- `->>` извлекает его как `text`.
- `#>` и `#>>` идут по пути, заданному как `text[]`, и возвращают соответственно `jsonb` и `text`.

Результат JSONB нужен для дальнейших операций с JSON, а текстовый — когда SQL должен показать, привести к типу, отсортировать или сравнить скалярное значение:

```sql
SELECT
  sku,
  attributes ->> 'color' AS color,
  (attributes #>> '{dimensions,weight_kg}')::numeric AS weight_kg
FROM products;
```

У кружки нет `dimensions.weight_kg`, поэтому извлечение и приведение к числу возвращают SQL `NULL`. А значение вроде `"heavy"` вызвало бы ошибку приведения. Если поле обязано быть числом, закрепите это правило или используйте типизированный столбец.

Иначе легко спутать три состояния:

- SQL `NULL` обозначает отсутствующее или неизвестное значение SQL;
- JSON `null` — это значение, хранящееся внутри документа JSON;
- отсутствующий ключ вовсе не входит в документ.

Оператор `?` проверяет, существует ли ключ верхнего уровня:

```sql
SELECT
  sku,
  attributes ? 'warranty_years' AS has_warranty_key,
  attributes -> 'warranty_years' AS warranty_json,
  attributes ->> 'warranty_years' AS warranty_text
FROM products;
```

Ни у одного из товаров в примере этого ключа нет, поэтому оба извлечения возвращают SQL `NULL`, а `?` возвращает false. Если же в ключе хранится JSON `null`, `->` вернёт JSONB `null`, `->>` вернёт SQL `NULL`, а `?` вернёт true. Выберите единое соглашение для необязательных полей и проверяйте `?`, когда важно само наличие ключа.

## Ищите по структуре

Оператор **вхождения** `@>` проверяет, содержит ли левое значение JSONB структуру и значения, заданные справа:

```sql
SELECT sku, name
FROM products
WHERE attributes @> '{
  "color": "black",
  "tags": ["water-resistant"]
}'::jsonb;
```

Вхождение объектов следует структуре документа, а массив справа может совпасть с входящими в него элементами без требования того же порядка. Запрос выше требует и члена `color` на верхнем уровне, и нужного элемента в массиве `tags` верхнего уровня.

Оператор существования не рекурсивен. Этот запрос проверяет только наличие ключа `dimensions` на верхнем уровне:

```sql
SELECT sku
FROM products
WHERE attributes ? 'dimensions';
```

Для условий на вложенные данные используйте извлечение или вхождение. PostgreSQL предлагает также `jsonpath` — язык для описания путей и условий внутри документов JSON.

## Обновляйте, не заменяя документ вручную

`jsonb_set` возвращает копию, в которой изменён один путь. Обновите вложенный вес сумки так:

```sql
UPDATE products
SET attributes = jsonb_set(
  attributes,
  '{dimensions,weight_kg}',
  to_jsonb(1.6::numeric),
  false
)
WHERE sku = 'BAG-001';
```

Путь состоит из ключей объекта; числовые компоненты могут указывать позиции в массиве, начиная с нуля. Последний аргумент `false` запрещает создавать отсутствующий последний член. Предшествующие компоненты пути тоже должны существовать, иначе значение останется прежним. Если отсутствующий путь следует считать ошибкой, проверьте получившийся документ: по одному лишь числу строк не видно, изменился ли путь.

Оператор конкатенации `||` удобен, чтобы добавлять или заменять члены верхнего уровня:

```sql
UPDATE products
SET attributes = attributes || '{"warranty_years": 3}'::jsonb
WHERE sku = 'BAG-001';
```

Для объектов ключ из правого значения заменяет такой же ключ верхнего уровня слева. Это не рекурсивное слияние, поэтому, если изменение вложенное, используйте `jsonb_set`.

Обновление даже одного поля JSONB всё равно блокирует всю строку, создаёт по правилам MVCC новую версию строки и затрагивает соответствующие индексы. Держите документы достаточно компактными. Данные, которым нужны независимые параллельные обновления, выносите в отдельные строки: отдельные столбцы одной строки всё равно делят её блокировку.

## Индексируйте под форму запроса

Выбирайте индексы под нужные вам запросы, как в уроке об индексах. Индекс GIN по всему документу поддерживает поиск по вхождению, по существованию ключей и подходящие поиски с `jsonpath`:

```sql
CREATE INDEX products_attributes_gin
ON products USING GIN (attributes);

SELECT sku, name
FROM products
WHERE attributes @> '{"color": "black"}'::jsonb;
```

Класс по умолчанию `jsonb_ops` поддерживает `@>`, операторы существования ключей (`?`, `?|`, `?&`) и операторы `jsonpath` (`@?`, `@@`). Альтернативный `jsonb_path_ops` поддерживает `@>`, `@?` и `@@`, но не операторы существования ключей. Его индексы обычно меньше и могут ускорять поддерживаемые виды поиска:

```sql
CREATE INDEX products_attributes_path_gin
ON products USING GIN (attributes jsonb_path_ops);
```

Считайте его альтернативой первому индексу. Оставляйте оба, только если измерения оправдывают затраты на их хранение и запись.

Для часто запрашиваемого скалярного значения прицельный индекс по выражению может оказаться меньше и поддерживать обычные сравнения B-tree. Запрос должен последовательно использовать именно проиндексированное выражение:

```sql
CREATE INDEX products_weight_idx
ON products (((attributes #>> '{dimensions,weight_kg}')::numeric));

SELECT sku, name
FROM products
WHERE (attributes #>> '{dimensions,weight_kg}')::numeric < 2;
```

PostgreSQL вычисляет приведение типа при построении и поддержке этого индекса, поэтому строка, чьё значение не является допустимым числом, вызовет ошибку при вставке или обновлении. Если полю нужны надёжная типизация, поиск по диапазонам, ограничения или соединения, типизированный столбец обычно оказывается понятнее.

Как и в любом маленьком примере, PostgreSQL может предпочесть последовательное сканирование, потому что прочитать всю таблицу дешевле. Прежде чем решать, поможет ли индекс рабочей нагрузке в продакшене, проверьте это с помощью `EXPLAIN` на репрезентативных данных.

## Очертите границы гибких данных

Сохраняйте предсказуемую структуру документов, даже когда поля от строки к строке различаются. Единообразная форма упрощает запросы, индексы и код приложения.

Храните значение в обычном столбце, если оно:

- идентифицирует строку или участвует во внешнем ключе;
- требует `NOT NULL`, уникальности или стабильного скалярного типа;
- часто встречается в соединениях, группировке, сортировке или фильтрах по диапазону;
- должно легко обнаруживаться любым пишущим приложением и любым инструментом отчётности.

## Практика

Создайте локальный каталог с намеренно разной формой документов:

```sql
DROP TABLE IF EXISTS practice_catalog;

CREATE TABLE practice_catalog (
  sku text PRIMARY KEY,
  details jsonb NOT NULL,
  CHECK (jsonb_typeof(details) = 'object')
);

INSERT INTO practice_catalog (sku, details)
VALUES
  ('CAM-1', '{"color":"black","tags":["travel","sale"],"specs":{"weight_g":420}}'),
  ('MUG-2', '{"color":"blue","tags":["kitchen"],"dishwasher_safe":true}'),
  ('BAG-3', '{"color":"black","tags":["travel"],"specs":{"weight_g":900},"warranty_years":null}');
```

Выполните следующие задания:

1. С помощью вхождения найдите чёрные товары с тегом для путешествий.
2. С помощью `?`, `->` и `->>` отличите отсутствующий ключ гарантии от значения JSON `null`.
3. Измените вложенный вес камеры на `430` с помощью `jsonb_set`, а затем добавьте числовой член `warranty_years` верхнего уровня.
4. Создайте индекс GIN по `details`, выполните `ANALYZE` и изучите запрос с вхождением через `EXPLAIN`. Для трёх строк последовательное сканирование по-прежнему вполне разумно.

Задание выполнено, когда первый запрос возвращает `CAM-1` и `BAG-3`, запрос о гарантии отличает отсутствие ключа от JSON `null`, а камера после обоих обновлений сохраняет свои исходные поля. По окончании удалите `practice_catalog`.
