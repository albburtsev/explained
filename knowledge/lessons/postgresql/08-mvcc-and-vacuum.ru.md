**Многоверсионное управление конкурентным доступом (MVCC)** позволяет PostgreSQL хранить несколько физических версий одной логической строки. Какую **версию строки** увидит оператор, определяет его снимок.

Обычный `SELECT` может читать зафиксированную версию, пока другая транзакция изменяет строку. Блокировка строки ему для этого не нужна, хотя блокировки таблицы по-прежнему способны его задержать. Старые версии занимают место, пока их нельзя безопасно удалить. **VACUUM** делает это место снова пригодным для использования.

## Свяжите снимки с версиями строк

Создайте небольшую таблицу и посмотрите на три системных столбца PostgreSQL:

```sql
CREATE TABLE mvcc_accounts (
  owner text PRIMARY KEY,
  balance numeric(12, 2) NOT NULL
);

INSERT INTO mvcc_accounts (owner, balance)
VALUES ('Alice', 500.00);

SELECT ctid, xmin, xmax, owner, balance
FROM mvcc_accounts;
```

Конкретные значения в каждой базе данных будут свои:

- `ctid` указывает текущее физическое расположение версии строки. Он полезен для наблюдения, но не годится как долговечный идентификатор в приложении.
- `xmin` хранит идентификатор транзакции, создавшей эту версию.
- `xmax` хранит идентификатор транзакции, удалившей или заменившей эту версию. В нём также может храниться информация о блокировке строки, поэтому его значение само по себе не является простым признаком удаления.

Теперь обновите логическую строку и посмотрите на неё снова:

```sql
UPDATE mvcc_accounts
SET balance = 550.00
WHERE owner = 'Alice';

SELECT ctid, xmin, xmax, owner, balance
FROM mvcc_accounts;
```

`UPDATE` создаёт новую версию строки. Запрос возвращает одну Alice, потому что его снимку видна лишь одна версия, хотя более старая может по-прежнему занимать место. `DELETE` тоже оставляет версию, которая после фиксации становится невидимой для последующих снимков.

Не используйте `xmin`, `xmax` и `ctid` как постоянные данные приложения. Они раскрывают детали реализации, которыми управляет PostgreSQL, и могут меняться при обновлении строк или перезаписи таблиц.

## Посмотрите, почему старая версия должна сохраниться

Откройте два сеанса, чтобы связать версии строк с поведением уровней изоляции из урока о транзакциях. В сеансе A получите снимок на уровне транзакции:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM mvcc_accounts
WHERE owner = 'Alice';
-- 550.00
```

Пока сеанс A остаётся открытым, обновите строку в сеансе B и зафиксируйте изменение:

```sql
UPDATE mvcc_accounts
SET balance = 600.00
WHERE owner = 'Alice';
```

Сеанс A по-прежнему видит версию из своего снимка:

```sql
SELECT balance
FROM mvcc_accounts
WHERE owner = 'Alice';
-- still 550.00

COMMIT;
```

Новый оператор после этой фиксации увидит `600.00`. PostgreSQL сохранил прежнюю версию для сеанса A и новую — для последующих читателей. Когда устаревшая версия больше не нужна ни одному снимку и ни одной реплике, она становится **мёртвой версией строки**, которую VACUUM может удалить.

## Поймите, что поддерживает VACUUM

Стандартный `VACUUM` выполняет несколько связанных задач обслуживания:

1. Удаляет мёртвые версии строк и мёртвые записи индексов, когда они больше не нужны, и помечает освободившееся место как доступное для будущих записей.
2. Обновляет **карту видимости** таблицы, где отмечены страницы, все строки которых видны любой транзакции. Благодаря ей последующие запуски VACUUM могут пропускать такие страницы, а сканирование только индекса — обходиться без обращения к таблице ради проверки видимости.
3. **Замораживает** достаточно старые версии строк, чтобы они надёжно распознавались как старые, когда конечный счётчик идентификаторов транзакций PostgreSQL сделает полный оборот.

Обычный VACUUM, как правило, делает место пригодным для повторного использования внутри файла таблицы, но не возвращает его операционной системе. Поэтому часто обновляемая таблица может переиспользовать место, а размер её файла остаётся стабильным.

`ANALYZE` — отдельная операция: она делает выборку из содержимого таблицы и обновляет статистику планировщика запросов. Когда после крупного изменения данных нужна немедленная очистка и свежая статистика, запустите обе явно:

```sql
VACUUM (VERBOSE, ANALYZE) mvcc_accounts;
```

Запускайте `VACUUM` вне явного блока транзакции. `VERBOSE` сообщает, что именно сделала операция; это полезно при изучении, но для обслуживания не обязательно.

## Доверьте рутину autovacuum

**Autovacuum** запускает `VACUUM` и `ANALYZE` по мере изменения таблиц. Кроме того, он выполняет очистку, чтобы предотвратить переполнение счётчика идентификаторов транзакций (wraparound). Держите его включённым и меняйте настройки, когда измерения показывают такую необходимость. Временные таблицы, которые использовались в уроках о планировании запросов, требуют ручного обслуживания, потому что autovacuum к ним доступа не имеет.

Посмотреть его статистику на уровне таблиц можно так:

```sql
SELECT
  relname,
  n_live_tup,
  n_dead_tup,
  last_vacuum,
  last_autovacuum,
  vacuum_count,
  autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

`n_live_tup` и `n_dead_tup` — это оценки. Сопоставляйте их динамику с отметками времени VACUUM и интенсивностью обновлений таблицы. Если оценка мёртвых строк растёт, а свежих запусков autovacuum не видно, разберитесь в причинах.

Ручной VACUUM помогает после крупного обновления или удаления либо когда autovacuum не успевает. Если нужна только свежая статистика планировщика запросов, используйте `ANALYZE`.

## Не задерживайте очистку

VACUUM не может удалить версию, которая ещё нужна транзакции или реплике. Поэтому долгие транзакции способны задерживать очистку, даже если сам VACUUM завершается успешно. Задержать её могут и подготовленные транзакции, ожидающие внешнего координатора, и слоты репликации, которые запоминают, какие данные ещё нужны реплике.

Найдите транзакции, которые остаются открытыми долгое время:

```sql
SELECT
  pid,
  usename,
  state,
  xact_start,
  now() - xact_start AS transaction_age
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Прежде чем завершать сеанс, выясните, кому он принадлежит и зачем нужен. В коде приложения начинайте транзакции тогда, когда они действительно нужны, и без промедления фиксируйте или откатывайте их. Не оставляйте сеанс в состоянии `idle in transaction`, когда он ждёт следующей команды при открытой транзакции.

Удаляйте слот репликации, только убедившись, что его потребителю он больше не нужен.

## Приберегите `VACUUM FULL` для исключительных случаев

`VACUUM FULL` переписывает таблицу в компактный файл. Ему нужно дополнительное место на диске и блокировка таблицы `ACCESS EXCLUSIVE`, которая не даёт другим сеансам ни читать таблицу, ни писать в неё.

Прибегайте к нему, только когда возврат значительного объёма дискового пространства оправдывает плановый простой, — например, после необычно крупного удаления. Если таблица снова вырастет, обычного VACUUM, как правило, достаточно.

## Практика

Создайте строку, которую смогут наблюдать два локальных сеанса:

```sql
DROP TABLE IF EXISTS practice_mvcc_accounts;

CREATE TABLE practice_mvcc_accounts (
  owner text PRIMARY KEY,
  balance numeric(12, 2) NOT NULL
);

INSERT INTO practice_mvcc_accounts (owner, balance)
VALUES ('Alice', 500.00);
```

Откройте два окна Terminal в macOS, подключённых к `postgresql_course`.

1. В сеансе A начните транзакцию `REPEATABLE READ` и выберите `ctid`, `xmin` и `balance` для Alice.
2. В сеансе B прибавьте Alice `100.00` и выведите те же три значения. Пока сеанс A остаётся открытым, выполните `VACUUM (VERBOSE, ANALYZE) practice_mvcc_accounts;`.
3. Снова прочитайте строку в сеансе A, зафиксируйте транзакцию и прочитайте строку ещё раз уже вне транзакции.
4. В сеансе B повторите VACUUM с `VERBOSE` и посмотрите на `n_live_tup` и `n_dead_tup` для этой таблицы в `pg_stat_user_tables`.

Задание выполнено, когда физические идентификаторы после обновления меняются, сеанс A внутри своего снимка продолжает видеть `500.00`, а последующий оператор видит `600.00`. Сравните два отчёта VACUUM, затем удалите таблицу.
