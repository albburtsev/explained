**Транзакция** объединяет операторы базы данных в единое целое, которое либо фиксируется, либо откатывается. Её изменения **атомарны**: они либо проходят все вместе, либо не проходят вовсе.

**Уровень изоляции** определяет, какие изменения других транзакций видны данной транзакции и от каких проблем параллельной работы защищает PostgreSQL. Само по себе объединение операторов в транзакцию не устраняет всех конфликтов с другими сеансами.

## Атомарное многошаговое изменение

Создайте для примеров небольшую таблицу:

```sql
CREATE TABLE accounts (
  owner text PRIMARY KEY,
  balance numeric(12, 2) NOT NULL CHECK (balance >= 0)
);

INSERT INTO accounts (owner, balance)
VALUES ('Alice', 500.00), ('Bob', 200.00);
```

Ограничение `CHECK` — это правило базы данных, которое отвергает отрицательный баланс. `PRIMARY KEY` делает каждого владельца уникальным, а `NOT NULL` требует, чтобы баланс был указан.

При переводе денег должны измениться оба баланса. Поместите оба оператора в одну транзакцию:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100.00
WHERE owner = 'Alice';

UPDATE accounts
SET balance = balance + 100.00
WHERE owner = 'Bob';

COMMIT;
```

`BEGIN` открывает блок транзакции. `COMMIT` делает все её успешные изменения видимыми разом. Если операцию нужно отменить, выполните вместо этого `ROLLBACK`:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 600.00
WHERE owner = 'Alice';
-- ERROR: the CHECK constraint rejects a negative balance

ROLLBACK;
```

После ошибки в операторе транзакция прерывается, и, прежде чем продолжить, нужно выполнить `ROLLBACK`. Проверяйте и те исходы, которые не выглядят как ошибки SQL. `UPDATE`, не нашедший счёта, завершается успешно, но затрагивает ноль строк. Прежде чем фиксировать перевод, убедитесь, что каждое изменение затронуло ровно одну строку.

Даже без явного блока транзакции PostgreSQL выполняет каждый оператор в транзакции и обычно автоматически фиксирует его, если он выполнился успешно. Такой режим, **autocommit**, удобен для независимых операторов, но сделать два отдельных оператора неделимым целым он не может.

Откат отменяет не всё. **Последовательность** — например, счётчик, стоящий за столбцом идентификации, — может израсходовать номера, даже если транзакция откатится. Не может откат отменить и действия во внешних системах.

## Что определяет изоляция

Допустим, транзакция A читает баланс, а B в это время его меняет. Изоляция определяет, увидит ли следующий запрос в A зафиксированное изменение B. **Снимок** — это представление зафиксированных данных, доступное запросу или транзакции.

Типичные аномалии параллельной работы таковы:

- **Грязное чтение** — транзакция видит незафиксированные данные другой транзакции.
- **Неповторяемое чтение** — повторное чтение той же строки возвращает другое значение, потому что тем временем другая транзакция зафиксировала изменение.
- **Фантомное чтение** — повторный запрос возвращает другой набор подходящих строк, потому что тем временем другая транзакция зафиксировала изменение.
- **Аномалия сериализации** — транзакции дают зафиксированный результат, который не мог бы получиться ни при каком порядке их поочерёдного выполнения.

PostgreSQL принимает все четыре названия уровней изоляции из стандарта SQL, но реализует лишь три различных поведения:

| Запрошенный уровень | Поведение снимков в PostgreSQL | Главное следствие |
| --- | --- | --- |
| `READ UNCOMMITTED` | Ведёт себя как `READ COMMITTED` | Грязного чтения всё равно не бывает. |
| `READ COMMITTED` | Новый снимок для каждого оператора | Два запроса в одной транзакции могут увидеть разные зафиксированные данные. |
| `REPEATABLE READ` | Один снимок, снятый при первом запросе или изменении данных в транзакции | Повторные запросы видят стабильную картину, но аномалии сериализации остаются возможными. |
| `SERIALIZABLE` | Стабильный снимок плюс проверки на опасные сочетания чтения и записи | Результат успешно зафиксированных транзакций согласуется с каким-либо последовательным порядком их выполнения. |

По умолчанию PostgreSQL использует `READ COMMITTED`. Уровень `REPEATABLE READ` в PostgreSQL строже, чем требует стандарт SQL: он предотвращает не только неповторяемое, но и фантомное чтение. Грязного чтения не допускает ни один из этих уровней.

## Снимок оператора и снимок транзакции

Откройте два окна Terminal в macOS и в каждом запустите `psql -d postgresql_course`. Назовите их сеансом A и сеансом B. В сеансе A начните транзакцию с уровнем изоляции по умолчанию и прочитайте баланс Alice:

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;

SELECT balance FROM accounts WHERE owner = 'Alice';
-- 400.00
```

После сделанного ранее перевода значение равно `400.00`. Не закрывая транзакцию в сеансе A, выполните в сеансе B:

```sql
UPDATE accounts
SET balance = balance + 50.00
WHERE owner = 'Alice';
```

Если сеанс B работает в режиме autocommit, его изменение уже зафиксировано. Повторите запрос в сеансе A:

```sql
SELECT balance FROM accounts WHERE owner = 'Alice';
-- 450.00

ROLLBACK;
```

Каждый `SELECT` получал снимок на момент начала своего оператора, поэтому второй запрос увидел только что зафиксированное значение.

Теперь повторите опыт со стабильным снимком транзакции. Начните в сеансе A:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance FROM accounts WHERE owner = 'Alice';
-- 450.00
```

Затем добавьте в сеансе B ещё `50.00` тем же `UPDATE`. Сеанс A по-прежнему видит исходный снимок:

```sql
SELECT balance FROM accounts WHERE owner = 'Alice';
-- still 450.00

ROLLBACK;
```

Снимок создаётся первым запросом или первым оператором, изменяющим данные, а не самой командой `BEGIN`. Кроме того, транзакция всегда видит собственные более ранние изменения.

Выбирайте уровень изоляции в момент начала транзакции, как в этих примерах. Равнозначная форма `SET TRANSACTION ISOLATION LEVEL ...` должна выполняться до первого запроса или оператора изменения данных в транзакции.

## Serializable для правил, охватывающих несколько строк

Стабильный снимок сам по себе не защищает правило, которое охватывает несколько строк. Допустим, служба требует, чтобы на дежурстве всегда оставался хотя бы один врач:

```sql
CREATE TABLE on_call (
  doctor text PRIMARY KEY,
  active boolean NOT NULL
);

INSERT INTO on_call (doctor, active)
VALUES ('Alice', true), ('Bob', true);
```

Две транзакции уровня `REPEATABLE READ` могут каждая насчитать двух дежурных врачей и снять с дежурства разных. Зафиксироваться могут обе, ведь они меняют разные строки, — и дежурить не останется никого. Это и есть аномалия сериализации: при поочерёдном выполнении вторая транзакция увидела бы лишь одного дежурного врача и отказалась бы от изменения.

Вместо этого выполняйте на уровне `SERIALIZABLE` каждую транзакцию, которая обеспечивает это правило:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT count(*)
FROM on_call
WHERE active;

-- Deactivate one doctor only when the count is greater than one.
UPDATE on_call
SET active = false
WHERE doctor = 'Alice';

COMMIT;
```

SQL-комментарий это условие не обеспечивает: приложение должно само проверить количество, прежде чем выполнять `UPDATE`. Если два сеанса сначала посчитают врачей, а затем снимут с дежурства разных, PostgreSQL отклонит одну из транзакций с ошибкой сериализации. Уровень Serializable допускает параллельную работу и прерывает транзакции, когда это нужно для сохранения гарантии последовательного порядка.

Используйте `SERIALIZABLE` для решений, которые опираются на несколько чтений и записей, если правило нельзя выразить ограничением базы данных. `REPEATABLE READ` выбирайте, когда нужна стабильная картина данных без гарантии последовательного порядка. `READ COMMITTED` подходит, если операция остаётся корректной при новом снимке для каждого оператора.

## Повторные попытки как часть контракта

Транзакции уровня `REPEATABLE READ` могут завершиться ошибкой, если пытаются изменить строку, которая изменилась после создания их снимка. Транзакции `SERIALIZABLE` могут завершиться ошибкой ещё и тогда, когда PostgreSQL обнаруживает аномалию сериализации. Ошибка сериализации имеет SQLSTATE `40001`.

Обрабатывайте её так: откатите транзакцию и повторите **всю транзакцию** с самого начала:

```text
begin a new transaction
read every decision input again
perform all changes again
try to commit
if SQLSTATE is 40001, discard the attempt and retry
```

Повтор одного лишь последнего оператора опирался бы на решения, принятые по старому снимку. Делайте транзакции короткими, ограничивайте число повторов и при высокой конкуренции выдерживайте небольшую паузу между попытками. До фиксации избегайте внешних действий, например отправки сообщения, если их нельзя безопасно повторить.

## Практика

Подключитесь к `postgresql_course` и создайте для упражнения отдельную таблицу:

```sql
DROP TABLE IF EXISTS practice_accounts;

CREATE TABLE practice_accounts (
  owner text PRIMARY KEY,
  balance numeric(12, 2) NOT NULL CHECK (balance >= 0)
);

INSERT INTO practice_accounts (owner, balance)
VALUES ('Alice', 500.00), ('Bob', 200.00);
```

Сначала переведите `80.00` от Alice к Bob внутри транзакции, посмотрите на оба баланса и выполните `ROLLBACK`. Убедитесь, что балансы вернулись к исходным значениям. Повторите перевод и выполните `COMMIT`: теперь балансы должны быть `420.00` и `280.00`, а их сумма по-прежнему `700.00`.

Затем откройте второе окно Terminal в macOS. В сеансе A начните транзакцию `REPEATABLE READ` и прочитайте баланс Alice. В сеансе B добавьте Alice `20.00` и зафиксируйте изменение. Снова прочитайте баланс Alice в сеансе A, затем зафиксируйте сеанс A и прочитайте баланс ещё раз.

Задание выполнено, когда сеанс A дважды видит `420.00` внутри своего стабильного снимка и `440.00` после фиксации. По окончании удалите `practice_accounts`.
