**Advisory-блокировка** защищает числовой ключ, выбранный приложением. Ключ может обозначать, скажем, перестроение отчёта или работу для одного тенанта. PostgreSQL разбирается с конфликтующими запросами на этот ключ, но не знает, что он означает, и никаких строк не блокирует.

Все участники должны использовать один и тот же ключ и захватывать блокировку до начала защищаемой работы. Если правило можно выразить напрямую ограничением, атомарным оператором или блокировкой строки, предпочтите их. Advisory-блокировки выручают, когда у операции нет подходящей строки или таблицы, которую можно было бы заблокировать.

## Продумайте стабильное соглашение о ключах

Каждая функция advisory-блокировки принимает либо один ключ `bigint`, либо пару ключей `integer`. У этих двух форм раздельные пространства ключей, поэтому ключ из одного значения никогда не конфликтует с ключом из двух.

Форма из двух целых чисел удобна, когда одно значение обозначает тип ресурса, а другое — конкретный экземпляр:

```text
(21, tenant_id) means "rebuild this tenant's search index"
(22, tenant_id) means "generate this tenant's monthly invoice batch"
```

Определите ключи в одном общем модуле приложения или функции базы данных, чтобы:

- один и тот же логический ресурс всегда давал один и тот же ключ;
- несвязанные типы ресурсов не могли случайно получить одинаковый ключ;
- все сервисы, согласующие работу с ресурсом, следовали одному соглашению;
- идентификатор умещался в сигнатуру выбранной функции — с `integer` или `bigint`.

Лучше всего опираться на уже существующий стабильный числовой идентификатор. Хеширование строк может давать коллизии, и тогда несвязанная работа будет ждать друг друга. Если в один `bigint` нужно уместить несколько значений, задокументируйте и протестируйте кодирование и допустимые диапазоны.

Ключи advisory-блокировок действуют в пределах одной базы данных. Одинаковые ключи, захваченные в разных базах, друг с другом никак не согласуются.

## Для работы с базой данных предпочитайте блокировку уровня транзакции

**Advisory-блокировка уровня транзакции** освобождается, когда транзакция фиксируется или откатывается. `pg_advisory_xact_lock` ждёт, пока не удастся захватить исключительную блокировку. В этом примере предполагается, что две таблицы с документами уже существуют; упражнению в конце урока таблицы не понадобятся:

```sql
BEGIN;

SELECT pg_advisory_xact_lock(21, 7001);

-- Rebuild the application-defined resource for tenant 7001.
DELETE FROM tenant_search_documents
WHERE tenant_id = 7001;

INSERT INTO tenant_search_documents (tenant_id, document_id, search_text)
SELECT tenant_id, id, title || ' ' || body
FROM tenant_documents
WHERE tenant_id = 7001;

COMMIT;
```

Если другая транзакция удерживает конфликтующую блокировку на `(21, 7001)`, `SELECT` будет ждать. Работа для `(21, 7002)` при этом может продолжаться, потому что у неё другой ключ. При `COMMIT` или `ROLLBACK` PostgreSQL снимает блокировку уровня транзакции автоматически; функции, которая снимала бы её вручную, не существует.

`UPDATE`, который обходит эту advisory-блокировку, всё равно может изменить строки тенанта `7001`. Правила, которым обязан подчиняться любой пишущий, оставляйте за ограничениями базы данных.

Используйте явную транзакцию. В режиме autocommit блокировка снимается, как только завершается захвативший её оператор. Захватывайте блокировку до того, как прочитаете состояние, от которого зависит решение. На уровне `READ COMMITTED` последующие операторы получают свежие снимки уже после того, как предыдущий владелец блокировки закончит. Ожидание блокировки не обновляет уже полученный снимок `REPEATABLE READ` или `SERIALIZABLE`.

Делайте транзакции короткими и после взаимоблокировки или ошибки сериализации повторяйте транзакцию целиком, как в уроке о транзакциях.

## Выберите между ожиданием и немедленным отказом

Что произойдёт, если конфликтующей блокировкой владеет другой сеанс, определяет имя функции:

| Поведение | Функция уровня транзакции | Результат |
| --- | --- | --- |
| Ждать | `pg_advisory_xact_lock(...)` | Возвращает управление, захватив блокировку. |
| Попробовать один раз | `pg_try_advisory_xact_lock(...)` | Сразу возвращает `true` при успехе или `false`, если блокировка недоступна. |

Форма с попыткой подходит, когда пропустить работу, перенести её или сообщить «занято» лучше, чем заставлять запрос ждать:

```sql
BEGIN;

SELECT pg_try_advisory_xact_lock(21, 7001) AS acquired;
```

Посмотрите на `acquired`. Если там `false`, откатите транзакцию, не выполняя защищаемую работу. Если `true`, выполните работу и зафиксируйте транзакцию. Это обновление приведено для иллюстрации и предполагает, что `tenant_search_state` уже существует:

```sql
-- Run only after acquired is true.
UPDATE tenant_search_state
SET rebuilt_at = clock_timestamp()
WHERE tenant_id = 7001;

COMMIT;
```

Блокирующий вызов подходит для работы, которая должна дождаться своей очереди, — с тайм-аутом и возможностью отмены. Задания по расписанию часто могут считать `false` признаком того, что работа «уже идёт», и пропустить запуск или перенести его.

## Применяйте блокировки уровня сеанса осознанно

**Advisory-блокировка уровня сеанса** переживает границы транзакций. `pg_advisory_lock` ждёт, а `pg_try_advisory_lock` сразу возвращает логическое значение. Исключительную блокировку уровня сеанса снимает `pg_advisory_unlock`:

```sql
SELECT pg_try_advisory_lock(30, 9001) AS acquired;

-- If acquired is true, the same database session may run several transactions.

SELECT pg_advisory_unlock(30, 9001) AS released;
```

Уровень сеанса полезен, когда одна согласованная операция намеренно охватывает несколько транзакций. Но он влечёт и дополнительные обязательства:

- Откат транзакции блокировку не снимает.
- Повторные захваты одним и тем же сеансом накапливаются: каждому успешному захвату нужно соответствующее освобождение.
- Блокировка снимается при завершении сеанса, но если полагаться на разрыв соединения как на обычный способ уборки, ошибки останутся незамеченными.
- Пул соединений повторно использует соединения с базой данных. Захват, работа и освобождение должны происходить в одном и том же физическом сеансе. Если вернуть его в пул с удерживаемой блокировкой, он может заблокировать посторонние запросы.

После успешного захвата обеспечьте гарантированную уборку, например в блоке `finally`, и проверьте, что `pg_advisory_unlock` возвращает `true`. Если работа укладывается в одну транзакцию, предпочитайте блокировки уровня транзакции.

## Выберите исключительный или разделяемый режим

Функции выше захватывают **исключительные** блокировки, которые конфликтуют с блокировками всех остальных сеансов на тот же ключ. **Разделяемые** блокировки позволяют нескольким сеансам удерживать ключ одновременно. Для разделяемых блокировок уровня транзакции используйте `pg_advisory_xact_lock_shared` или `pg_try_advisory_xact_lock_shared`.

Так можно допустить либо нескольких читателей, либо одного исключительного обслуживающего процесса — при условии, что и читатели, и писатели следуют одному соглашению. Те же правила конфликтов действуют и между запросами уровня сеанса и уровня транзакции.

Для разделяемых блокировок уровня сеанса служат `pg_advisory_lock_shared`, `pg_try_advisory_lock_shared` и парная им `pg_advisory_unlock_shared`. Не снимайте разделяемую блокировку функцией для исключительной.

## Предотвращайте взаимоблокировки и случайные наборы блокировок

Advisory-блокировки участвуют в обычном механизме обнаружения взаимоблокировок PostgreSQL. Если одной операции нужно несколько ключей, все пути в коде должны захватывать их в одном и том же стабильном порядке:

```sql
BEGIN;

SELECT pg_advisory_xact_lock(21, 7001);
SELECT pg_advisory_xact_lock(21, 7002);

-- Coordinate work involving both tenants.

COMMIT;
```

Упорядочивание сначала по типу ресурса, а затем по числовому идентификатору — одно из возможных соглашений. Если взаимоблокировка всё же возникнет, PostgreSQL прервёт одну из транзакций; откатите её и повторите операцию целиком.

Когда функции блокировки вызываются над результатами запроса, из-за порядка вычисления блокировок может оказаться больше, чем подсказывает приписанный `LIMIT`. Сначала выберите нужные ключи в подзапросе. Этот шаблон предполагает, что `pending_rebuilds` существует, а `resource_id` имеет тип `integer`; выполняйте его внутри транзакции, содержащей защищаемую работу:

```sql
SELECT pg_advisory_xact_lock(21, selected.resource_id)
FROM (
  SELECT resource_id
  FROM pending_rebuilds
  WHERE ready
  ORDER BY resource_id
  LIMIT 10
) AS selected;
```

Advisory-блокировки делят память менеджера блокировок PostgreSQL с обычными блокировками. Они хороши для ограниченной координации, но не для блокировки неограниченного числа строк взамен блокировок строк.

## Посмотрите на активные advisory-блокировки

Advisory-блокировки видны в `pg_locks`. Следующий запрос показывает владельцев и ожидающих в текущей базе данных:

```sql
SELECT
  pid,
  mode,
  granted,
  waitstart,
  classid,
  objid,
  objsubid
FROM pg_locks
WHERE locktype = 'advisory'
  AND database = (
    SELECT oid
    FROM pg_database
    WHERE datname = current_database()
  )
ORDER BY granted DESC, pid;
```

`granted = false` означает ожидающий запрос. Чтобы найти тех, кто его блокирует, используйте `pg_blocking_pids(pid)`. Для ключей из двух целых чисел `classid` содержит первый ключ, `objid` — второй, а `objsubid` равен `2`. Для одного `bigint` в `classid` и `objid` лежат его старшая и младшая 32-битные половины, а `objsubid` равен `1`.

## Практика

Откройте два окна Terminal в macOS, подключённых к `postgresql_course`. В сеансе A захватите advisory-блокировку уровня транзакции и оставьте транзакцию открытой:

```sql
BEGIN;
SELECT pg_advisory_xact_lock(90, 1);
```

В сеансе B начните транзакцию и попробуйте захватить два ключа без ожидания:

```sql
BEGIN;
SELECT pg_try_advisory_xact_lock(90, 1) AS same_resource;
SELECT pg_try_advisory_xact_lock(90, 2) AS different_resource;
```

Не завершая ни одну из транзакций, посмотрите на строки advisory-блокировок в `pg_locks` и определите их `pid`, поля ключа, режим и признак предоставления. Откатите сеанс B, зафиксируйте сеанс A, затем начните в сеансе B новую транзакцию и снова попробуйте `(90, 1)`. Посмотрев на результат, откатите её.

Задание выполнено, когда первая попытка для `(90, 1)` возвращает `false`, другой ключ возвращает `true`, а исходный ключ после фиксации сеанса A тоже возвращает `true`. Ни ручного снятия блокировок, ни уборки не требуется: все блокировки действовали в пределах транзакции.
