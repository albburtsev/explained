**Индекс** — это отдельная структура данных, которая помогает PostgreSQL находить строки или упорядочивать их. Благодаря индексу запросу порой достаточно прочитать лишь малую часть таблицы.

Использовать ли индекс, решает планировщик запросов. Для маленькой таблицы или условия, под которое попадает множество строк, последовательное сканирование может оказаться дешевле. Каждый запрос проверяйте измерениями — так, как показано в предыдущем уроке про `EXPLAIN`.

## Измерьте запрос до создания индекса

Создайте временную таблицу, в которой строк достаточно, чтобы разница между способами доступа стала заметной:

```sql
CREATE TEMP TABLE index_orders AS
SELECT
  n::bigint AS id,
  (n % 1000) + 1 AS customer_id,
  CASE WHEN n % 100 = 0 THEN 'pending' ELSE 'paid' END AS status,
  timestamptz '2026-01-01 00:00:00+00'
    + (n * interval '1 minute') AS placed_at,
  ((n * 37) % 10000)::numeric / 100 AS total
FROM generate_series(1, 200000) AS n;

ANALYZE index_orders;
```

Посмотрите на типичный запрос — последние заказы одного покупателя:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, placed_at, total
FROM index_orders
WHERE customer_id = 42
ORDER BY placed_at DESC
LIMIT 20;
```

Ваш план и время выполнения могут отличаться. Пока индекса нет, PostgreSQL, скорее всего, просмотрит таблицу целиком и отсортирует подходящие строки, прежде чем применить ограничение. Запишите узел сканирования, число строк, отброшенных его фильтром, узел сортировки, буферы и время выполнения. Эти наблюдения станут точкой отсчёта для сравнения.

## Подберите индекс под форму запроса

`CREATE INDEX` создаёт B-tree, если не указан другой метод. B-tree поддерживает привычные сравнения на равенство и диапазоны, а также умеет возвращать записи по порядку.

Первое, что приходит в голову, — проиндексировать только столбец из фильтра:

```sql
CREATE INDEX index_orders_customer_idx
ON index_orders (customer_id);

ANALYZE index_orders;
```

Снова выполните тот же `EXPLAIN (ANALYZE, BUFFERS)`. Теперь планировщик запросов может найти строки покупателя `42` через индекс, хотя сортировать их по `placed_at`, возможно, всё равно придётся.

Но полная форма запроса — это и равенство по `customer_id`, и сортировка по `placed_at`. Составной индекс способен поддержать и то и другое:

```sql
CREATE INDEX index_orders_customer_time_idx
ON index_orders (customer_id, placed_at DESC);
```

Выполните план в третий раз. PostgreSQL может начать с записей покупателя `42`, читать их в порядке убывания времени и остановиться после 20 строк. В зависимости от данных и состояния кэша вы, вероятно, увидите `Index Scan` без отдельной сортировки.

Порядок столбцов важен. Составной B-tree обычно работает эффективнее всего, когда на его ведущие столбцы наложены условия равенства, а за ними следует условие диапазона или сортировки. Иногда PostgreSQL может использовать и последующие столбцы без условия на ведущий. И всё же, прежде чем считать, что `(customer_id, placed_at)` хорошо покрывает поиск по одному `placed_at`, измерьте такой поиск.

Второй индекс нередко справляется и с простым поиском по покупателю. Если планы подтверждают это для всей нагрузки, удалите избыточный индекс по одному столбцу: он лишь занимает место и добавляет работы при записи.

## Применяйте специализированные индексы осознанно

B-tree по умолчанию подходит для многих нагрузок, но PostgreSQL предлагает и другие методы индексирования и способы описать индекс. Выбирайте их по тем операторам и запросам, которые индекс должен поддерживать:

- **B-tree** обслуживает равенство, диапазоны, проверки на null и выборку в заданном порядке.
- **Hash** обслуживает только равенство.
- **GIN** — инвертированный индекс: он сопоставляет составные части значения со строками, в которых они встречаются. Он поддерживает массивы, полнотекстовый поиск и подходящие операторы JSONB.
- **GiST** и **SP-GiST** поддерживают расширяемые стратегии — например, геометрический поиск, поиск по диапазонам и поиск ближайших соседей, — в зависимости от класса операторов.
- **BRIN** хранит сводку по диапазонам блоков таблицы. Он бывает компактным и эффективным, когда индексируемые значения следуют физическому порядку строк, — например, для временных меток в таблице, куда новые строки в основном добавляются в конец.

**Класс операторов** определяет, какие операторы индекс поддерживает для данного типа данных. Прежде чем выбрать метод, посмотрите, какие операторы используются в предложениях `WHERE`, `JOIN` и `ORDER BY` запроса.

**Индекс по выражению** хранит вычисленное значение. Создайте временную таблицу, чтобы опробовать поиск по email без учёта регистра и проверку уникальности:

```sql
CREATE TEMP TABLE users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL
);

CREATE UNIQUE INDEX users_email_lower_uniq
ON users (lower(email));

INSERT INTO users (email)
VALUES ('Ada@example.com');

SELECT id
FROM users
WHERE lower(email) = lower('ada@example.com');
```

Запрос использует проиндексированное выражение `lower(email)`. Вычислять и поддерживать его приходится при каждой записи, и это её удорожает.

**Частичный индекс** включает только строки, удовлетворяющие его предикату — условию после `WHERE`. Вернитесь к `index_orders` и проиндексируйте лишь заказы в ожидании:

```sql
CREATE INDEX orders_pending_customer_time_idx
ON index_orders (customer_id, placed_at DESC)
WHERE status = 'pending';
```

Запрос может использовать такой индекс, только если PostgreSQL ещё на этапе планирования способен доказать, что из условия запроса следует `status = 'pending'`. Согласуйте предикат с устойчивыми условиями нагрузки: условия, записанные иначе или параметризованные, могут не позволить вывести это следствие.

**Покрывающий индекс** содержит все столбцы, нужные запросу. `INCLUDE` добавляет столбцы, которые можно вернуть из индекса, но которые не служат ключами поиска:

```sql
CREATE INDEX orders_customer_time_cover_idx
ON index_orders (customer_id, placed_at DESC)
INCLUDE (id, total, status);
```

Здесь есть все столбцы, которые нужны запросу последних заказов из примера выше. **Сканирование только индекса** (index-only scan) может обойтись без чтения страниц таблицы, если PostgreSQL к тому же знает, что строки видны транзакции. Недавно изменённые страницы всё же может понадобиться посетить, чтобы проверить видимость. Включённые столбцы увеличивают индекс, поэтому измерьте, окупает ли экономия на чтении таблицы этот рост.

## Отделяйте производительность от корректности

Для первичного ключа и ограничения уникальности PostgreSQL сам создаёт уникальные индексы B-tree. Не добавляйте дублирующие индексы по тем же ключам. Если нужна уникальность обычных столбцов, ограничение выражает это правило напрямую. Этот вариант, в отличие от индекса по `lower(email)` из примера выше, сравнивает `email` в том виде, в каком он хранится:

```sql
ALTER TABLE users
ADD CONSTRAINT users_email_unique UNIQUE (email);
```

`CREATE UNIQUE INDEX` применяйте, когда правилу нужно именно выражение или подмножество строк, как в примерах выше. Напомним урок о внешних ключах: PostgreSQL индексирует первичный или уникальный ключ, на который ссылаются, но не создаёт индекс по ссылающимся столбцам автоматически.

Обычный неуникальный индекс лишь добавляет ещё один возможный путь доступа и никогда не гарантирует, что запрос им воспользуется. Корректность не должна зависеть от конкретного плана.

## Учитывайте затраты на протяжении жизни индекса

Индексы занимают место на диске и добавляют работы при записи и очистке. Сравнивайте планы на репрезентативных данных, проверяйте, что результаты остаются верными, и оставляйте только те индексы, польза от которых оправдывает эти затраты.

Для постоянной таблицы обычное построение индекса разрешает чтение, но блокирует запись до своего завершения. `CONCURRENTLY` позволяет писать в таблицу во время построения. Например, если бы у таблицы `orders` из урока о внешних ключах ещё не было поддерживающего индекса, его можно было бы построить так:

```sql
CREATE INDEX CONCURRENTLY orders_customer_id_idx
ON orders (customer_id);
```

Если такой индекс уже есть, пропустите эту команду. Для временных таблиц индекс всегда строится неконкурентно, потому что другие сеансы к ним доступа не имеют.

Конкурентное построение выполняет больше работы, обычно длится дольше и не может выполняться внутри блока транзакции. Сбой может оставить невалидный индекс: запросы его игнорируют, но при записи он по-прежнему поддерживается. Проверьте результат командой `\d orders`. Чтобы исправить положение, удалите невалидный индекс и повторите построение или воспользуйтесь `REINDEX INDEX CONCURRENTLY`.

Прежде чем удалять индекс, понаблюдайте за ним в течение репрезентативного периода. `idx_scan` в `pg_stat_user_indexes` считает сканирования только с момента последнего сброса статистики. Проверьте также, не обеспечивает ли индекс какое-либо ограничение, не поддерживает ли он редкие, но критичные операции и не обслуживает ли запросы, с которыми другой индекс эффективно не справится.

## Практика

Постройте временную таблицу, достаточно большую, чтобы локально сравнить два пути доступа:

```sql
CREATE TEMP TABLE practice_orders AS
SELECT
  n::bigint AS id,
  (n % 2000) + 1 AS store_id,
  timestamptz '2026-01-01 00:00:00+00'
    + (n * interval '1 minute') AS created_at,
  ((n * 37) % 10000)::numeric / 100 AS total
FROM generate_series(1, 200000) AS n;

ANALYZE practice_orders;
```

С помощью `EXPLAIN (ANALYZE, BUFFERS)` снимите исходные показатели для запроса такой формы: фильтр `store_id = 42`, сортировка по `created_at` по убыванию, возврат `id`, `created_at` и `total`, остановка после 20 строк. Запишите сканирование, сортировку, число буферов и время выполнения.

Создайте один индекс B-tree, порядок столбцов в котором поддерживает и условие равенства, и нужную сортировку. Выполните `ANALYZE`, снова получите план того же самого запроса и сравните его с исходным.

Задание выполнено, когда оба запроса возвращают одни и те же 20 строк в одном и том же порядке, а вы можете объяснить, почему план с индексом способен остановиться раньше и обойтись без отдельной сортировки. Время выполнения от запуска к запуску может меняться. Временная таблица и индекс исчезнут, когда сеанс завершится.
