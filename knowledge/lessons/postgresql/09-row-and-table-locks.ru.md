MVCC позволяет обычному чтению работать со снимками, не мешая записи. Но некоторые решения требуют ещё и не допускать параллельных изменений. **Блокировка** заставляет несовместимые операции ждать. Многие блокировки PostgreSQL берёт автоматически, а явные блокировки защищают решения, которые растягиваются на несколько операторов.

Важен охват блокировки:

- **Блокировка на уровне строк** согласует изменения выбранных строк. Обычный `SELECT` она не задерживает, но может заставить ждать другую транзакцию, которая пытается обновить, удалить или несовместимо заблокировать те же строки.
- **Блокировка на уровне таблицы** согласует доступ ко всей таблице. PostgreSQL берёт её для каждой таблицы, которой касается оператор, даже если тот блокирует и отдельные строки.

Блокировки строк и таблиц обычно держатся до `COMMIT` или `ROLLBACK`. Решая, как долго удерживать блокировку, помните о границах транзакции из урока о транзакциях.

## Заблокируйте строку, прежде чем принимать решение

Создайте небольшую таблицу складских остатков:

```sql
CREATE TABLE inventory (
  product_id bigint PRIMARY KEY,
  stock integer NOT NULL CHECK (stock >= 0)
);

INSERT INTO inventory (product_id, stock)
VALUES (101, 5);
```

Допустим, приложению нужно прочитать текущий остаток, принять в своём коде небольшое решение, а затем списать три единицы. В сеансе A заблокируйте строку в момент чтения:

```sql
BEGIN;

SELECT stock
FROM inventory
WHERE product_id = 101
FOR UPDATE;

-- The application confirms that stock is at least 3.
UPDATE inventory
SET stock = stock - 3
WHERE product_id = 101;

COMMIT;
```

Пока сеанс A удерживает блокировку, обычный `SELECT` в сеансе B может прочитать последнюю зафиксированную версию строки. А конкурирующие `UPDATE`, `DELETE` или `SELECT ... FOR UPDATE` для товара `101` будут ждать.

На уровне `READ COMMITTED` блокирующее чтение, которому пришлось ждать, после завершения сеанса A перепроверяет строку и возвращает обновлённую версию, если та по-прежнему удовлетворяет `WHERE`. Удалённая строка возвращена не будет. На уровнях `REPEATABLE READ` и `SERIALIZABLE` строка, изменённая после получения снимка, может вместо этого привести к ошибке сериализации.

Охват блокировки задаёт предложение `WHERE`. Выбирайте только те строки, которые действительно нужны транзакции, и поддерживайте поиск подходящим индексом, чтобы PostgreSQL находил их эффективно. Блокировка строки может ещё и повлечь запись на диск, потому что PostgreSQL помечает строку как заблокированную.

Не разносите блокирующее чтение и обновление по разным транзакциям. Фиксация сразу после `SELECT ... FOR UPDATE` снимает блокировку раньше, чем она успеет что-либо защитить.

## По возможности обходитесь одним атомарным оператором

Явная блокировка нужна не всегда. Изменение остатка может выразить своё правило в одном операторе:

```sql
UPDATE inventory
SET stock = stock - 3
WHERE product_id = 101
  AND stock >= 3
RETURNING stock;
```

На уровне `READ COMMITTED` PostgreSQL автоматически блокирует обновляемую строку и, дождавшись параллельного обновления, перепроверяет `stock >= 3`. Одна возвращённая строка означает успех, ноль — что товара не хватает или такого товара нет. Проверка и изменение происходят в одном операторе. В режиме autocommit блокировка снимается, когда завершается транзакция этого оператора.

Блокирующее чтение применяйте, когда решение требует нескольких операторов, опирающихся на одну и ту же строку. Работу, которой не нужна база данных, по возможности выносите за пределы транзакции, удерживающей блокировку.

## Выбирайте самую слабую достаточную блокировку строки

В предложении блокировки `SELECT` PostgreSQL предлагает четыре уровня силы:

| Предложение | Что оно защищает | Типичное применение |
| --- | --- | --- |
| `FOR UPDATE` | Не пускает другие блокировки строки, обновления и удаления. | Транзакция может обновить ключевые столбцы или удалить строку. |
| `FOR NO KEY UPDATE` | Не пускает конфликтующих писателей, но допускает `FOR KEY SHARE`. | Транзакция изменит только неключевые значения. |
| `FOR SHARE` | Допускает другие разделяемые блокировки строки, но не пускает обновления и удаления. | Несколько транзакций могут изучать строку, не давая её изменить. |
| `FOR KEY SHARE` | Запрещает удаление и изменение ключа, но допускает обновление неключевых значений. | Транзакция рассчитывает, что ключ строки, на который ссылаются, останется действительным. |

`UPDATE` и `DELETE` берут блокировки строк автоматически. Для явного блокирующего чтения выбирайте самый слабый режим, который ещё защищает правило. Более сильные режимы могут заставить ждать больше транзакций.

В соединении добавьте `OF <alias>`, если заблокировать нужно только один из источников:

```sql
SELECT o.id, o.total, c.email
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE o.id = 42
FOR UPDATE OF o;
```

Так блокируется подходящая строка `orders`, но не участвующая в соединении строка `customers`.

## Решите, стоит ли ждать

По умолчанию PostgreSQL ждёт освобождения несовместимой блокировки. Два модификатора дают осознанную альтернативу:

- `NOWAIT` сразу выдаёт ошибку, если выбранную строку нельзя заблокировать.
- `SKIP LOCKED` пропускает строки, которые нельзя заблокировать немедленно.

`NOWAIT` подходит для интерактивной работы или работы, чувствительной к задержкам, когда вызывающая сторона может повторить попытку или сообщить, что ресурс занят:

```sql
SELECT *
FROM inventory
WHERE product_id = 101
FOR UPDATE NOWAIT;
```

`SKIP LOCKED` предназначен для особого случая — таблиц-очередей с несколькими обработчиками. Каждый обработчик может забрать отдельную готовую задачу в рамках одной транзакции:

```sql
CREATE TABLE jobs (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  status text NOT NULL CHECK (status IN ('ready', 'running', 'done'))
);

INSERT INTO jobs (status)
VALUES ('ready'), ('ready');

BEGIN;

WITH next_job AS (
  SELECT id
  FROM jobs
  WHERE status = 'ready'
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs AS j
SET status = 'running'
FROM next_job
WHERE j.id = next_job.id
RETURNING j.*;

COMMIT;
```

Пропуск заблокированных строк намеренно даёт неполную картину, поэтому не используйте его для обычных отчётов или проверок корректности. Оба модификатора относятся к блокировкам строк: оператор всё равно может ждать нужную ему блокировку на уровне таблицы.

## Разберитесь в автоматических блокировках таблиц

Операторы, обращающиеся к таблицам, захватывают блокировки таблиц. Каждый режим конфликтует с определённым набором других режимов. Вопреки названиям, `ROW SHARE` и `ROW EXCLUSIVE` — это блокировки на уровне таблицы.

Полезнее всего уметь узнавать следующие режимы:

| Оператор или операция | Обычный режим на уровне таблицы | Практический эффект |
| --- | --- | --- |
| Обычный `SELECT` | `ACCESS SHARE` | Уживается с обычными чтением и записью; его блокирует только `ACCESS EXCLUSIVE`. |
| `SELECT ... FOR UPDATE` и другие чтения с блокировкой строк | `ROW SHARE` | Сообщает, что строки могут быть заблокированы, но допускает обычные чтение и запись. |
| `INSERT`, `UPDATE`, `DELETE` или `MERGE` | `ROW EXCLUSIVE` | Допускает параллельные изменения данных; конфликтующие блокировки строк по-прежнему выстраивают изменения одних и тех же строк в очередь. |
| `CREATE INDEX` без `CONCURRENTLY` | `SHARE` | Допускает чтение, но блокирует операторы, изменяющие данные. |
| `TRUNCATE`, `DROP TABLE`, `VACUUM FULL` и многие изменения схемы | `ACCESS EXCLUSIVE` | Конфликтует со всеми режимами, включая обычное чтение. |

Даже небольшое изменение схемы может застрять за долгой транзакцией, а за ним в очередь выстроятся другие сеансы. Прежде чем выполнять команду на нагруженной таблице, сверьтесь с документацией: какой именно режим блокировки она берёт.

Явную блокировку таблицы применяйте, когда этого требует правило. Например, обслуживание может запретить параллельные изменения данных, по-прежнему разрешая чтение:

```sql
BEGIN;

LOCK TABLE inventory IN SHARE MODE NOWAIT;
-- Perform the coordinated maintenance work.

COMMIT;
```

Всегда указывайте режим. Без него `LOCK TABLE` запрашивает `ACCESS EXCLUSIVE` — самый строгий режим. Явная блокировка таблицы должна выполняться внутри транзакции и удерживается до её завершения.

## Предотвращайте взаимоблокировки и восстанавливайтесь после них

**Взаимоблокировка (deadlock)** возникает, когда транзакции образуют цикл: каждая удерживает блокировку, нужную другой. PostgreSQL обнаруживает цикл и прерывает одну из транзакций, но какую именно, приложение предсказать не может.

Предотвратить взаимоблокировки помогает единый порядок захвата блокировок. Перевод средств может заблокировать оба счёта в порядке ключей, прежде чем менять любой из них:

```sql
BEGIN;

SELECT owner
FROM accounts
WHERE owner IN ('Alice', 'Bob')
ORDER BY owner
FOR UPDATE;

-- Apply both balance changes after both rows are locked.

COMMIT;
```

Все пути в коде, блокирующие эти счета, должны соблюдать один и тот же порядок. Если транзакции понадобится сильный режим блокировки объекта, берите его сразу, при первой же блокировке, а не повышайте позже. Делайте транзакции короткими. Никогда не держите транзакцию открытой, пока ждёте ввода от пользователя.

Взаимоблокировки всё равно могут случаться. Относитесь к ошибке взаимоблокировки как к сбою транзакции: откатите её и повторите всю операцию с самого начала — так же, как с повторяемыми сбоями транзакций из урока об уровнях изоляции.

## Найдите заблокированные сеансы

Если запрос как будто завис, начните с `pg_stat_activity` и функции PostgreSQL, которая показывает блокирующие процессы:

```sql
SELECT
  pid,
  pg_blocking_pids(pid) AS blocked_by,
  now() - query_start AS query_age,
  query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

`blocked_by` перечисляет идентификаторы процессов, которые стоят впереди каждого ожидающего сеанса. `query_age` измеряет время с начала запроса, а не только ожидание блокировки. Прежде чем отменять блокирующий сеанс, выясните, чем он занят.

Для более глубокого разбора `pg_locks` показывает запрошенные режимы и то, предоставлены ли они:

```sql
SELECT
  pid,
  locktype,
  relation::regclass AS relation,
  mode,
  granted,
  waitstart
FROM pg_locks
WHERE NOT granted
  AND (
    database IS NULL
    OR database = 0
    OR database = (SELECT oid FROM pg_database WHERE datname = current_database())
  );
```

Ожидание на уровне строки часто выглядит не как запись типа tuple, а как ожидание идентификатора транзакции сеанса, удерживающего блокировку строки. Используйте `pg_blocking_pids()`, а не пытайтесь вывести, кто кого блокирует, соединяя `pg_locks` с самой собой.

## Практика

Создайте в `postgresql_course` небольшую очередь задач:

```sql
DROP TABLE IF EXISTS practice_jobs;

CREATE TABLE practice_jobs (
  id bigint PRIMARY KEY,
  status text NOT NULL CHECK (status IN ('queued', 'running', 'done'))
);

INSERT INTO practice_jobs (id, status)
VALUES (1, 'queued'), (2, 'queued'), (3, 'queued');
```

Откройте два окна Terminal в macOS. В каждом сеансе начните транзакцию и выберите одну задачу в статусе queued, упорядочив по `id`, с `FOR UPDATE SKIP LOCKED LIMIT 1`. Оставьте сеанс A открытым после того, как он выберет первую строку, а затем выполните выборку в сеансе B. Обновите каждую полученную задачу до `running` и зафиксируйте обе транзакции.

Верните строкам статус `queued`. В сеансе A заблокируйте задачу `1` с помощью `FOR UPDATE` и оставьте транзакцию открытой. В сеансе B попробуйте заблокировать ту же строку с `NOWAIT`; получив ожидаемую ошибку, откатите сеанс B, а затем откатите сеанс A.

Задание выполнено, когда обработчики забирают задачи с разными идентификаторами, а попытка с `NOWAIT` сразу завершается ошибкой вместо ожидания. Когда обе транзакции завершатся, удалите `practice_jobs`.
