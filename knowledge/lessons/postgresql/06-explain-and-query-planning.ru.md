**Планировщик запросов** решает, как PostgreSQL будет выполнять запрос. Опираясь на статистику о данных, он оценивает стоимость возможных способов. Выбранный им **план выполнения** — это дерево операций: сканирования, фильтрации, соединения, группировки и сортировки строк.

`EXPLAIN` показывает план. `EXPLAIN ANALYZE` вдобавок выполняет оператор и сообщает результаты измерений.

## Предсказуемый пример

**Временная таблица** видна только текущему сеансу и удаляется, когда сеанс завершается. Здесь `generate_series` создаёт 100 000 строк. `ANALYZE` собирает статистику для планировщика:

```sql
CREATE TEMP TABLE plan_orders AS
SELECT
  n AS id,
  (n % 1000) + 1 AS customer_id,
  CASE WHEN n <= 100 THEN 'pending' ELSE 'paid' END AS status,
  CURRENT_DATE - (n % 30) AS placed_on
FROM generate_series(1, 100000) AS n;

ANALYZE plan_orders;
```

Изучите запрос, который группирует ожидающие оплаты заказы по клиентам и возвращает пять групп с наибольшим числом заказов:

```sql
EXPLAIN
SELECT customer_id, count(*) AS order_count
FROM plan_orders
WHERE status = 'pending'
GROUP BY customer_id
ORDER BY order_count DESC
LIMIT 5;
```

Обычный `EXPLAIN` строит план оператора, не выполняя его. Начинайте с него, если выполнение может оказаться медленным или изменить данные.

## Как читать дерево плана

Каждая операция — это **узел плана**, подробности о котором выводятся под ним. Отступ показывает место узла в дереве: родитель использует строки, которые выдают его потомки. Чтобы проследить путь данных, читайте план от самых глубоких узлов вверх.

Найдите в своём выводе для этого запроса следующие виды работы:

- Сканирование получает строки из `plan_orders` и применяет фильтр по `status`.
- Агрегирование группирует оставшиеся строки по `customer_id` и вычисляет `count(*)`.
- Сортировка упорядочивает группы по количеству.
- Ограничение останавливается после пяти выходных строк.

Названия узлов и числа зависят от версии PostgreSQL, статистики, конфигурации и данных. Прежде чем вникать в числа, определите, какую работу выполняет каждый узел.

Раздел с оценками обычно выглядит так:

```text
(cost=<startup>..<total> rows=<estimated-output-rows> width=<average-row-bytes>)
```

- `startup` — оценка работы, которую узел должен проделать, прежде чем выдать первую строку. У сортировки обычно есть такая начальная работа: сначала ей нужно собрать все входные данные.
- `total` — оценка работы, если узел выполнится до конца. Стоимость родителя включает работу его потомков, поэтому не складывайте стоимости всех узлов.
- `rows` — оценка числа строк, которые узел выдаёт, а не обязательно тех, которые он просматривает.
- `width` — оценка среднего размера каждой выдаваемой строки в байтах.

Стоимость в планировщике измеряется в условных единицах, а не в миллисекундах. С её помощью можно понять, почему PostgreSQL предпочёл один вариант плана другому; но не сравнивайте число стоимости напрямую с реальным временем.

## Сравнение оценок с действительностью

Теперь выполните тот же запрос только для чтения и соберите измерения:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, count(*) AS order_count
FROM plan_orders
WHERE status = 'pending'
GROUP BY customer_id
ORDER BY order_count DESC
LIMIT 5;
```

Здесь параметр `ANALYZE` запускает запрос, а отдельная команда `ANALYZE table_name` собирает статистику. Теперь план содержит `actual time` в миллисекундах, число выданных строк `rows` и `loops` — количество выполнений узла. Для повторяющихся узлов время и число строк усредняются по одному выполнению. Чтобы оценить общую работу такого узла, умножьте их на `loops`.

Сравните оценочное и фактическое значения `rows`. Сильное расхождение в глубоком узле может привести к неудачным решениям выше по дереву, ведь все оценки над ним опираются на него. `Rows Removed by Filter` показывает, сколько строк было просмотрено, но отброшено.

`BUFFERS` показывает, как PostgreSQL обращался к блокам таблиц и индексов. `hit` означает, что запрошенный блок уже находился в буферном кеше PostgreSQL. `read` означает, что PostgreSQL пришлось запросить блок у хранилища, хотя операционная система могла держать его в своём кеше. Счётчики буферов часто объясняют, почему два выполнения с похожей формой плана занимают разное время.

Не складывайте время узлов: измерения родителя включают его потомков. `Execution Time` сообщает время выполнения на сервере, без учёта планирования и отправки результатов клиенту. Измерения узлов помогают найти дорогостоящую работу; полное же время отклика приложения включает не только выполнение запроса.

## Цикл целенаправленной диагностики

Если запрос неожиданно медленный, действуйте по такой схеме:

1. Зафиксируйте точный текст SQL и типичные значения параметров. Разные значения могут давать совершенно разное число строк.
2. Выполните обычный `EXPLAIN` и прочитайте план от листьев вверх.
3. Если выполнять запрос безопасно, запустите `EXPLAIN (ANALYZE, BUFFERS)` в условиях, близких к реальным.
4. Найдите самое раннее сильное расхождение между оценочным и фактическим числом строк. Проверьте, не изменились ли данные существенно без обновления статистики; обновляет её `ANALYZE <table>`.
5. Ищите работу, умноженную на большое значение `loops`, большое число строк, отброшенных фильтром, дорогие сортировки и сканирования, которые обрабатывают гораздо больше строк, чем выдают.
6. Меняйте что-то одно за раз, получайте новый план и сравнивайте как результаты, так и измерения.

Последовательное сканирование — не обязательно проблема. Прочитать большую часть небольшой таблицы подряд может оказаться дешевле, чем выполнить множество разрозненных обращений. В следующем уроке объясняется, как индексы создают дополнительные пути доступа и как понять, подходит ли индекс для конкретной нагрузки.

## `EXPLAIN ANALYZE` — это выполнение

`EXPLAIN ANALYZE` выполняет и операции записи. Они изменяют данные, запускают триггеры (автоматические действия, привязанные к таблице), захватывают блокировки и могут ждать другие транзакции. Чтобы откатить обычные изменения таблицы, воспользуйтесь приёмом из урока о транзакциях:

```sql
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
UPDATE plan_orders
SET status = 'archived'
WHERE placed_on < CURRENT_DATE - 20;

ROLLBACK;
```

Делайте так, только если выполнение самой записи безопасно. Откат отменяет не все возможные последствия: например, не возвращает значения, израсходованные из последовательностей, и не отменяет действия, которые внешняя система выполняет в ответ на триггер. Рискованные или дорогие операторы лучше проверять не в production, а в представительной тестовой среде.

## Практика

Создайте временный набор данных, статистику которого можно намеренно сделать устаревшей:

```sql
CREATE TEMP TABLE practice_events AS
SELECT
  n AS id,
  (n % 500) + 1 AS actor_id,
  CASE WHEN n <= 100 THEN 'error' ELSE 'info' END AS event_type
FROM generate_series(1, 100000) AS n;

ANALYZE practice_events;
```

Выполните `EXPLAIN (ANALYZE, BUFFERS)` для запроса, который отбирает строки с `event_type = 'error'`, группирует их по `actor_id`, сортирует по `count(*)` по убыванию и возвращает первые пять групп. Запишите для узла сканирования оценочное и фактическое число строк, число строк, отброшенных фильтром, а также общее время выполнения на верхнем уровне.

Не запуская `ANALYZE`, установите `event_type = 'error'` во всех строках с `id <= 20000` и снова получите план. Найдите первое существенное расхождение между оценочным и фактическим числом строк. Обновите статистику, получите тот же план в третий раз и сравните оценку.

Задание выполнено, когда вы можете показать, как устаревшая статистика изменила оценку, и при этом не путаете стоимость в планировщике с затраченными миллисекундами. Временная таблица исчезнет, когда завершится сеанс.
