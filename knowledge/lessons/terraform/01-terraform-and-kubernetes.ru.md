Terraform следует идее `infrastructure as code` (инфраструктура как код): вы описываете инфраструктуру в текстовых файлах, храните их в Git, а реальные объекты создаёт инструмент. Эти файлы проходят ревью, как любой другой код, и одни и те же файлы всегда описывают одну и ту же конфигурацию. Terraform способен управлять всем, у чего есть API: облачными сетями, кластерами Kubernetes, базами данных, DNS-записями и объектами внутри кластера.

Kubernetes-разработчик уже работает так со своими приложениями. В этом уроке Terraform раскладывается на знакомые вам понятия Kubernetes, чтобы дальше можно было сосредоточиться на практике.

## То же желаемое состояние, другой язык

Вот namespace в виде манифеста Kubernetes:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: demo
```

А вот тот же namespace в Terraform:

```hcl
resource "kubernetes_namespace_v1" "demo" {
  metadata {
    name = "demo"
  }
}
```

Файлы Terraform пишутся на `HCL` (HashiCorp Configuration Language) и имеют расширение `.tf`. Блок `resource` объявляет один объект, которым управляет Terraform. Первая метка, `kubernetes_namespace_v1`, — это тип ресурса. Вторая, `demo`, — локальное имя, по которому к ресурсу обращается остальной код Terraform. Оба файла декларативны: они описывают результат, а не шаги, которые к нему ведут.

Главное различие кроется не в синтаксисе, а в том, кто и когда воплощает описание в жизнь.

## Plan и apply вместо цикла управления

В Kubernetes команда `kubectl apply` сохраняет объект в API-сервере, а дальше за ним неотрывно следят контроллеры. Если Pod упал или кто-то отредактировал Deployment, контроллер это заметит и вернёт желаемое состояние. Этот непрерывный процесс называется reconciliation.

У Terraform нет постоянно работающего процесса — он действует, только когда вы запускаете команду:

1. `terraform plan` читает ваши `.tf`-файлы, через API проверяет реальные объекты и сравнивает одно с другим. Результат — `plan`: список объектов, которые нужно создать, изменить или удалить. В конце выводится сводка вроде `Plan: 1 to add, 0 to change, 0 to destroy.` Пока ничего не изменилось.
2. `terraform apply` показывает план, просит подтверждения и затем вносит изменения в правильном порядке. Этот шаг называется `apply`.
3. Terraform сохраняет сведения о сделанном и завершает работу.

Выходит, что Terraform сверяет состояние один раз за запуск, а человек видит изменение до того, как оно произойдёт. Между запусками за объектами никто не следит. Если кто-то вручную поменяет управляемый объект, Terraform ничего не предпримет, пока следующий `plan` не покажет расхождение. Такое расхождение между кодом и реальным миром называется `drift`; о нём пойдёт речь в пятом уроке.

## Провайдер вместо контроллера

Контроллер или оператор Kubernetes умеет воплощать в жизнь ресурсы одного вида. В Terraform есть похожая идея: провайдер (`provider`) — это плагин, который знает один API. Провайдер `kubernetes` общается с API-сервером Kubernetes, провайдер `helm` устанавливает чарты, а облачные провайдеры работают с AWS, Google Cloud или Azure. Каждый провайдер определяет свои типы ресурсов, например `kubernetes_namespace_v1` или `kubernetes_deployment_v1`.

В отличие от контроллера, провайдер не живёт в кластере. Terraform запускает его на вашей машине или в CI-задаче на время команды, и с её окончанием провайдер останавливается. Провайдер `kubernetes` читает ваш kubeconfig и обращается к API-серверу точно так же, как kubectl.

При этом Terraform не заменяет контроллеры Kubernetes. Когда Terraform создаёт Deployment, ReplicaSet и Pods по-прежнему создаёт контроллер Deployment. Terraform управляет только теми объектами, которые вы объявили в его файлах.

## State вместо etcd

Kubernetes хранит все объекты в etcd, за API-сервером. Terraform же нужна собственная запись о том, чем он управляет. Эта запись называется `state`. По умолчанию это JSON-файл `terraform.tfstate` в каталоге проекта.

State связывает каждый блок ресурса в коде с реальным объектом — например, `kubernetes_namespace_v1.demo` с namespace `demo` в вашем кластере — и хранит последние известные атрибуты этого объекта. Перед каждым планом Terraform обновляет state по данным реальных API, поэтому план сравнивает код с тем, что существует на самом деле.

State — это не реальный мир и не ваш код, а память Terraform. Потеряв её, Terraform забудет, что эти объекты создал он. Кроме того, в state могут оказаться секреты, так что обращайтесь с файлом бережно. Команды держат state в общем удалённом хранилище — об этом расскажет десятый урок.

## Бок о бок

| Понятие | Kubernetes | Terraform |
| --- | --- | --- |
| Желаемое состояние | YAML-манифесты | `.tf`-файлы на HCL |
| Единица работы | Объект определённого вида | Ресурс определённого типа |
| Знает API | Контроллер или оператор | Провайдер |
| Когда происходят изменения | Непрерывно, в цикле управления | Только при запуске `apply` |
| Предпросмотр изменений | `kubectl diff` | `terraform plan` |
| Запись об объектах | etcd за API-сервером | Файл state |
| Охват | Объекты одного кластера | Всё, у чего есть API, включая сами кластеры |

## Где место Terraform, Helm и kubectl

Создавать объекты Kubernetes умеют все три инструмента, поэтому команды обычно делят между ними работу:

- Terraform создаёт сам кластер, облачные ресурсы вокруг него — сети, базы данных, DNS — и общие платформенные компоненты: namespaces, правила доступа или ingress-контроллер.
- Манифесты Kubernetes и Helm-чарты описывают приложения. Разворачивает их обычно CI-конвейер или GitOps-инструмент вроде Argo CD или Flux.
- kubectl нужен, чтобы осматриваться и отлаживать: `get`, `describe`, `logs` и быстрые эксперименты.

В вашей команде граница может проходить иначе. Важно одно правило: у каждого объекта один владелец. Если одним и тем же Deployment управляют и Terraform, и Argo CD, каждый из них будет отменять изменения другого.

В этом курсе Terraform управляет объектами Kubernetes напрямую. Локальный кластер позволяет практиковаться без облачного аккаунта, а язык, plan, apply и state для облачных ресурсов работают точно так же.

## Пара слов об OpenTofu

В некоторых репозиториях вместо `terraform` встречается `tofu`. OpenTofu — открытый форк Terraform. Он появился в 2023 году, после того как HashiCorp перевела Terraform на Business Source License, и развивается под эгидой Linux Foundation. Язык конфигурации у него тот же, так что большая часть курса применима и к нему.

## Проверьте себя

Deployment `web` управляется через Terraform с `replicas = 2`. Коллега выполняет `kubectl scale deployment web --replicas=5`. Подумайте над двумя вопросами:

- Что произойдёт сразу? Со стороны Terraform — ничего. Ни один процесс Terraform не запущен, и у Deployment остаётся 5 реплик.
- Что произойдёт при следующем `terraform plan`? Terraform обновит state, увидит 5 вместо 2 и предложит вернуть Deployment к 2 репликам. Вам решать, применить это изменение или поправить код.
