В предыдущих уроках вы много раз запускали `plan` и `apply`, и каждый раз Terraform точно знал, какой Deployment в кластере — его `web`. Это знание он берёт из state. В этом уроке мы разберёмся, что хранится в state, что происходит, когда кто-то вручную меняет управляемый объект, и как заглянуть в state, ничего не сломав.

## Зачем Terraform нужен state

После первого `apply` в каталоге `terraform-course` появился файл `terraform.tfstate`. Это и есть `state` — JSON-запись обо всех объектах, которыми Terraform управляет в этом проекте.

Kubernetes обходится без такого файла: его API-сервер хранит и объекты, которые вы запросили, и их текущий статус. Terraform же работает с множеством самых разных API, и у большинства из них нет места для собственных заметок Terraform. Поэтому он ведёт отдельную запись и опирается на неё в трёх случаях:

- **Сопоставление.** State связывает каждый адрес ресурса в коде, например `kubernetes_deployment_v1.web`, с идентификатором реального объекта, например `demo/web`. Без этой связи Terraform не смог бы понять, какие объекты принадлежат ему, и не знал бы, что удалять, когда вы убираете блок из кода.
- **Метаданные.** State помнит зависимости между ресурсами. Даже когда ресурсы уже исчезли из кода, Terraform знает, в каком порядке их безопасно удалить.
- **Производительность.** State хранит копию атрибутов каждого объекта. Terraform может пользоваться этой копией, а не опрашивать API о каждом объекте, — в очень больших проектах это ощутимо.

У `kubectl apply` есть похожая память: последний применённый манифест он сохраняет в аннотации `kubectl.kubernetes.io/last-applied-configuration` прямо на объекте. Terraform держит свою память вне объектов — в одном файле.

Откройте `terraform.tfstate` в редакторе и посмотрите на него, но ничего не меняйте. Фрагмент файла выглядит примерно так:

```json
{
  "version": 4,
  "serial": 6,
  "resources": [
    {
      "mode": "managed",
      "type": "kubernetes_deployment_v1",
      "name": "web",
      "instances": [
        {
          "attributes": {
            "id": "demo/web"
          }
        }
      ]
    }
  ]
}
```

Поля `type` и `name` вместе дают адрес `kubernetes_deployment_v1.web`. Поле `id` указывает на настоящий Deployment `web` в пространстве имён `demo`. Число `serial` растёт всякий раз, когда Terraform записывает новую версию state.

## Три взгляда на один объект

Каждый управляемый объект теперь существует в трёх местах:

| Взгляд | Где находится | О чём говорит |
| --- | --- | --- |
| Конфигурация | Ваши файлы `.tf` | Чего вы хотите |
| State | `terraform.tfstate` | Что Terraform увидел при последнем запуске |
| Реальный мир | Объекты в кластере | Что существует прямо сейчас |

Обычно все три согласуются. `Drift` — это ситуация, когда реальный мир расходится с тем, что записал Terraform. Так бывает, если кто-то меняет управляемый объект в обход Terraform: через `kubectl`, через дашборд или другим инструментом.

## Как plan находит drift

Любой `plan` начинается с шага `refresh`: Terraform просит провайдер прочитать из реального мира каждый объект, записанный в state. Строки `Refreshing state...` в выводе — это и есть этот шаг. Затем Terraform сравнивает конфигурацию со свежей картиной и предлагает изменения, которые приведут реальный мир в соответствие с кодом.

Обычный `plan` не сохраняет обновлённые данные в файл state. Новый state записывает только `apply`.

## Создаём drift намеренно

В примерах ниже предполагается, что `var.replicas` равно `2`. Если у вас другое значение, числа в выводе тоже будут другими.

Измените число реплик за спиной у Terraform:

```sh
kubectl scale deployment/web --replicas=5 -n demo
kubectl get deployment web -n demo
```

Через несколько секунд у Deployment будет 5 готовых подов. Для Kubernetes 5 теперь и есть желаемое состояние, и его контроллер всем доволен. Команда `kubectl edit deployment web -n demo` привела бы к тому же результату.

Теперь спросите Terraform:

```sh
terraform plan
```

Terraform обновляет сведения о Deployment, видит 5 реплик, сравнивает это с кодом и планирует вернуть всё назад. Сокращённый фрагмент вывода:

```text
  # kubernetes_deployment_v1.web will be updated in-place
  ~ resource "kubernetes_deployment_v1" "web" {
      ~ spec {
          ~ replicas = "5" -> "2"
        }
    }

Plan: 0 to add, 1 to change, 0 to destroy.
```

Провайдер хранит `replicas` как строку, поэтому значения выводятся в кавычках. Выполните `terraform apply` и подтвердите словом `yes`, чтобы вернуть Deployment к двум репликам.

В этом и состоит главное отличие от Kubernetes. Контроллер Deployment непрерывно следит за своими объектами и за считаные секунды восстанавливает пропавший под. Terraform — не контроллер: он ни за чем не следит и сверяет состояние, только когда кто-то запускает `plan` или `apply`. Между запусками кластер может расходиться с кодом часами и неделями. Именно поэтому команды вносят изменения через код Terraform, и именно поэтому неожиданное изменение в плане заслуживает вопроса на ревью.

## Принимаем изменение вместо отката

Иногда ручное изменение было верным — скажем, быстрой правкой во время инцидента. Тогда хочется, чтобы Terraform его запомнил, а не откатил. Снова создайте drift:

```sh
kubectl scale deployment/web --replicas=5 -n demo
terraform plan -refresh-only
```

План в режиме `refresh-only` не предлагает менять кластер. Он лишь показывает, что изменилось в обход Terraform, и предлагает обновить state. Сокращённый фрагмент:

```text
Note: Objects have changed outside of Terraform

Terraform detected the following changes made outside of Terraform since the
last "terraform apply":

  # kubernetes_deployment_v1.web has changed
  ~ resource "kubernetes_deployment_v1" "web" {
      ~ spec {
          ~ replicas = "2" -> "5"
        }
    }

This is a refresh-only plan, so Terraform will not take any actions to undo
these. If you were expecting these changes then you can apply this plan to
record the updated values in the Terraform state without changing any remote
objects.
```

Чтобы сохранить новые значения, выполните:

```sh
terraform apply -refresh-only
```

Terraform попросит подтверждения, запишет 5 в state и не тронет кластер. Теперь запустите обычный план:

```sh
terraform plan
```

Он по-прежнему предлагает `"5" -> "2"`, потому что в коде всё ещё написано 2. Refresh-only apply обновляет память Terraform, но не ваше намерение. Чтобы оставить 5 реплик, поменяйте значение `replicas` в коде. В рамках курса выполните `terraform apply` и верните 2.

## Безопасно заглядываем в state

Для повседневных вопросов не нужно читать JSON-файл. Следующие команды только читают state и никогда его не меняют:

```sh
terraform state list
terraform state show kubernetes_deployment_v1.web
terraform show
```

- `terraform state list` выводит адреса всех ресурсов в state, например `kubernetes_deployment_v1.web`, `kubernetes_namespace_v1.demo` и `kubernetes_service_v1.web`.
- `terraform state show <address>` показывает все записанные атрибуты одного ресурса в виде, похожем на HCL.
- `terraform show` выводит весь последний state в том же удобочитаемом виде.

Эти команды не выполняют refresh. Они показывают то, что Terraform записал при последнем запуске, а это может отличаться от кластера. Чтобы сверить данные с реальным миром, запустите `terraform plan`.

## Храним state в тайне и не трогаем руками

С state нужно обращаться так же бережно, как с файлом паролей:

- **В нём открытым текстом лежат секреты.** Если конфигурация создаёт `kubernetes_secret_v1`, его данные попадают в state. Пометка `sensitive` скрывает значение в выводе CLI, но не в state. Команда `terraform show -json` тоже печатает такие значения открытым текстом.
- **Никогда не коммитьте его.** Если `terraform-course` — Git-репозиторий, убедитесь, что в его `.gitignore` есть такие строки:

  ```gitignore
  .terraform/
  *.tfstate
  *.tfstate.*
  ```

  Второй шаблон заодно закрывает `terraform.tfstate.backup` — предыдущую версию, которую Terraform хранит рядом с state.

- **Никогда не правьте его вручную.** Неверный идентификатор или испорченный файл могут привести к тому, что Terraform потеряет объект из виду или запланирует его удаление. Меняйте state только командами Terraform.

## Команды, которые меняют state

Они нужны редко, но могут встретиться в заметках вашей команды:

- `terraform state mv` переносит объект на новый адрес — например, после переименования блока ресурса. Тогда Terraform сохраняет объект, а не удаляет и создаёт его заново.
- `terraform state rm` заставляет Terraform забыть объект, не удаляя его. Объект остаётся в кластере, но Terraform им больше не управляет.

В современном коде вместо них часто используют блоки `moved`, `removed` и `import`. Они описывают те же операции в конфигурации, поэтому изменение появляется в обычном плане и проходит ревью. В этом курсе они вам не понадобятся.

## State в команде

Локальный `terraform.tfstate` подходит одному человеку на одном ноутбуке. Команде нужен общий state и блокировка, чтобы двое не запустили `apply` одновременно. Remote state и блокировки разбираются в уроке о командной работе.
